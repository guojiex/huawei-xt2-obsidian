# 邮件反馈拉起方式（API24）

## 用户转交的 AI 答复要点

- 系统邮件能力用于拉起邮件应用并预填收件人、主题、正文，最终由用户确认发送；不是后台静默发送接口。
- 提议通过 mailto + startAbility，或 startAbilityByType('mail', …) 打开邮件应用。
- 静默发送需另建服务端中转；客户端不放 SMTP 凭据。
- 没有邮件客户端时拉起可失败；邮件参数必须编码。

原答复只有 rsub 引用标识，没有实际官方页面地址；其概括与完整邮件匹配行为不能单凭该答复视为设备验证。

## 本机 SDK 26.0.0.105 核对

`openharmony/ets/api/application/UIAbilityContext.d.ts`：

- 第 247 行：`startAbility(want: Want, options?: StartOptions): Promise<void>`，since 9。
- 第 985 行：`startAbilityByType(type: string, wantParam: Record<string, Object>, abilityStartCallback: AbilityStartCallback): Promise<void>`，since 11，要求前台。**用户转交示例的两参数调用缺少必需的第三参数，不能照抄**。
- `@ohos.app.ability.wantConstant.d.ts` 第 418 行有 `ACTION_SEND_TO_DATA = 'ohos.want.action.sendToData'`。

接口与 action 存在不等于已经证明设备安装了邮件客户端或其 mailto 处理行为。邮件服务匹配、收件人/中文/特殊字符、无客户端、取消返回及 API24/XT2 仍待运行验收；不据 SDK 声明推导后台静默能力。

## 本项目选择

沿用已定邮箱方案，首选 mailto + startAbility 创建草稿，邮箱真源为 app_config.json，不新增后台、SMTP、权限或第二套面板实现。subject/body 每个参数值用 encodeURIComponent 编码，不手工只替换部分字符，不把完整 URI 一并编码。当前仅预填收件人和固定主题，不读取/附带笔记或日志。

同时捕获同步异常与 Promise 拒绝；失败提示“未能打开邮件应用，请使用下方邮箱地址手动反馈”，地址保持可见。调用成功最多说明邮件应用已打开，不能说明发送或送达成功。不得为了验收自动发送邮件；用户在邮件应用自行确认。浏览器原型的 mailto 只证明链接内容，不替代原生验收。
