## 1. 目录选择：能否选目录、返回什么

本机 `@ohos.file.picker.d.ts`：

| 项 | 声明 | 起始版本 | 是否 ≤ API 24 |
| --- | --- | --- | --- |
| `DocumentViewPicker.select(option?): Promise<Array<string>>` | 启动 documentPicker 页面，返回所选 URI 数组 | `@since 9` | ✅ |
| `DocumentSelectOptions.selectMode?: DocumentSelectMode` | 所选文档类型，默认 FILE | `@since 11` | ✅ |
| `DocumentSelectMode.FOLDER = 1` | 选目录 | `@since 11`，syscap `FileManagement.UserFileService.FolderSelection` | ✅ |
| `DocumentSelectOptions.maxSelectNumber` | 注释写明「Directories can be selected only on devices that have the system capability. **A maximum of one directory can be selected at a time.**」 | `@since 10` | ✅ |
| `DocumentSelectOptions.authMode` | 注释写明「**This parameter can be used on 2-in-1 devices but has no effect on other devices.**」 | `@since 12` | （手机上无效） |

要点：

- API 24 **确实有官方的「选目录」入口**，不需要自己做目录浏览器。
- 但每次只能选一个目录；也二合一设备的 `authMode` 在手机上无效果，不能依赖它。
- 目录选择依赖 syscap `FolderSelection`，实施前要用 `canIUse()` 判一遍设备是否具备。

## 2. 持久授权：跨应用重启 / 设备重启能不能保住

本机 `@ohos.fileshare.d.ts`：

| API | 签名 | 起始版本 | 所需权限 |
| --- | --- | --- | --- |
| `persistPermission(policies: Array<PolicyInfo>): Promise<void>` | 把已拿到的**临时权限**持久化 | `@since 11` | `ohos.permission.FILE_ACCESS_PERSIST` |
| `activatePermission(policies): Promise<void>` | 激活已持久化授权 | `@since 11` | 同上 |
| `deactivatePermission(policies): Promise<void>` | 停用 | `@since 11` | 同上 |
| `revokePermission(policies): Promise<void>` | 撤销 | `@since 11` | 同上 |
| `checkPersistentPermission(policies): Promise<Array<boolean>>` | 检查某个 URI 是否已持久化 | `@since 17` | 同上 |

`PolicyInfo` = `{ uri: string; operationMode: number }`；`OperationMode` 为位标记 `READ_MODE=0b1` / `WRITE_MODE=0b10`（`CREATE_MODE` / `DELETE_MODE` 起始 20，> API 24，不可用）。
`PolicyErrorCode`：`PERSISTENCE_FORBIDDEN=1`、`INVALID_MODE=2`、`INVALID_PATH=3`、`PERMISSION_NOT_PERSISTED=4`；存在任一 URI 失败时抛 13900001，失败清单在异常的 `data` 里。

⚠️ **关键阻塞**：`persistPermission` 等五个接口**全部**要求 `ohos.permission.FILE_ACCESS_PERSIST`。

- 华为官方 FAQ（如何使用公共目录下的数据库文件）写明：该权限**属于 ACL 受限权限**，APL 等级 **system_basic**，普通 normal 级应用需要通过 ACL 跨级申请。
- 同一 FAQ 写明：持久化授权数据存在系统数据库；**应用或设备重启后需要调用 `activatePermission()` 激活**才能继续用。
- 本工程当前 `module.json5` 只申请 `INTERNET`（仓库手册硬约束 13），新增受限权限是**许可边界变更**，须用户先拍板，不能直接落码。

## 3. 递归读写：拿到目录 URI 后怎么遍历与编辑

- SDK 侧 `fileIo.openSync(uri, OpenMode.READ_ONLY)` 接受 URI，`listFileSync(path, ListFileOptions)` 支持 `recursion` 与多种过滤（仓库已在 v1.3 用 `copyFile` 处理 Picker 图片附件，见 [api_notes Q1](api_notes.md#q1-picker-uri-的授权范围与-sdk-声明存在不同表述)）。
- 华为社区 / 开发者论坛给的做法是「用 Picker 返回的目录 URI `openSync` 取 fd，再 `listFile`」，示例代码存在，但**不是官方 API 保证**。
- ❓待设备确认的三件事：① 对目录 URI 的临时 / 持久授权是否顺延到子文件与新建文件；② 在这个 URI 空间里能否直接使用本工程现有 `AtomicFile`（AtomicFile 的输入是哪一种路径/URI，仓库手册硬约束 10 只覆盖沙箱内路径）；③ 外部删除 / 移动后 `statSync` / `listFileSync` 的失败形态。

## 4. 另一款软件能否管理同一目录（15.4 的前置）

- Picker + `fileshare` 只是**本应用视角**的授权；能否让 PC 工具 / 云盘客户端管理同一份文件，取决于那个目录本身所在的命名空间（例如 `Download` 的公共目录），而不是本 App 授予的权限。
- ❓没有任何本地证据能回答此项；需要选定具体场景（例如 Download 下的某个目录）后在真机/设备实测。

## 5. 与仓库现有约束的关系（实施前必须解决的冲突）

1. 硬约束 13「沙箱内读写不需要任何权限，只申请 INTERNET」——持久授权路线要新增 ACL 受限权限 **FILE_ACCESS_PERSIST**，需用户拍板。
2. 硬约束 14「库内相对路径 → 绝对路径只用一层解析器」——外部目录的授权 URI 与沙箱路径是两套命名空间，解析器如何统一需要在核实通过后单独定案。
3. 硬约束 10 / 15（`AtomicFile`）——已有文件保存仍走 AtomicFile；它是否支持目录 URI 需先验证（见 §3）。

## 结论（2026-10-31）

- 目录选择能力✅（API 24 可用，官方 `DocumentSelectMode.FOLDER`）。
- 持久授权能力✅存在，但**依赖 ACL 受限权限**，这是产品与安全边界决策，不是技术细节。
- 递归读写、跨应用共管、外部变更感知均为❓，需要 XT2 / API 24 设备实测。
- 因此 v1.5 在用户拍板是否申请 `FILE_ACCESS_PERSIST` 之前**不落码**；即便拍板通过，也要先在设备上跑通示例，再回填 §1–§4。
