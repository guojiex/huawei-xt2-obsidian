## 一句话结论

官方确认：**ArkTS 侧确实没有基于目录 URI 的枚举 API**（我们的实测与 SDK 契约判断完全正确）；
但链路没断，可行路径是

> **ArkTS `fs.openSync(目录URI, READ_ONLY|DIR)` 拿目录 fd → 把 fd 传给 Native →
> POSIX `fdopendir()` + `readdir()` + `openat()` 递归遍历**

我们的 Q5-C（「不存在授权一次外部目录、长期自由读写的形态」）**不成立**，产品形态不用改。

### ⚠️ 答复中的硬伤

官方示例写的是 `fs.openSync(dirUri, fs.OpenMode.READ_DIR)` ——
**`OpenMode.READ_DIR` 不存在**。本机 `@ohos.file.fs.d.ts`：

| 行 | 声明 |
| --- | --- |
| 199 | `const DIR = 0o200000;` |
| 1012 / 1109 / 2453 … | `- **OpenMode.DIR(0o200000)**: If **path** does not point to a directory, throw an exception.` |

正确写法是 **`OpenMode.READ_ONLY | OpenMode.DIR`**。直接抄答复过不了编译，
我们自己在 `ExternalDirProbeDevice.ets` 里就是这么改的。

> 顺便注意 `OpenMode.DIR` 的语义："path 不是目录就抛异常" —— 它是**约束**不是权限，
> 所以目录 fd 必须组合读模式使用。

## 设备实测证据（XT2，2026-10-31 21:02）

核实页 `pages/ExternalDirProbePage` 跑完整时序，hilog tag `ProbeRunner`：

```
select            ok=true   URI = file://docs/storage/Users/currentUser/Download
persist           ok=true   临时授权已持久化
check             ok=true   checkPersistentPermission 为 true
activate          ok=true   activatePermission 未抛错
list              ok=false  listFileSync → 13900002        ← 复现已知结论
native_flat       ok=true   单层 fdopendir 拿到 16 条
native_recursive  ok=true   递归 31 条｜含 com.xueqiu.hm/600066_..._q231.pdf 这类子目录路径
atomic            ok=false  code=-1                        ← T6，尚未定位
```

两个关键读数：

1. **单层 16 条**＝Picker 列表里显示的「Download … 16 项」——`fdopendir` 能吃下这个 fd，
   数量口径与 Picker 自报一致。
2. **递归 31 条，且出现 `com.xueqiu.hm/xxx.pdf` 这种带子目录前缀的路径**——
   说明 `openat(fd, 子项名)` 成功进入子层，**授权确实顺延到子目录**。31 条还算少了Download下如此多——
   因为当时 Picker 列表项本身只有 16 个顶层条目，子层内容不多；数量不是重点，重点是**有子层路径**。

对照：同一 URI 的 `listFileSync` 依旧 **13900002**。两个接口、同一个串、同一时刻 —— 差异只有一个解释，
就是 `listFile` 的 path 契约不含 URI。

| 下方产 Sukbet：写入链路（AtomicFile 对 URI 的可行性） | ❌ **未验证**，见 api_notes **T6** |

**Native 侧注意事项（答复提醒 + 我们已实现）**：`fdopendir` 会接管 fd 所有权，
必须先 `dup()` 再传入，否则 ArkTS 侧稍后的 `closeSync` 会 double close。
本项目实现见 `vaultdir_napi.c` 的 `vaultdir_scan()`，`dup` 之后立即 `fdopendir`，`closedir` 收尾。
