## 后续核实应收敛到的缺口

1. 保留自有聊天工作区时，是否存在 App 主动调用小艺模型、传历史/动态提示词并接收流式消息和结构化工具调用的正式协议？端 A2A 服务端不自动回答这个问题。
2. API 24 端 A2A 的完整收发/鉴权实现是什么？S4 称支持 API 24，但其链接的 S7 helper 从 26.0.0 起提供；不能直接照抄 helper，也不能因此断言 API 24 不支持端 A2A。
3. 独立核实 InsightIntentEntry 的 API 24 声明/配置和平台发布路径，再判断本地笔记工具应走意图工具还是已有 Agent 的 A2A 适配。
4. 核实个人开发者与未正式发布 App 的测试条件。S4 列出了 AGC 发布前置，测试白名单不等于自动豁免前置。
5. 继续追问执行时限、取消/重复调用/进程回收语义、后台场景资格和正文端云边界；编辑保护与 AtomicFile 由项目服务保障，不视为平台自动提供。

本次只核对与归档文档，未开通能力、未配置平台、未调用模型、未修改应用代码或做设备验收。

SDK 辅助核对：本机 `/Applications/DevEco-Studio.app/Contents/sdk/default/hms/ets/kits/@kit.AgentFrameworkKit.d.ts` 只导出功能组件/控制器和 A2A 服务端相关类型；`@hms.ai.AgentFramework.d.ets` 没有导出通用模型聊天/工具调用客户端。`openharmony/ets/api/@ohos.app.ability.InsightIntentExecutor.d.ts` 的后台执行方法 since 11，返回类型包含 Promise。这里只证明声明，不证明设备时限、并发和平台资格。

## 同日代码接线核对

仓库只读核查：`AgentRuntime.executeStep` 是依赖本地 session/references 的私有方法，不能直接视为平台参数入口；可复用 NoteService、VaultPathResolver 和操作记录逻辑，但仍须为正式端插件补参数映射、结构化返回、授权上下文和重放语义。本次未实施代码、未调用真实端插件。

架构判断见 [api_notes F12–F14](../api_notes.md)。先前对“意图框架方向错误”的口头判断过强：S8/S10 已证明它可作为托管 Agent 的本地工具桥；缺失的是把托管模型假定成自有聊天页 Provider 的依据。保留自有 UI 时，接入明确支持历史/流式/工具调用的模型服务是工程建议，尚未选择供应商、增加版本需求或授权发送笔记正文。
