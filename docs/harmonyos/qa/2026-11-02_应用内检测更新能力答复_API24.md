## 二、官方答复与我方 SDK 核对的两处分歧（**别照答复落码**）

### 1. `versionName` / `versionCode` 不是「应用场景返回 undefined」这么简单

- 答复：字段存在，「仅元服务场景返回，应用场景调用时返回 undefined」。
- SDK 实际：`CheckUpdateResult.updateAvailable` 是 `@since 5.0.0(12)`；而 **`versionName?` 与 `versionCode?` 本身是 `@since 6.0.0(20)`** 才加入的字段，注释为「This parameter is available only for atomic services」。同一文件里 `on('updateChange')` / `UpdateSessionState` / `RequestErrorCode` 也全是 `@since 6.0.0(20)` 的元服务侧能力。
- 结论：语义方向与答复一致（**应用侧拿不到市场版本号**），但「返回 undefined」是答复的运行时推断，SDK 只承诺「仅元服务可用」，是否真为 `undefined`、还是缺省 / 空串，**未实测**。
- **本版一律不读这两个字段**：界面不下「目标版本号」，更不做客户端版本比较。有/无更新只以 `updateAvailable` 枚举为准。

### 2. 「至少 30 分钟一次」不是挂在 `checkAppUpdate` 上的

- 答复：引官方建议「建议仅在用户主动点击时调用一次，或设置至少 30 分钟的调用间隔」。
- SDK 实际：那段「每天最多六次、每 30 分钟仅一次」的 NOTE 挂在 **`on(type: 'updateChange')`（元服务更新监听，`@since 6.0.0(20)`）** 的文档块上；`checkAppUpdate` 只声明会抛 `1009400006 - Time limited`，**没有给出阈值数字**。
- 结论：30 分钟 / 六次是**元服务监听接口**的已记载约束，不能原样当 `checkAppUpdate` 的官方阈值。`checkAppUpdate` 的实际限流阈值 **❓ 未记载**。
- 落码取保守工程选择：只在用户主动点击时调用，本会话内做冷却，冷却值是工程选择不是官方承诺（需在 [api_notes V5](../api_notes.md) 记明这个区分）。
