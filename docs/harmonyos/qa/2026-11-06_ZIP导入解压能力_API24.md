# ZIP 导入解压能力核对（API 24）

> 这是本机 SDK 类型声明核对，不是向官方 Agent 发起的新问答。
> 本机 HarmonyOS SDK：`C:\Program Files\Huawei\DevEco Studio\sdk\default\openharmony`（DevEco Studio 26.0）；工程兼容 API 为 `6.1.1(24)`。因此这里记录的是 API 起始版本与签名证据，不代表 API 24 或 XT2 运行验收。
> 背景：[v1.36 需求文档 §5](../../releases/v1.36/需求文档.md) 的三项前置核实（逐条目解压 / picker 限定 `.zip` / 取消与空间不足）。

## 1. ZIP 解压能力（前置核实项 1）✅ 逐条目方案成立

- 本机 `openharmony/ets/api/@ohos.zlib.d.ts`（`@kit.BasicServicesKit`）声明：
  - `decompressFile(inFile, outFile, options?): Promise<void>` since 9（回调重载 since 9/10）：**整包解压**到已存在的 `outFile` 目录，同名覆盖；inFile 扩展名必须 `.zip`；非 ZIP 或损坏抛 `900003`；API 13 起 inFile/outFile 含 `..` 抛 `900001`/`900002`，**ZIP 内条目名含 `../` 抛 `900003`**（声明注释原文）。
  - `getOriginalSize(compressedFile): Promise<number>` since 12：返回 ZIP 原始（解压后）总字节数。
  - `createZipSync(): Zip` since 12；`Zip.inflateInit2(strm, windowBits)` since 12，**windowBits 取 [-15,-1] 即 Raw Deflate**（ZIP 条目 method 8 的载荷格式）；`Zip.inflate(strm, flush): Promise<ReturnStatus>` since 12；`inflateEnd(strm)` since 12；`ZStream`（`nextIn`/`availableIn`/`nextOut`/`availableOut`/`totalOut`）since 12。
- 结论：**v1.36 需求 §5 的「若 1 不成立则回炉」不触发**。ArkTS 侧可自绘 ZIP 解析：`fileIo`/`fs` 读文件字节 → 解析 End of Central Directory 与 Central Directory（条目名、压缩前后大小、method、general purpose flag、external attributes）→ **解压前**校验全部条目（绝对路径、`..` 越级、反斜杠、盘符、加密标志位、symlink 模式位、ZIP64、条目数与总大小上限）→ 逐条目 `inflateInit2(strm, -15)` + `inflate` 解压 → `fs` 写入临时库目录。拒绝 `..`/绝对路径由**我方条目名校验**在解压前完成，不依赖 `decompressFile` 的运行时拒绝。
- `CompressFlushMode.FINISH`（since 12）用于 `inflate` 的 flush 参数；`ReturnStatus.STREAM_END`（since 12）表示单条目解压完成。
- `Options.pathSeparatorStrategy`（反斜杠替换，since 21）仅作用于 `decompressFile` 整包路径且 API 24 不可用——**不得引用**；自绘解析对反斜杠条目名直接按非法拒绝即可。

## 2. 文件选择器限定 `.zip`（前置核实项 2）✅ 成立

- 本机 `openharmony/ets/api/@ohos.file.picker.d.ts`：`DocumentSelectOptions.fileSuffixFilters?: Array<string>` **since 10**，格式如 `'笔记库备份|.zip'`（描述|后缀；无描述可只写后缀）；`maxSelectNumber` since 10（单文件选 1）。
- 授权范围与时长沿用既有结论：`DocumentViewPicker.select()` 返回 URI 临时授权（见 [T 组 / Q1](../api_notes.md)），导入侧按图片附件同款「复制已授权 fd 到沙箱」链路，不申请权限（`INTERNET` + `FILE_ACCESS_PERSIST` 之外零新增）。

## 3. 取消与空间不足（前置核实项 3）✅ 形态已定

- **取消**：`decompressFile` 无取消参数；自绘逐条目方案在条目间检查取消标志即可中断（取消粒度 = 条目），无需额外 API。
- **空间不足**：本机 `@ohos.file.fs.d.ts` 写类 API 一律声明 `13900025 - No space left on device`（写失败时的错误形态）。预检：`@ohos.file.statvfs.d.ts` 的 `statfs.getFreeSizeSync(path): number` **since 10**（注意导出命名空间叫 `statfs`，文件名是 `statvfs`），传入 `context.filesDir` 所在沙箱路径查剩余字节。
- 顺序读：`fs.read/readSync` 的 `ReadOptions { offset, length }` since 11（offset 相对当前 filePointer）；自绘解析按「顺序读条目 + 尾部单独读 EOCD/Central Directory」即可，无需随机寻址 API。

## 4. 未核实边界（留待实现期单测 + 设备验收）

- `Zip.inflateInit2` Raw Deflate 在 API 24 运行时的实际行为（`ZStream.availableIn/availableOut` 每轮更新语义、错误码 `17800004/17800005` 的触发形态）——声明齐全但未实测；实现期用 Node 侧等价逻辑对照 + 真机 ZIP 往返验证，不把声明可编译等同于解压已验收。
