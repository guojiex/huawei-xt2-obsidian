# 模拟器 FOLDER 模式能力缺失定性、官方依据与 Phone 支持起点（2026-11-18，API24）

> 背景：继 [2026-11-17 一轮](2026-11-17_FilePicker_选择路径交互_API24.md)确认 XT2 真机 FOLDER 交互与本机 x86_64 模拟器形态差异后，就该轮遗留的三个问题（模拟器有无成功案例、官方出处、绕行方案）继续求证官方。答复为官方 Agent 文档型回答（用户转交，见下方逐条），关键声明已用本机文档库（`devecocli docs`）与仓库既有实测复核。**本轮最重要的产出是复核中挖出的一条官方指南明文：Phone 设备自 API 26.0.0 起才支持 FOLDER selectMode**——答复与指南两端一致，修正了 T1「API 24 可以用」的口径。

## 问了什么（可复现粒度）

环境：同 2026-11-17 一轮——DevEco Studio，compileSdkVersion API 24（`compatibleSdkVersion 6.1.1(24)`）；XT2 真机（LAP-AL10，系统 API 26）；本机 x86_64 模拟器（API 26 镜像）。Stage 模型 ArkTS 应用，经 `picker.DocumentViewPicker.select()` + `DocumentSelectMode.FOLDER` 选沙箱外目录。

已掌握的事实（2026-11-17 轮）：XT2 真机 FOLDER 正常（「选择路径」页，右上角对勾确认）；本机 x86_64 模拟器拉起「我的手机」Sheet 弹窗，`uitest dumpLayout` 全量节点树 313 节点中没有任何可勾选 / 确认控件，选目录流程无法完成。

提问：

1. x86_64 模拟器上有没有「FOLDER 模式成功选中目录」的已知成功案例？还是该环境 FilePicker 未实现目录选中交互（能力限制）？
2. 这一限制有没有官方 issue / 文档出处（《模拟器与真机的差异》等是否记载）？
3. 如不能解决，社区通行的绕行方案是什么？

末尾防编造约束：以官方文档或 SDK 声明为依据回答，查不到的条目直接回答「未记载」，不要猜测接口名或参数名。

## 官方逐条答复

### 1. 模拟器成功案例：无，属模拟器侧能力限制

FOLDER 模式依赖 `SystemCapability.FileManagement.UserFileService.FolderSelection`；x86_64 模拟器上的系统文件选择器是简化实现（「我的手机」Sheet 形态），没有实现 FOLDER 模式所需的「目录选中」交互，钻到哪一层都不会出现勾选框和确认按钮。不是代码问题，没有参数能改变，没有公开的「x86_64 模拟器上 FOLDER 模式成功选中目录」案例。答复同时声称：API 26 之前该能力仅对 2in1 设备开放，API 26.0.0 起 Phone 设备也开放支持并新增 `allowsMulFolderSelection` 多选参数；真机（XT2，API 26）正常正是因为带了这条能力。

### 2. 官方出处：差异文档未记载，最接近依据是通用错误码 804

- 《模拟器与真机的差异》目前没有 FilePicker 条目；Core File Kit「模拟器支持情况」只列备份恢复、分布式文件系统、端云协同三条。
- 最接近的官方依据是通用错误码 804「The capability is not supported on the emulator at this time」，明确把「模拟器暂未实现此 API，将在后续版本实现」列为官方承认的一类情况，处理措施就是「请在真实设备上调测」。本例（FOLDER 模式 UI 缺失）本质上属于这一类：模拟器未实现、文档尚未补记。
- 建议运行时用 `canIUse` 做能力判断（比「真机/模拟器」设备类型判断可靠，官方推荐），参考《选择用户文件》。
- 暂无专门针对「模拟器 FilePicker FOLDER 模式」的公开缺陷单；建议经 DevEco Studio 反馈入口提单，推动文档补记。

### 3. 绕行方案：模拟器 mock Picker 步骤，端到端验证放真机

- 模拟器上把 Picker 这一步 mock 成沙箱路径（如 `context.filesDir` 下的目录），让后续遍历、授权持久化等业务逻辑先在模拟器跑通；「用户实际选中目录」的端到端验证放真机 / 远程真机。
- 附带提醒：FOLDER 模式下 `maxSelectNumber` 不生效（单次只能选 1 个目录），多选要用 API 26 新增的 `allowsMulFolderSelection`；Picker 返回临时授权 URI，跨重启需 `persistPermission` 持久化并声明 `ohos.permission.FILE_ACCESS_PERSIST`。
- 答复附带示例代码：`canIUse` 判 syscap + `deviceInfo.productModel` 含 "emulator" 判模拟器 + 模拟器直接 mock 沙箱目录。

## 既有实测的补充证据（仓库已有，非本轮新增实验）

- **`canIUse` 在 API26 x86_64 模拟器上返回 true（间接实测）**：2026-11-17 模拟器会话中，产品链路 `Index.ets` → `ExternalVaultAuthorizationService.pickDirectory()`（`ExternalVaultAuthorizationDevice.ets` 以 `canIUse(FOLDER_SELECTION_SYSCAP)` 为门禁，不支持会先抛 -2 不拉 Picker）成功拉起了「我的手机」弹窗——门禁放行即 `canIUse` 为 true，但该环境 FilePicker 无目录选中控件。
  → **`canIUse` 通过 ≠ FOLDER 流程能完成**：`canIUse` 能识别设备 / 系统版本能力缺口（如 API 24/25 Phone），**识别不了模拟器 Picker 的实现缺口**。答复「`canIUse` 比设备类型判断更可靠」只对前者成立。
- 2026-11-17 轮 `uitest` 节点树 dump（313 节点无可勾选 / 确认控件）与答复「模拟器未实现目录选中交互」互相印证 ✅。

## 对本工程的影响

1. **能力边界修正（本轮最重要）**：官方指南明文 Phone 设备自 API 26.0.0 才支持 FOLDER selectMode。本工程 `compatibleSdkVersion` 为 API 24——在 API 24/25 的 Phone 设备上 `canIUse(FolderSelection)` 预期为 false（❓ 手上无该档位真机，待实测），v1.5「导入本地目录」在该档位走既有降级（`ExternalVaultAuthorizationError` -2「此设备不支持系统目录选择」）。XT2（系统 API 26）不受影响。产品语义：**v1.5 外部库功能的实际可用下限是「系统 API 26 的 Phone」，不是「API 24 的 Phone」**。canIUse 门禁已在代码中（`ExternalVaultAuthorization` / `ExternalDirProbeDevice`），无需改动。T1「API 24 可以用」同步加更正注。
2. **模拟器定位不变**：x86_64 模拟器继续只作 UI 证据、不作 FOLDER 链路证据；「选目录 → 持久授权 → 读写」端到端只在 XT2 真机验收（与 2026-11-17 轮、v1.5 §6.2.3 一致）。答复的「模拟器 mock Picker 步骤」绕行方案与本仓库现行做法（模拟器不 mock、真机验收）不同——本仓库不采纳，理由：产品代码加模拟器分支 mock 会引入 `productModel` 判断这类无官方依据的分支，且模拟器证据本来就不外推。
3. **可选待办**：经 DevEco Studio 反馈入口提单，推动《模拟器与真机的差异》补记 FilePicker 条目。不阻塞 v1.5。
