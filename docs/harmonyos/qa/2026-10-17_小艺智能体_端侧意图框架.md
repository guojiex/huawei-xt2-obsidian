## 一、答复的方案骨架

```
用户在笔记 App 内点击智能体入口
  → FunctionComponent 拉起「小艺开放平台自建智能体」
  → 用户说「在行程安排后加一段 XX」
  → 大模型解析语义、规划工具调用序列
  → QueryNotes 检索定位 → ReadNote 读取原文 → EditNote 细粒度修改
  → 意图执行器在 App 进程内改写沙箱里的 markdown
  → 自动 git commit 形成版本记录
  → 结果回传智能体，转自然语言反馈用户（听到的是「已修改，提交版本 a1b2c3」）
```

三个构成件：

| 件 | 作用 | 官方说法 |
| --- | --- | --- |
| 自建智能体（小艺开放平台） | 承载对话与语义解析 | **无需人工审核渠道**（技能以 MCP / 插件形式发布到自己的智能体即可）；要进小艺主对话入口才需审核 |
| 端侧意图执行（Insight Intent） | 真正的读写执行器，**跑在 App 进程内** | 沙箱数据不出应用 |
| git 版本底座 | 修改历史 + 撤销 | 官方称为「AI 改笔记最理想的安全网」 |

## 三、⚠️ 与本工程现状的三处冲突（**最需要看的部分**）

### 3.1 致命：示例假设有「原生 git」，而我们的 git 跑在 Web 组件里

示例代码的核心一行是 `GitService.getInstance().commit(notePath, msg)`，
它默认存在**一个原生 ArkTS 的 git 实现**。我们的实际情况完全不同：

- 同步层 F6 是 **isomorphic-git 打包进 `rawfile/gitbridge/index.html`，跑在 ArkWeb 页面里**，
  ArkTS 侧只有 `GitFsBackend` / `GitHttpBackend` 两个桥接，真正的 git 计算在 JS 侧。
- 而答复自己明确指出：后台执行模式下**冷启动生命周期是 `onCreate → onExecute`，不建 window**。
  → **此时 Web 组件根本没挂载，`gitbridge` 页面不存在，commit 无从调用。**
- 即使 App 在前台，常驻 Web 用的是 `visibility(Hidden)`（B-4 结论），
  Hidden 状态下 ArkWeb 是否暂停 JS、能否响应跨边界调用 —— **未验证**。

**结论：不能照抄「意图执行器里同步 await commit」的写法。** 三种可行出路（待拍板）：

| 出路 | 做法 | 代价 |
| --- | --- | --- |
| **A. commit 入队、延迟执行** ⭐ | 意图执行器写完文件后，把「待 commit 的路径 + 消息」写入队列文件；App 回到前台、Web 组件就绪后由主线程消费 | 用户听到的版本号不是即时的，需改成「已修改，版本待提交」 |
| B. 意图执行时同步拉起 Web 再 commit | 冷启动也能挂一个不可见 Web，但冷启动建 WebView 有耗时，且 Hidden 下 JS 是否跑未验证 | 慢 + 不可靠 |
| C. 放弃意图内的 git，只留文件级备份 | 写文件前复制一份 `.bak`（或自建轻量历史目录），撤销走备份而非 git | 失去「git log 摘要 / 历史查询」这类高价值扩展，且备份目录会污染 vault |

### 3.2 严重：示例的写文件方式与我们的原子写硬约束冲突

示例用 `openSync(READ_WRITE | TRUNC)` 清空原内容后覆盖写。
**TRUNC 写到一半崩溃 = 文件半截**，这正是我们早先决定用 `fileIo.AtomicFile`（C1 结论）要解决的问题。

→ **意图执行器里的写回必须换成 `AtomicFile`**（`openWrite` → `writeSync` → `finishWrite` / 失败 `failWrite`）。
决策表已记，编码时不要被示例代码带偏。

### 3.3 中：示例假设「单层扁平目录」，我们是多库 + 多级目录

示例路径 `${context.filesDir}/notes/${noteId}.md` 隐含两件事：单库、单层。我们的实际结构：

- 多库：`vaults/<库id>/…`
- 多级：用户自己的 vault 就是 `00_Inbox/`、`10_Notes/Engineering/流式系统/` 这种两级以上

→ `noteId` 不能是「文件名」，必须能唯一定位到**库 + 库内相对路径**。
两个候选（待拍板）：

1. `noteId` = `<库id>::<库内相对路径>` 的 URL-safe 编码 —— 一个参数搞定，但长、且大模型容易填错
2. 意图参数拆成 `vaultId` + `path` —— 更不容易填错，但要智能体先知道有哪些库（需补 `ListVaults` 意图）

另外答复也问到了我们的目录组织方式，回问时可以直接答复「多库 + 多级」。

## 四、答复里值得直接采纳的设计：锚点定位法

官方强调「修改粒度要很细」的关键不在代码，而在**意图参数设计**，推荐 **anchor（锚点）定位法**：

> 修改指令必须携带一个 `anchor`（笔记原文中的精确片段），执行器用字符串定位后按 `action` 执行重组。

这比「第几行第几列」或「标题路径」可靠——**大模型读完原文后擅长精确复制片段**，
且锚点与原文不一致时可以**拒绝执行并要求重新读取**（这是防错改的关键闸门）。

建议的意图清单（官方给的五个）：

| 意图 | 参数 | 作用 |
| --- | --- | --- |
| `QueryNotes` | keyword | 检索笔记，返回 ID 与摘要 |
| `ReadNote` | noteId | 读全文，供智能体取锚点 |
| `EditNote` | noteId、anchor、action、newContent | 细粒度修改：`replace` / `insertBefore` / `insertAfter` / `delete` |
| `AppendNote` | noteId、content | 末尾追加（**高频简单操作单独开意图，降低出错率**） |
| `UndoLastEdit` | noteId | git 回滚，配合版本底座 |

**我们要补的一条工程细节**（答复没提，但必须做）：
anchor 在文中出现**多次**时应拒绝执行，否则会改错位置。
执行器应校验 `indexOf` 的出现次数，>1 就返回错误并要求智能体给出更长的锚点。

## 五、官方推荐的智能体系统提示词约束（建议照抄进配置）

> 修改任何笔记前必须先调用 `ReadNote` 获取原文；
> `anchor` 必须取自原文，禁止凭记忆编造；
> 执行修改后向用户复述变更内容。
