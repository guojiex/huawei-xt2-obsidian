## B-1 `onInterceptRequest` 能否拿到 POST body（含二进制）

**结论：能拿到，但 `getRequestBody()` 返回 `string`，二进制 body 存在编码损坏风险。**

- `WebResourceRequest` 提供：`getMethod()` / `getUrl()` / `getHeader()` / **`getRequestBody(): string`** —— 接口与返回类型 ✅ 文档明确记载
- ⚠️ 因为是 `string` 而非 `ArrayBuffer` / `Uint8Array`：文本类 body（JSON / form-urlencoded）没问题；**二进制 body（git-receive-pack 的 zlib packfile）经 string 序列化可能损坏**
- ❓ 官方**既没说"支持二进制"，也没说"仅支持文本"** —— 灰色地带

**响应侧**（回填给 JS）是流式 API ✅：`new WebResourceResponse()` → `setResponseMimeType` / `setResponseHeader` / `setResponseStatusAndReasonCode(200,'OK')` / `setResponseData(data)`。

三方案对比（对方给出）：

| 方案 | 请求 body | 响应 body | 适用性 |
| --- | --- | --- | --- |
| `onInterceptRequest` 拦截 | string（**二进制风险**） | 可流式回填 | clone/fetch 可行，**push 存疑** |
| JS 自定义 http client → `@ohos.net.http` | ArrayBuffer ✅ | ArrayBuffer ✅ | push / clone **均可行** |
| 混合（GET/小 POST 拦截，大 POST 走 MessagePort） | ArrayBuffer | 拦截回填 | 可行但复杂 |

**对方建议**：git 场景**继续用自定义 http client 转发到 `@ohos.net.http`**；`http.HttpRequestOptions` 的 `data` 字段支持 `ArrayBuffer` / `Uint8Array`，能正确处理二进制 packfile。

→ **我们的决策：拦截方案 ❌ 正式否决（对 push 不适用），保留现有转发方案。**

## B-2 `WebMessagePort` 在 `resource://rawfile/` 页面的可用性

**结论：可用；`ArrayBuffer` 支持，但大小上限未记载。**

- ✅ `WebMessage` 定义：`interface WebMessage { data: string | ArrayBuffer }` —— 文档明确支持 ArrayBuffer
- ✅ `controller.createWebMessagePort()` 返回一对 port：一端注入 HTML（`postMessage`），一端原生持有（`onMessageEvent`）
- ⚠️ rawfile 页面可用：`resource://rawfile/` 是 ArkWeb 内部协议，`createWebMessagePort` 是**组件级** API，不依赖页面协议的跨域策略
- ❓ **单条消息的 ArrayBuffer 大小上限未记载**；推断受 Chromium IPC 单条消息上限（数十 MB 级）与设备内存约束
- 建议：**分块传输**（示例用 4MB/块，末尾发 `__TRANSFER_COMPLETE__` 标记）

## B-3 `runJavaScript()` 传参 / 返回值长度上限

**结论：官方未记载具体数值。**

- ✅ 签名：`runJavaScript(script: string, callback: (result: string) => void): void`
- ❓ `script` 参数长度上限、`callback` 的 `result` 长度上限**均未记载**
- ⚠️ 推断：返回值是字符串化结果，二进制需先 base64（**膨胀 33%**）；packfile 级别数据不适合走它
- → **大数据走 `WebMessagePort.postMessage(ArrayBuffer)`**

## B-4 `NodeContainer` 卸载后 JS 状态是否保留

**结论：不保留；重新挂载会重新加载页面。** ⚠️（推断，基于组件生命周期）

`NodeContainer` 从组件树移除 → Web 组件销毁、Chromium 实例释放 → 变量/闭包/Worker 全丢；重新挂载时 `makeNode()` 重新创建实例，页面从 `resource://rawfile/` **重新加载**。文档未记载"节点缓存"或"后台保活"。

**常驻容器的正确做法**（对方给出）：不要动态卸载，改用 **Stack + `visibility(Hidden)` 保持 Web 常驻**：

```typescript
Stack() {
  Web({ src: $rawfile('git-worker.html'), controller: this.controller })
    .width('100%').height('100%')
    .visibility(this.webVisible ? Visibility.Visible : Visibility.Hidden)
  NoteEditor()
}
```

⚠️ Hidden 时 JS 环境保留，但**不排除 ArkWeb 会做内存优化（暂停 JS 或降优先级）** —— 待真机验证。

## B-5 中文输入法（contenteditable / textarea）

**结论：官方无明确记载，仍需真机实测。** ❓

- 相关配置项：`keyboardAvoidMode`（页面级）、`blurOnKeyboardHideMode`、`onInterceptKeyboardAttach`（组件级）—— ⚠️ 主要影响**容器布局**而非 Web 内部输入逻辑
- 页面级键盘避让：`win.setWindowAvoidAreaTypes([AvoidAreaType.TYPE_KEYBOARD], cb)`
- 实测重点：**拼音 / 语音 / 手写**三种输入下的 **composition（预编辑）事件**与**光标位置**
- ⚠️ **对方建议优先用 `<textarea>` 而非 `contenteditable`**（前者输入法兼容性通常更好）→ **与我们选型冲突，见「影响」**

## B-6 Web Worker 在 ArkWeb 中的可用性

**结论：可用；Worker 内 MessagePort 可用；`javaScriptProxy` 不可用。** ⚠️（推断，基于 Chromium M114）

- Worker / MessageChannel / fetch / IndexedDB 等标准能力应可用（`SharedWorker` 不确定）
- **`javaScriptProxy` 注入的是 `window` 对象，Worker 内没有 window → 不可访问**（与上一轮答复一致）
- **但可以绕过**：把原生侧的 `WebMessagePort` 通过 `worker.postMessage({type:'init', port}, [port])` **transfer 进 Worker**，Worker 内直接用 port 收发 ArrayBuffer 与原生通信
- 退路：Worker 内 `postMessage` 回主线程，由主线程中转调用原生
