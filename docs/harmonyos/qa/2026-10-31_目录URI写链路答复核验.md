## 设备实测读数（XT2 / API 26，同一 URI 连续两轮）

```
step atomic            ok=false  失败（code=-1）            ← 对照组：AtomicFile 确实不可用
step native_read       ok=true   目录里没有 Markdown，跳过
step native_write      ok=true   新建并回读一致（76 字节）
step native_overwrite  ok=true   变短覆盖无残留（76 → 7 字节）
step native_rename     ok=true   renameat 成功，按新名可读
step native_delete     ok=true   unlinkat 成功，探针文件已清理
```

**重激活后（杀进程重启 → activatePermission → 重跑）结果完全相同**，五步全绿。

### 两个额外的硬证据

1. **探针自清理成功**：第一轮跑完后，第二轮 `native_recursive` **仍是 31 条**（没有变成 32）。
   如果rename/delete 没真正生效，计数器一定会涨。
2. **改写无残留尾部**：`native_overwrite` 特意把内容从 76 字节改成 7 字节并做**严格相等**回读。
   非原子的原地 `write` 在这种场景下会留下旧尾部，`renameat` 不会 —— 这正是坚持 Q3(a) 的理由。

## 落地形态

```
ArkTS：Picker 选目录 → fileShare.persistPermission → 每次启动 activatePermission
       → fs.openSync(目录URI, READ_ONLY | OpenMode.DIR) 拿 dirFd
Native：fdopendir/readdir 枚举 · openat 读写 · renameat 原子替换 · unlinkat 删除
```

- `native/vaultdir_napi/src/vaultdir_napi.c`：`readFileByFd` / `writeFileByFd` /
  `deleteByFd` / `renameByFd`（与已有 `listDirByFd` / `listDirRecursiveByFd` 同模块）
- `model/VaultDirNative.ets`：`VaultDirFileStore`（DI 封装）+ `VaultDirSession`（fd 借用）
- `model/ExternalDirProbeDevice.ets`：`createVaultDirFileStore()`
- 单测：`tools/tests/test_vault_dir_native.mjs`（14 例，含 fd 生命周期、开 fd 失败短路、原生写失败带 errno）

### 实现里按答复补的两个细节

- **tmp 文件名带 pid**（`name.<pid>.tmp`）：同一目录并发写时不互相踩。
- **`fsync(dirFd)` 的 EINVAL 降级**：某些 DFS/FUSE 挂载点不支持对目录 fd 做 fsync；
  此时数据在 rename 前已 fsync 过，内容不丢，所以只当作软警告，不把整个写判死。

## 对 v1.5 的意义

**「编辑笔记并保存回原文件」这条需求的技术阻塞解除。**
原先因为 `AtomicFile` 报 code=-1 而悬空的写链路，现在有了已实测的形态，
且天然满足「写一半崩溃不留半截笔记」—— 这是 AtomicFile 本来要解决的问题，
Native `renameat` 用 POSIX 语义直接给了。

按答复建议，**不要等 ArkTS 侧补齐**（明确无公开版本计划）。
