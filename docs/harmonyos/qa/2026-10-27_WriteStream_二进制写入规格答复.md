## 需求反馈草稿（未提交）

【需求描述】
希望 HarmonyOS 为 AtomicFile 提供受支持的二进制原子写入能力，例如让 startWrite() 返回的 WriteStream 支持直接写入 Uint8Array，保持原始字节不变，支持分块写入，并保留 finishWrite() 成功提交、failWrite() 失败回滚的完整性语义。请同步明确 WriteStream 与父类 Writable.write 的类型支持差异、适用 API 版本、错误码及二进制示例。项目最低兼容 API 24，希望优先覆盖；如无法覆盖，请明确最低支持版本和现有版本的官方替代方案。

【原始场景】
应用为“曜石笔记”，面向华为三折叠设备的本地 Markdown 笔记应用，使用 ArkTS + Stage 模型，笔记库包含 Markdown、图片及 Git 数据。
1. Git 同步：用户输入仓库信息并执行 clone，网络数据接收后，经应用文件系统桥接以 Uint8Array 写入本地。即使内容是文本（如 .git/config），桥接也以字节表示；图片、Git 对象等则必须保持任意二进制字节原样。现有 AtomicFile 写入路径在 WriteStream.write 阶段失败，clone 无法完成。
2. 图片导入：用户在编辑器选择插入图片，经系统 Photo Picker 选择图片，应用打开已授权源 URI、读取字节，再写入笔记库附件目录，成功后插入 Markdown 引用。已观察到 AtomicFile 返回流写入 Uint8Array 时失败，因此未插入引用。
现有复现来自 API 26 arm64 模拟器，错误为 13900020: Invalid argument；API 24 和 XT2 真机尚未验证。问题发生在 write 阶段，不是已证实的 startWrite 失败。

【影响】
当前开发和功能验收阶段已经用到。Git 同步是核心功能，一次 clone 可能触发多文件写入；图片导入也是日常笔记操作，但目前没有线上频次统计。更新已有文件时需要失败保留旧内容，不能以直接截断覆盖替代原子写入。
目前未验证到能在 API 24 ArkTS 环境直接替代此能力、且提供同等完整性保证的三方库。Git 库本身不能补足底层存储能力。新建唯一命名图片可另行评估从已授权源 fd 复制文件，但该方案仍需核实 API 和授权用法，也不能替代已有二进制文件更新的原子写入需求。将二进制转成普通文本或 Base64 落盘会改变文件格式，不满足 Git 和图片文件的字节一致性要求。
若在现有 AtomicFile/WriteStream 上补充支持，预计主要调整共享文件写入层并补充验证，业务交互无需大幅返工；具体工作量取决于最终接口及支持版本。
