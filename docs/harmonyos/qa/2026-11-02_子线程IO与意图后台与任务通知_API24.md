### 答复给的落地建议（原文要点）

AI 编辑 / 多轮工具调用**不要申请长时任务**（无对应类型、易被判超范围）；改为「前台执行 + 意图回调内快速返回 + `sendIntentResult` 延迟回传」；后台保存场景用短时任务兜底（须在退后台 5 秒内申请）；所有 Agent 侧未记载语义（去重、调用 ID、轮数上限）在首发前用调测证书真机压一轮多轮工具循环，把实测值记进 `api_notes.md`。

## 3. 与官方答复的分歧与新增结论

1. **`openNotificationSettingsWithResult` 在 API 24 不可用（since 26.0.0）**，答复把它当作「用户拒绝授权后」的推荐路径 → 该建议在本工程失效。API 24 上的替代是 `openNotificationSettings(context)`（since 13，无返回值），拒绝后引导只能走它 + 自行判断授权状态（`isNotificationEnabled`）。
2. **A2A 程序化通道在 API 24 不成立**：`createA2AServer` since 26.0.0。`AgentExtensionAbility`（AgentRuntime，since 24）虽有声明，但没有 helper 支持就不能当作可直接落码的通道；这与既有 F11 / F13 的「API 24 未找到完整 App 主动调用协议」一致，且把「存疑」升级为「本机版本表已证 helper 越界」。
3. **短时任务的具体数值首次拿到明文**（5 秒申请窗、同时 ≤3 个、无续期、每日配额需运行时读 `getTransientTaskInfo`）→ 原 N1 的 ⚠️ 可以收紧为「文档明确，但设备表现仍待实测」。
4. **「AI 编辑 / 多轮工具调用」无对应长时任务类型，归入任何一类都属超范围使用** —— 这是本轮对本项目最有约束力的结论，直接支持既有决定「默认前台，不开假后台模式」。
5. 答复的推断项（AtomicFile 子线程可用、1-4 并发不保证、4-3(a)(b)(d)、2-2(b)、5-2）在 SDK 侧无法证伪 → 保持 ⚠️/❓，不进关键路径。
