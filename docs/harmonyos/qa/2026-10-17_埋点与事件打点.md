## 提问

> 鸿蒙 SDK 是否原生支持 app 里面不同位点（埋点）的展示上报？

---

## 官方答复要点（按我们关心的顺序整理）

### 1. 结论：支持，且三类埋点都有原生 API，无需第三方 SDK ✅

官方给出的能力分层：

```
采集层（曝光 / 点击 / 页面事件监听）
   ↓
存储层（hiAppEvent.write 落盘）
   ↓
订阅层（addWatcher 订阅 + triggerCondition 触发）
   ↓
上报层（自建 http 上报到自有服务器）
```

| 埋点类型 | 原生 API | 起始版本 | 我们 API 24 可用？ |
| --- | --- | --- | --- |
| 曝光（展示） | 组件事件 `onVisibleAreaApproximateChange` | **17+** | ✅ |
| 曝光（全局无侵入） | `FrameNode.setOnVisibleAreaApproximateChange` | **12+** | ✅ |
| 点击 | `UIObserver.on('willClick')`（点击**触发前**回调，可拿 `ClickEvent` 与 `FrameNode`） | **12+** | ✅ |
| 页面 | `UIObserver.on('navDestinationSwitch')` | **12+** | ✅ |

→ **全部 ≤ 24，版本上无障碍。** 这是本批答复里最该先确认的一条，结论是乐观的。

### 2. 曝光埋点三要素

- `ratios: [0.5]` 与 `expectedUpdateInterval: 500`：**官方说明「ratios 设 [0.5] 时实际生效阈值为 [0.0, 0.5]」**，回调在比值**跨越阈值**时触发，不是每帧触发。
- `onVisibleAreaApproximateChange` 相比 `onVisibleAreaChange` **降低计算频度**（由 `expectedUpdateInterval` 控制），**列表大量注册时功耗更优** → 我们文件树场景应当用它。
- **去重必须自己做**：官方示例用 `Set<string>` 按 `scene_itemId` 去重。⚠️ 这个 `Set` 是**内存态**，进程重启即失效 → 落码时要考虑持久化（见下方「我们的补充」）。

### 3. 批量取出：`addWatcher` + `takeNext`

- `triggerCondition: { row, size }` 满足**任一**条件即触发 `onTrigger`（官方示例 row=10 / size=1000 字节）
- `onTrigger` 里用 `holder.takeNext()` **逐包取出**，直到返回 null
- 官方提示：**`addWatcher` 涉及 I/O，性能敏感场景放子线程**，且要保证该线程在整个使用周期内不被销毁
- watcher **同名会覆盖前一次订阅**

### 4. 全局无侵入方案（对我们最有价值）✅

> 业务组件只声明 `.id()` 与 `.customProperty()` 标识身份，Ability 层统一通过 `UIObserver` + `FrameNode.setOnVisibleAreaApproximateChange` 完成监听，**业务代码零侵入**。

点击同理：`observer.on('willClick', callback)` **全局注册一次**即可捕获所有组件点击，回调里通过 `FrameNode` 读组件标识。

→ 这正好匹配我们的文件树：不用给每个节点挂监听器，Ability 层注册一次即可。

### 5. 明确的能力限制 ⚠️

- **可见区域计算不支持**：兄弟组件遮挡、窗口遮挡、组件旋转场景。只计算**自身节点相对祖先节点直至窗口边界的裁切面积比值**。
- 对三折叠的影响：形态切换时窗口尺寸会变（我们已用 `windowSizeChange` 处理布局），但**曝光比值在切换瞬间的准确性不受保证** → 相关埋点只当趋势看，不当精确数据看。

### 6. 另一条路径：华为分析（Analytics Kit）

上架华为应用市场后可用，AGC 控制台直接看数据，**免开发上报与分析后台**。与原生方案的差别：

| | hiAppEvent + UIObserver | Analytics Kit |
| --- | --- | --- |
| 数据归属 | **归你自己**，上报目标自主可控 | 华为侧 |
| 后台成本 | 需自建上报与分析 | 免费现成看板 |

官方说两者**可以并用**：本地 hiAppEvent 落盘保数据不丢，云端分析做日常运营看板。

## 我们的补充与警示（官方没说，但落码前必须定）

### ⚠️ 1. 笔记内容**一律不得进入埋点**

这是笔记 App 的硬性红线。可采集的只有**行为坐标**（打开了第几层目录、用了哪种形态、点了哪个按钮），**禁止采集**：笔记标题、文件名、路径、正文、字数、标签。

理由有二：① 隐私（这是个人知识库，不是内容社区）；② 合规（上架需隐私声明，采集用户内容会显著抬高合规成本与审核风险）。

→ **埋点字段设计必须先过这条红线**，别等上报出去了再删。

### ⚠️ 2. 曝光去重 Set 是内存态，进程重启即失效

官方示例的 `exposedSet` 只活在内存里。笔记 App 的使用模式是**每天打开几次、每次看同样的文件树**，进程重启后同一批笔记会被**重复计一次曝光** → 跨会话数据失真。

→ 落码时要么接受「单次会话内去重」（把指标定义成"会话内曝光"），要么把已曝光 key 持久化。前者更简单，推荐先按前者定义指标。

### ⚠️ 3. 埋点上报本身就是一次网络请求，别和同步抢

我们的 git 同步走 Web → 原生 http 桥接。埋点上报若也走 http，在弱网下会**与同步争带宽**。

→ 上报策略应设为**非实时批量**（`triggerCondition` 本来就是累积触发）、且**失败即丢弃**（不做重试队列，别为了埋点拖累主链路）。

## 对本项目最有价值的埋点场景（暂不实现，先记录）

1. **三形态使用分布** —— sm / md / lg 各自被用到的时长占比。这是本项目**最独有**的数据：三折叠三屏态到底有没有人真的展开用，直接决定后续版本该往哪投入。（对应 v0.1 的三形态适配，v0.1 发布后即可看出结论）
2. **目录栏收起率** —— 双屏/三屏下用户有多常收起目录栏，验证「一栏一屏」这套布局假设是否成立。
3. **左滑操作条各按钮使用率** —— 重命名 / 移动 / 删除 各被点多少次，判断滑到底直删的手势是否真的有人用（或是误触）。
4. **同步成功率与耗时** —— clone/push 的成功率、失败原因分布（401/404/网络），这是 v0.3 之后最需要的运营数据。

> 以上四项**全部不触碰笔记内容**，符合 §⚠️1 红线。
