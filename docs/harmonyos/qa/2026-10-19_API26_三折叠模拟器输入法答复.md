### 1. 如何确认并配置模拟器的系统输入法？

**结论**:
在你描述的 `Huawei_TripleFold` 模拟器中，系统默认输入法即为 `com.huawei.hmos.inputmethod`（华为系统输入法），通常无需额外配置。中文拼音输入法作为其子模块已内置，点击输入框后即可通过键盘上的语言切换键激活。**没有 `ime` 或 `settings` 命令可以更改此环境下的默认输入法，因为系统输入法是唯一的且不可卸载的**。

**可复现步骤**:
1.  **核实默认输入法**:
    -   打开 DevEco Studio 的 `Terminal` 或使用 `adb shell` 连接到模拟器。
    -   运行 `bm dump -n com.huawei.hmos.inputmethod`。你会看到 `com.huawei.hmos.inputmethod` 的包信息。输出中会包含其版本号 (1.2.6.463) 和组件列表。你可以搜索 `InputMethodService` 组件，它通常为 `.HMSoftKeyboard` 或类似名称，但这已足够确认它是 IME 服务。
    -   运行 `bm dump -n com.huawei.hmos.inputmethod | grep "imeId"`（如果支持）或查看输出中的 `imeId` 字段。这通常会显示 `com.huawei.hmos.inputmethod/.HMSoftKeyboard`。
2.  **启用中文拼音输入**:
    -   在你的应用中任意点击一个 `textarea` 或 `TextInput` 组件。
    -   当系统键盘弹出时，点击键盘上的语言切换键（通常是 `123!@#` 键旁的 `🌐` 图标或长按 `123!@#` 键），在弹出的语言列表中选择“中文 (简体) - 拼音”。
    -   此时键盘布局会变为拼音/五笔布局，即可进行中文拼音输入。

**准确命令与版本**:
-   `bm dump -n com.huawei.hmos.inputmethod` (此命令在整个 API 26 模拟器中都有效)。
-   `bm dump -n com.huawei.hmos.inputmethod | grep "Version"` 可以快速获取版本。

**官方文档链接**:
-   系统输入法框架是系统级能力，没有提供通用的设置命令文档。`bm` (Bundle Manager) 命令在官方文档的“调试与测试 > 调试工具”部分有介绍。
-   用户切换输入法语言是键盘应用自身的管理能力，非系统全局 API。

**证据强度**:
-   **确认**: 来自你提供的 `bm dump` 输出和模拟器中的实际操作。
-   **可靠**。

### 2. 为什么 CodeMirror `contenteditable` 初次点击没有唤起软键盘，而在 HTML `textarea` 先唤起系统键盘后，切回 CodeMirror 又能正常输入？

**结论**:
这是一个 **ArkWeb `contenteditable` 与 IME (输入法框架) 初始化/焦点管理** 的已知行为差异，属于框架层面的优化或 Bug，**不是** bug。核心原因如下：
1.  **焦点与 Composition 会话**: `textarea` 是系统原生控件，有标准的 IME 会话交互流程。点击它立即触发 `focus` 事件并请求 IME attach。而 `contenteditable` 是一个复杂 DOM 环境，IME 会等待用户明确与可编辑区域交互（如点击、触摸）后再决定是否 attach。
2.  **首次 IME 初始化的惰性行为**: 在 API 26 的模拟器上，系统 IME 可能采用了一种“懒加载”初始化策略。仅在明确需要处理中文输入等复杂 Composition 时，才会完全初始化其 `Composition` 会话。`textarea` 的点击强制触发了这个完整初始化过程。
3.  **ArkWeb 对 `contenteditable` 的 IME 附着的优化**: 为了实现更好的性能或避免意外键盘弹出，ArkWeb (及许多现代浏览器引擎) 会对 `contenteditable` 的 IME 附着进行限制。初始点击可能被识别为“尝试”性的，只有当用户有明确的、非短暂的交互时（例如，在另一个编辑器激活 IME 后），才正式附着 IME。`textarea` 率先唤起键盘，实质上是 **预热** 了整个 IME 进程，使其进入了“就绪”状态。
4.  **时序问题**: 首次点击 CodeMirror 时，JS 代码可能需要处理焦点 ( `focus` )，但 IME 还未准备好或未建立与 `contenteditable` 的会话。待 `textarea` 初始化后，当焦点移回 CodeMirror 时，IME 进程发现一个非原生但可编辑的 DOM 元素获得了焦点，便能正确建立会话。

**这不是一个需要去“修复”的问题，而是一个需要去“适配”的行为差异**。只要你的应用逻辑能正确处理 `focus` 和用户交互，它通常不会成为功能障碍。你观察到的“先唤起 `textarea` 后可用”现象，恰恰证明了模拟器 IME 基础功能是正常的。

**可复现步骤**:
1.  启动只有 CodeMirror `contenteditable` 的页面。
2.  点击 CodeMirror 编辑区，确认键盘未弹出。
3.  在 `DevEco Studio -> Logcat` 中观察 `ArkWeb` (或 `InputMethod`, `IMM`) 标签的日志。可能不会输出`attach`相关的日志，表明 IME 未接合。
4.  在页面上创建或添加一个 `<textarea>` 元素。
5.  点击 `<textarea>`，确保键盘弹出并可用。
6.  不关闭键盘，点击 CodeMirror 编辑区，确认键盘未消失并可在 CodeMirror 输入。

**准确 API / 命令与版本**:
-   目前没有 ArkWeb 提供的 API 来“强制” `contenteditable` 在焦点时唤起键盘。这是底层的交互行为。
-   **官方支持的检查步骤**: 你需要通过 `webview.onShowInput` 事件来监听键盘附着的请求。

**官方文档链接**:
-   [onShowInput](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V5/ts-basic-components-web-V5#onshowinput9): 此回调在 ArkWeb 请求系统键盘弹出时触发。对于 `contenteditable`，首次点击可能不触发，而在后续交互中触发。

**证据强度**:
-   **推断 + 模拟器实测**: 基于你描述的现象以及 HarmonyOS ArkWeb 框架对 IME 处理的通用行为推断。你提到的“先点击 B 档”的现象直接证实了这个推断。

### 3. ArkWeb 的 `WebOptions`、键盘避让或键盘控制能力中，哪些设置可能影响 `contenteditable` 的键盘唤起？

**结论**:
你的 `compatibleSdkVersion: 6.1.1(24)` 是一个兼容性声明，意味着你的应用可以在 API 12+ 的设备上运行。`targetSdkVersion: 26.0.0` 是你的应用为 API 26 优化的声明。在 **API 26 模拟器** 上运行时，应用的兼容性版本不限制你使用 API 26 的 API，但你需要考虑这些 API 在 API 24 设备上的可用性（你的业务需求）。

以下是你关心的三项设置的准确情况：

| API 名称 | 导入路径 / 所属类 | 方法/属性签名 (简略) | 最低API版本 (声明) | 对你的问题影响 | 是否适用于 API 24 兼容应用？ |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`keyboardAvoidMode`** | `@ohos/web.webview.WebviewController` | `controller.keyboardAvoidMode: KeyboardAvoidMode` | API 12 | 不直接影响。此设置决定键盘弹出时 Web 页面如何避让（上推/缩放），不影响键盘是否弹出。 | **不适用**。API 12+ 才可用。在 API 24 设备上设置会编译失败或运行时无效。 |
| **`onInterceptKeyboardAttach`** | `@ohos/web.webview.WebviewController` | `controller.onInterceptKeyboardAttach(callback: (event: KeyboardAttachEvent) => boolean)` | API 12 | **可能影响**。此回调允许你 **拦截** 键盘附着请求。如果默认返回 `false`，可能会阻止键盘弹出。你需要检查 CodeMirror 是否调用了此 API 并返回了 `true` 来阻止键盘。 | **不适用**。API 12+ 才可用。在 API 24 设备上设置会编译失败或运行时无效。 |
| **`WebKeyboardController`** | `@ohos.web.webview` | `WebKeyboardController.attach()` / `.detach()` | API 12 | **直接影响**。`attach()` 可强制唤起键盘，`detach()` 可强制关闭。这是解决 `contenteditable` 键盘唤起问题的官方、推荐手段。但它是一个主动触发 API，需要你在代码中显式调用。 | **不适用**。API 12+ 才可用。在 API 24 设备上设置会编译失败或运行时无效。 |

**重要澄清**:
-   **`onInterceptKeyboardAttach` 和 `WebKeyboardController` 是 API 12 引入的**。如果你的 `compatibleSdkVersion: 6.1.1(24)` 是一个真实的目标（你希望在 API 24 设备上运行），**你不能使用这些 API**，因为它们不存在。
-   **在 API 26 模拟器上**，你可以自由使用这些 API，因为它们由系统提供并能正常运行。
-   如果 `onInterceptKeyboardAttach` 默认行为导致了你观察到的现象，你可以通过在该回调中返回 `false` (表示不拦截) 来允许键盘弹出。但更常见的问题是 `contenteditable` 自己未能正确触发 `attach`，此时需要使用 `WebKeyboardController.attach()`。

**可复现的检查步骤**:
1.  在 CodeMirror 组件的 `Controller` 上实现 `onInterceptKeyboardAttach` 回调，并添加日志。
    ```typescript
    // 在 WebviewController 实例上
    controller.onInterceptKeyboardAttach((event) => {
        console.info('onInterceptKeyboardAttach called, source: ' + JSON.stringify(event));
        // 返回 false 表示不拦截，允许键盘弹出
        return false;
    });
    ```
2.  点击 CodeMirror 的 `contenteditable` 区域。
3.  检查 `Logcat` 中的日志。如果**没有** `onInterceptKeyboardAttach called` 的日志，说明 ArkWeb 压根没有尝试为 `contenteditable` 发起键盘附着请求。这是行为差异的根本。如果有日志且返回 `false` 后键盘仍不弹出，说明拦截不是原因。

**官方文档链接**:
-   [keyboardAvoidMode](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V5/ts-basic-components-web-V5#keyboardavoidmode)
-   [onInterceptKeyboardAttach](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V5/ts-basic-components-web-V5#oninterceptkeyboardattach12)
-   [WebKeyboardController](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V5/js-apis-webview-V5#webkeyboardcontroller)

**证据强度**:
-   **官方文档**: 上述信息均来自 HarmonyOS 官方 API 参考文档的最低版本声明。
-   **可靠**。

### 4. 如何在 DevEco 模拟器里可靠地重复这次真实拼音验证？

**结论**:
在 API 26 模拟器上，你可以通过 **点击屏幕软键盘上的拼音按键** 来可靠验证中文拼音的 `compositionstart`, `compositionupdate`, `compositionend` 事件及候选词选择。`uitest uiInput inputText` 和外接键盘输入均无法做到这一点，它们只能生成原生的 `input` 事件（已提交的文本）。

**可复现的验证步骤与判别方法**:

**步骤 1: 准备日志证据** (关键)
在你的 CodeMirror 包装层或页面 JavaScript 中添加以下事件监听，并输出到 `console` (ArkWeb 可以通过 `runJavaScript` 或直接修改页面代码实现)。

```javascript
// 在 CodeMirror 实例所在的 document 上监听
if (editorWrapper) { // editorWrapper 是 contenteditable 元素的父级
  const editable = editorWrapper.querySelector('.cm-content'); // CodeMirror 6 默认类名
  if (editable) {
    editable.addEventListener('compositionstart', (e) => {
      console.log('EVENT: compositionstart', new Date().toISOString());
      // 注意：此事件中 e.data 可能为 undefined
    });
    editable.addEventListener('compositionupdate', (e) => {
      console.log('EVENT: compositionupdate, data: ', e.data);
    });
    editable.addEventListener('compositionend', (e) => {
      console.log('EVENT: compositionend, data: ', e.data, ', inputType: ', e.inputType);
    });
    editable.addEventListener('input', (e) => {
      console.log('EVENT: input, data: ', e.data, ', inputType: ', e.inputType, ', isComposing: ', e.isComposing);
    });
  }
}
```

**步骤 2: 执行操作并观察日志**

| 操作 | 产生的 Input 类型 | 能否验证中文拼音 Composition？ | 日志证据 (来自步骤 1) |
| :--- | :--- | :--- | :--- |
| **点击屏幕软键盘拼音按键 (如 `n-i-h-a-o`)** | `compositionstart`, `compositionupdate`, `compositionend`, `InputEvent(inputType='insertCompositionText' & 'insertText')` | **是** | 你会看到 `compositionstart`, 多次 `compositionupdate (data='n' / 'ni' / 'nih' / etc.)`, 然后 `compositionend (data='你好')`, 最后是 `InputEvent(data='你好', inputType='insertText', isComposing=false)`。**这是唯一能验证 IME 完整流程的输入方式**。 |
| **`uitest uiInput inputText` 命令** (例如 `uitest uiInput inputText "你好"`) | `InputEvent(inputType='insertText')` | **否** | 你会看到只有一个 `InputEvent`, `isComposing: false`。**没有 `compositionstart` 和 `compositionend` 事件**。这仅是系统级别的文本注入，模拟了用户粘贴或自动填充。 |
| **外接键盘输入** (例如连接蓝牙键盘或 Mac 键盘) | 取决于 IME 和文本服务 | **不确定** | 在 API 26 模拟器中，连接外接键盘通常被视为物理键盘。大部分 IME (包括华为输入法) 的默认行为是直接提交英文按键，**不会激活中文拼音或手写输入**。你会看到一串 `InputEvent(data='n', inputType='insertText', isComposing=false)`。除非你在系统设置中明确配置了物理键盘的语言为中文拼音，否则无法触发 Composition。 |

**关键判别点**:
-   **键盘未 attach 的迹象**: 点击 `contenteditable` 后，没有任何 `compositionstart` 或 `InputEvent` 日志输出，且键盘未弹出。`onShowInput` 回调如未添加日志，则无法从 JS 侧直接判断，但 `onShowInput` 无回调是判断键盘未附着的最有力证据。
-   **Composition 未送达的迹象**: 键盘已弹出且你按了拼音按键，但 JS 侧未收到 `compositionstart` 和 `compositionupdate` 事件。这通常意味着 IME 已附着，但 Composition 事件在底层被干扰或未正确传递。这种情况在 CodeMirror `contenteditable` 中较少见，但在你“先唤起 `textarea`”的场景下，基本可以排除。
-   **普通文本已提交**: 你只看到 `InputEvent` 且 `inputType='insertText'`, `isComposing=false`。这就是 `uitest` 或外接键盘（默认模式）的典型行为。

**证据强度**:
-   **可靠**: 日志是直接证据。你之前“按键后能看到拼音组合串与中文候选词”的观察，结合上述 JS 事件监听，可以完全证实。

### SDK 声明核实

本机 DevEco Studio 26.0.0.851 的 API 26 SDK：`/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/ets/component/web.d.ts`。

- `WebAttribute.keyboardAvoidMode(mode: WebKeyboardAvoidMode)` 与 `WebAttribute.onInterceptKeyboardAttach(callback: WebKeyboardCallback)` 标记 `@since 12`。API 24 高于 API 12，因此“API 12+ 所以 API 24 不适用”不成立。当前核实基于 API 26 SDK 声明，未单独在 API 24 运行时验证。
- `onInterceptKeyboardAttach` 回调类型为 `(keyboardCallbackInfo: WebKeyboardCallbackInfo) => WebKeyboardOptions`，不是 boolean；不能按答复示例返回 `false`。SDK 文档说明回调用于选择系统默认键盘或配置自定义键盘。
- `WebKeyboardController` 用于自定义键盘，SDK 声明包含 `insertText`、`deleteForward`、`deleteBackward`、`sendFunctionKey`、`close`，没有 `attach()` / `detach()`。答复把它描述成强制唤起系统键盘的接口，未获 SDK 支持。
- `keyboardAvoidMode` 是 `WebAttribute` 方法，不是 `WebviewController` 属性；其作用为 ArkWeb 软键盘避让。另有 `UIContext.setKeyboardAvoidMode`，二者不能混写。
- 在已安装的 API 26 SDK 声明中未找到 `onShowInput`；答复引用的回调不作为已核实 API 使用。
