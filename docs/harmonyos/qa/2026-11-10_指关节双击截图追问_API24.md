## 答复原文（AI 生成，仅供参考）

以下结论均以当前公开的 SDK 声明（d.ts）与官方文档为依据，查不到的一律标注「未记载」。

### 1. API 24 上三方应用能否识别指关节输入来源

**不能，且未记载任何扩展能力。** 逐项核对公开输入接口：

- 触屏事件来源枚举 `SourceType`（`@ohos.multimodalInput.touchEvent`，`@kit.InputKit`）仅包含三类：`TOUCH_SCREEN`（触摸屏）、`PEN`（手写笔）、`TOUCH_PAD`（触控板），指关节不会作为独立来源上报<rsub ref="G.1.1">1</rsub>。
- 多模态手势事件模块 `@ohos.multimodalInput.gestureEvent`（API 10 起）仅覆盖 `Pinch`（捏合）、`Rotate`（旋转）、`ThreeFingersSwipe`（三指滑动）、`FourFingersSwipe`（四指滑动）、`ThreeFingersTap`（三指轻点），无指关节类手势<rsub ref="G.1.5">2</rsub>。
- ArkUI 通用触摸事件（`onTouch`/`setOnTouch`）提供的是触点位置、类型、历史点等信息，不含指关节识别<rsub ref="G.1.2">3</rsub>。

除您已排除的 `TouchEvent.sourceType` 与 NDK `OH_ArkUI_UIInputEvent_GetSourceType()/GetToolType()` 之外，公开 SDK 中**未记载**任何能识别指关节输入来源或监听指关节双击手势的生产可用接口。指关节双击截屏属于系统级手势，在系统层完成识别与消费，不会以触摸事件形式透传给应用。

### 2. XT2 上指关节双击截屏是否系统统一识别、应用是否需要配合

指关节截屏（含单指关节双击截屏、双指关节双击录屏）属于系统级交互能力，由系统统一识别，在应用前台（包括 ArkWeb 获得焦点的编辑场景）默认生效。官方文档中**未记载**应用侧需要任何 `module.json5` 声明、权限或配置项来配合该手势——即应用无需任何处理，也不存在可供应用关闭/开启它的公开配置。系统设置中的「指关节截屏」开关由用户控制，与应用无关<rsub ref="H.2.10">4</rsub>。

### 3. 是否有公开 API 查询「指关节截屏」开关状态

**未记载。** 公开 SDK 中不存在查询该系统开关状态的接口。官方推荐的引导方式是应用内提供文字引导，指引用户前往系统 **设置 → 辅助功能 → 快捷启动及手势 → 截屏**（不同版本路径略有差异），开启「指关节截屏」开关。应用无法代替用户读取或修改该开关。

### 4. API 26 起的「智慧手势输入事件」是否覆盖指关节

**不覆盖。** API 26 的智慧手势（`smartGestureShortcut` 属性、`SmartGestureController` 及 `enableSmartTapAndSlideGestures` 等接口，起始版本 26.0.0）定义的是用户通过设备上的「敲一敲」「划一划」「翻腕」的 **隔空手势**，实现对组件的选中、点击、滚动、翻页、返回等交互<rsub ref="G.1.4">5</rsub><rsub ref="H.1.6">6</rsub><rsub ref="H.2.2">7</rsub>。它与触屏上的指关节手势是两套独立能力，文档中未记载二者存在关联或后续版本将指关节触屏手势纳入智慧手势的计划。因此：

- API 24 应用**无降级使用途径**（`smartGestureShortcut` 等接口起始版本为 26.0.0，且能力语义不同）<rsub ref="G.1.4">5</rsub>；
- 若您的应用未来升级到 API 26+ 且面向穿戴等支持设备，可另行接入智慧手势，但这不能替代指关节截屏的识别需求<rsub ref="H.2.6">8</rsub>。

### 5. 若实测指关节手势在应用某场景（如 ArkWeb 内）不触发，官方建议的应用侧处理

官方文档**未记载**针对 ArkWeb 或特定应用场景下指关节截屏失效的应用侧修复方案。可参考的合规处理路径：

1. 排除系统侧因素：确认系统「指关节截屏」开关已开启、设备未处于隐私模式/安全键盘等限制截图的场景（隐私模式下截图行为受系统限制，应用无法干预）。
2. 应用侧兜底：为用户提供应用内主动截图能力作为替代，例如在编辑器工具栏提供截图入口，调用 `screenshot.capture()`（API 14 起，需申请 `ohos.permission.CUSTOM_SCREEN_CAPTURE` 权限，API 22 起亦可申请 `CUSTOM_SCREEN_RECORDING`）<rsub ref="H.1.4">9</rsub><rsub ref="H.1.5">10</rsub>；或使用 `screenshot.pick()` 提供手势框选区域截图<rsub ref="H.1.5">10</rsub>。若仅需截取应用自身组件，可使用 `componentSnapshot` 组件截图，无需上述权限<rsub ref="H.1.9">11</rsub>。
3. 若确认是系统手势识别在特定场景（如 ArkWeb 焦点编辑态）的兼容性问题，建议通过 DevEco Studio 反馈通道或华为开发者社区提单，由系统侧评估修复。

## 本机 SDK 复核（2026-11-10）

复核环境：DevEco Studio 26.0.0.851 自带 API 26 SDK（`/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony`）。以下为静态声明核对，不代表 API24 / XT2 运行验收。

- `ets/api/@ohos.multimodalInput.touchEvent.d.ts`：`SourceType` 枚举实为且仅为 `TOUCH_SCREEN = 0`、`PEN = 1`、`TOUCH_PAD = 2`（均 @since 9）——答复第 1 条 ✅ 属实，无指关节来源。
- `ets/api/@ohos.multimodalInput.gestureEvent.d.ts`：接口仅有 `Pinch` / `Rotate` / `ThreeFingersSwipe` / `FourFingersSwipe` / `ThreeFingersTap` 五个（@since 10/11）——答复第 1 条 ✅ 属实，无指关节类手势。
- `ets/api/@ohos.arkui.UIContext.d.ts`：`SmartGestureController` / `UIContext.getSmartGestureController()` 均 `@since 26.0.0`——答复第 4 条 ✅ 属实，API 24 兼容目标不可用，且语义为隔空手势。
- 答复第 2、3、5 条属系统行为与「未记载」类结论，SDK 静态声明无法替代，仍需 API24 / XT2 实测（系统开关路径、应用前台 / ArkWeb 焦点场景是否触发截图）。
- ⚠️ 答复第 5 条建议的「应用侧兜底」`screenshot.capture()` / `screenshot.pick()` 需要新增 `CUSTOM_SCREEN_CAPTURE` 权限（pick 免权限但走系统框选 UI），与 [AGENTS.md 硬约束 13](../../../AGENTS.md)「非 v1.5 功能不得新增权限」冲突——除非用户显式拍板，不采纳该兜底方向；`componentSnapshot` 免权限但仅截组件，不改变本需求边界。
