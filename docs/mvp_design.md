**库是第一等公民**：一个库 = `vaults/` 下的一个目录。本地笔记是其中一个库，导入的每个 Git 仓库各自也是一个库。这样设计的原因是——如果强制先配 GitHub 才能用，装完应用是个空壳；而如果只做一个混合目录，本地笔记和被跟踪的仓库会互相污染。

### 1.3 明确不做（MVP 之后）

全文搜索、双链 `[[wikilink]]` 与反链面板、关系图谱、标签与每日笔记、模板、插件系统、PDF 与附件预览。其中搜索和双链已分别规划到 v1.1 / v1.2，其余仍在需求池。

**跨库检索同样不做**：搜索与双链只在当前库内生效，切库要重新搜（索引层规划在 v1.1）。

**历史决定（2026-10-17，已被 2026-10-25 排期调整覆盖）**：AI 助手曾后置。用户希望「在手机 App 里接入小艺做笔记编辑」，需求已登记在
`requirements_backlog.md` G 节，但**不进 MVP**，原因有二：

1. **自动 commit 的架构冲突未解**（不再阻塞本地文件操作）—— 官方方案的 git 版本底座假设有原生 ArkTS git，我们的 git 跑在 ArkWeb 里；
   而后台意图执行的生命周期是 `onCreate → onExecute`，**不建 window → Web 组件可能不存在 → commit 无处调用**。
   三条出路（入队延迟提交 / 执行时拉起不可见 Web / 放弃 git 改文件级备份）待拍板，见 `api_notes.md` **F6**。
2. **接口未核实** —— `FunctionComponent`、`@InsightIntentEntry` 等本轮答复**未附文档链接**，
   API 24 下的存在性与签名必须先复核（见 `docs/harmonyos/README.md` 待解决清单 F-A / F-B / **F-C**）。

**但两处设计要现在就预留**（成本为零，事后补会很痛）：
笔记路径统一由一层「库内相对路径 → 绝对路径」的解析器产出（意图执行器与 UI 共用，别各拼一遍字符串）；
以及 AI 写文件同样必须走 `AtomicFile`（官方示例的 TRUNC 覆盖写违反我们的原子写硬约束）。

**历史决定（已由 2026-10-25 本地优先排期覆盖）**：Git 双向同步（F6）曾纳入 MVP。原因很直接——手机端"随手记必须能回写"是硬需求，不能留到 MVP 之后。原本担心的冲突处理深水区已经绕开：手机上不做合并，冲突直接推 `xt2` 分支，丢给 PC 端解决（见 4.4）。

其余功能不做的共同理由：它们的前提都是**全库索引**，而索引层本身是独立的工作量。先跑通"单文件闭环"，再谈"库级别智能"。

## 2. 形态与断点

XT2 的三折叠意味着断点不是两档而是三档，这是本应用与普通手机 App 的核心差异。

> 官方三折叠 / 阔折叠 UX 设计指南的存档与对照结论见 `docs/三折叠_UX设计指南.md`（图文笔记被官方点名为三折叠价值场景；官方图文比例建议不覆盖我们的折痕避让约束）。

| 形态 | 断点 | 窗口宽度 | 布局 | 组件实现 |
| --- | --- | --- | --- | --- |
| 单屏态（外屏） | sm | < 600vp | 单栏：编辑器或预览二选一，底部分段切换 | `Navigation` Stack |
| 双屏态 | md | 600–840vp | 双栏：文件树抽屉 + 编辑/预览 Tab | `Navigation` Auto + `SideBarContainer` Overlay |
| 三屏展开态 | lg | ≥ 840vp | 三栏：文件树常驻 + 编辑 + 预览 | `Navigation` Auto + `SideBarContainer` Embed + 内容区左右分栏 |

### 2.1 断点获取方式

不能写死设备类型，必须在运行时按窗口宽度判断：

```ts
// EntryAbility.onWindowStageCreate
const win = windowStage.getMainWindowSync();
win.on('windowSizeChange', (size) => {
  const widthVp = px2vp(size.width);          // 必须换算成 vp
  AppStorage.setOrCreate('breakpoint', widthVp < 600 ? 'sm' : widthVp < 840 ? 'md' : 'lg');
});
```

页面侧用 `@StorageProp('breakpoint') bp: string = 'lg'` 消费，布局按 `bp` 分支。

### 2.2 形态切换的状态保持

折叠/展开只触发窗口尺寸变化，UIAbility 不重建，但布局会重排。必须保证三件事不丢：

1. 当前打开的笔记（存 `AppStorage` 或 `NavPathStack` 状态）
2. 编辑器光标位置与滚动位置（Web 方案下需要显式保存 `scrollTop` 与 selection，切换后回填）
3. 未保存的编辑内容（落盘或草稿临时文件）

### 2.3 默认分栏、拖动与折痕标注

当前按窗口宽度响应布局，不以物理屏数或折叠枚举直接决定布局。默认双栏等分、三栏各 1/3；等分不等于真实折痕位置，不承诺所有栏边界压在折痕上。折痕接口和实测边界只链接 [api_notes A2 / A6](harmonyos/api_notes.md)，不在本文复制旧 API 推断。

- 笔记页可拖分栏、导航宽度继承、独立编辑宽度、持久化和重置以 [v0.7 7.22–7.23](releases/v0.7/需求文档.md) 为准；v1.0 只回归。
- lg 导航默认 1/3，编辑与预览均分剩余宽度；收起导航后的编辑/预览宽度按独立状态处理。单屏横屏规则与真实双屏规则按同一版本条款分别验收，不从原型预设猜设备形态。
- 每个可见栏至少 240vp 是当前设计起点；拖动、恢复保存值与旋转均受窗口宽度约束，不将其称为平台硬限制。
- 折痕只作标注，不参与动态栏宽计算；不再安排“真机校准后改为物理屏宽常量表”。布局约束与组件选型依据见 [已定决策](open_questions.md) 和 [API 笔记](harmonyos/api_notes.md)。

### 2.3 折痕避让：栏宽 = 一整块物理屏

XT2 有两条铰链，把屏幕分成三块。**规则是：一栏占且只占一整块物理屏，栏边界压在折痕上**，这样任何一栏的内容都不会横跨折痕。

| 形态 | 物理屏数 | 分栏 | 每栏宽度 | 折痕位置 |
| --- | --- | --- | --- | --- |
| 外屏合起 | 1 | 单栏 + 抽屉 | 100% | 无 |
| 展开双屏 | 2 | 列表 + 编辑 | **各 50%** | 50% |
| 全展开三屏 | 3 | 列表 + 编辑 + 预览 | **各 1/3** | 33.3% / 66.6% |

推导顺序是**先定"一栏一屏"，再算宽度**，而不是先拍一个好看的宽度再去躲折痕——后者必然躲不掉（早期版本把双屏态侧栏定成 46%，编辑区就被折痕劈成两半）。

由此带来一个副作用要接受：**侧栏会比它实际需要的宽**。文件树 240vp 就够，但双屏态 330vp、三屏态 373vp 是硬性约束，收窄就会跨折痕。处理方式是把多出来的宽度用起来（每条笔记多显示一行修改时间与字数、后续放最近打开列表或摘要），而不是压缩栏宽。

**折痕位置不能写死** —— 上表的 50% / 1/3 是按三块屏等分的假设。核实后的实际情况比预想麻烦（详见 `docs/harmonyos/api_notes.md` A 组）：

- `display.getCurrentFoldCreaseRegion()` 的签名**只返回单个 Rect**，而三折叠有**两条**铰链；官方未记载三折叠下该接口返回哪一段。所以**不能把三栏边界直接建立在这个接口上**。
- `display.getFoldStatus()` 的枚举只有 4 个值，**三屏全展开（G 态）对应哪个值官方文档未记载**，需真机打印确认（可配合 `foldAngleChange` 返回的两个折轴角度综合判断）。

**分栏实现：自绘**（2026-10-17 决策）。

曾把官方 `FoldSplitContainer` 列为首选，查完官方参数表后**否决**，三条硬伤（详见 `docs/harmonyos/api_notes.md` A2-bis）：

1. **它的"三分栏"不是三列横排** —— 实际结构是 `extra` 作为右侧贯穿列，`primary` / `secondary` 在左侧**上下堆叠**。横排的列只有 2 个，而我们要的是三块物理屏横向排列的「文件树 | 编辑器 | 预览」。
2. **比例只能用预设枚举** —— `PresetSplitRatio` 只有 `LAYOUT_1V1`(1:1) / `LAYOUT_3V2`(3:2) / `LAYOUT_2V3`(2:3)，**没有 1:1:1，也不支持任意值**。
3. **它是为双折叠悬停态设计的** —— 二分栏时只有 `verticalSplitRatio`（上下分），连"列表 | 详情"左右分栏都不是它的默认形态。

因此采用：

| 阶段 | 做法 |
| --- | --- |
| M0 起步 | **自绘 + 等分**：Row/Column 按断点分档，双屏态各 50%、三屏态各 1/3。折痕在此阶段**只做标注**，不参与计算 |
| 真机校准后 | 打印 `getCurrentFoldCreaseRegion()` 与 `foldAngleChange` 双角度，得到**实际铰链位置**，把等分替换为校准值（写成常量表，按断点档位查） |

自绘的代价是折痕避让要自己做，但换来三列横排 + 任意比例的自由——后者是 XT2 的核心体验，不能让给组件。

**注意**：`EXPANDED` 在三折叠上表示"折轴一展开、折轴二折叠"，即**双屏态**；`FOLDED` 才是单屏态——与双折叠设备的直觉不同，别照搬。

除分栏外，按钮、输入框、拖拽热区也不要横跨折痕；悬停态的官方避让标准是上半屏由中线向上避让 16vp、下半屏向下避让 40vp。

**A5 已确认**：三折叠在系统中始终是 `phone`，全展开 10 英寸也不会变成 tablet / 2in1，所以 `deviceTypes` 不用改，断点差异全部交给 `windowSizeChange`（官方明确推荐这么做，不要用 `getFoldDisplayMode()` 做分支）。

## 3. 编辑器与渲染方案

### 3.1 关键判断

**无论选哪条路线，预览渲染都建议使用 Web 组件**（Markdown 的表格、代码块、嵌套列表用 ArkUI 自绘成本过高）。三条路线的真正分歧只有一个：**编辑端放不放进 WebView**。

### 3.2 方案对比

| 维度 | A：Web + CodeMirror 6 | B：ArkTS 原生 + Web 预览 | C：Native C++ + 自绘 |
| --- | --- | --- | --- |
| 编辑体验上限 | 高（高亮、多光标、代码块语言包开箱即用） | 中（无语法高亮，TextArea 纯文本） | 中（取决于编辑端用 A 还是 B） |
| 开发量 | 中（打包 + 桥接） | 低 | 高（解析 + 渲染 + 样式全自研） |
| 主要风险 | WebView 中文输入法与光标、resize 闪烁、桥接开销 | 无高亮，长文滚动需自优化 | MVP 阶段投入产出比低 |
| 大文档性能 | 依赖 WebView，需实测 | 可控 | 最好 |
| 结论 | **MVP 推荐** | 降级预案 | 后置到优化阶段 |

### 3.3 方案 A 落地要点（已选定）

**决策**：采用方案 A（Web 组件 + CodeMirror 6），并在 M1 之前完成 WebView 编辑可行性验证（spike）。spike 不通过则编辑端退回 `TextArea`（方案 B），预览端维持 Web 渲染不变。

资源布局：

```
entry/src/main/resources/rawfile/editor/
  index.html
  editor.js      # CodeMirror 6 + Markdown 语言包 + marked/DOMPurify，vite 打包为 IIFE
  editor.css
```

通信约定：

- ArkTS → Web：`runJavaScript('setContent(...)')`、`setSelection(...)`、`setScrollTop(...)`
- Web → ArkTS：`javaScriptProxy` 注入 `NativeBridge.onChange(patch)` / `onSave()` / `onScroll(...)`
- **禁止每次编辑都全文往返**，内容变化用增量 patch；首次加载才传全文

降级预案：若第一周的 WebView 编辑可行性验证（中文输入法 / 光标 / 滚动 / 折叠切换 resize 四项）不通过，编辑端退回 `TextArea`，预览端维持 Web 渲染，即方案 B。

## 4. 存储设计

> **2026-10-26 修订**：以下早期目录示意不作为当前物理布局。已确认存储方向与删库联动见 [决策总表](open_questions.md) 和 [存储规划](engineering/应用内部存储架构_审查稿.md)；不强制新增 app.json，不迁移已有 Preferences。旧示意的 app.db / app_prefs.xml 不代表已有实现；“目录名即身份”由稳定 vaultKey 与可读目录映射方案修订，尚未落码。

### 4.1 目录

笔记库存放在应用沙箱（EL2 用户级加密区），通过 `UIAbilityContext.filesDir` 访问，无需任何权限申请。

```
filesDir/
  vaults/                     # 库根目录，每个子目录 = 一个独立库
    我的笔记/                  # 首次启动创建的空白个人库
      .obsidian/              # 可选，PC 端 Obsidian 配置目录；导入时原样保留
    曜石笔记教程/              # 首次启动创建并预置共享样例，首次设为当前库
      00_开始/快速上手.md
    obsidian-vault/           # 从 GitHub 导入的库，目录名 = 仓库名（重名加 -2）
      .git/
      ...
  .index/                     # 后续搜索/双链索引（MVP 预留，不实现）
  drafts/                     # 编辑中草稿，按库分目录，异常退出可恢复
databaseDir/
  app.db                      # 应用元数据（最近打开、UI 偏好）
preferencesDir/
  app_prefs.xml               # 断点、主题、字体、当前库 id、库注册表
```

单个库内部就是一棵普通文件树，与 PC 端 Obsidian 的 vault 结构一致——这一点很重要：**导出到 PC 时目录不用转换**。

### 4.1.1 为什么是「库根 + 子目录」而不是单一 vault

- **开箱即用**：不配 GitHub 也能记，装上就能写。强制先同步等于把应用变成空壳。
- **互不污染**：本地随手记和被 git 跟踪的笔记分开，不会出现 `git status` 里混进一堆不想推的草稿。
- **各库独立**：remote、branch、token、同步频率都是库级别的；一个库同步失败不影响其他库。
- **目录名即身份**：库 id = 目录名，不做额外映射表，导出/备份时结构自解释。

### 4.2 写入策略（要点）

- **原子写：改用官方 `fileIo.AtomicFile`（API 15+，我们 API 24 可用）**，替换原设计的自研 `tmp + renameSync`。
  原因是核实后发现 **`renameSync` 在目标已存在时是否覆盖、是否原子，官方文档均未记载**——把笔记完整性押在未记载的行为上不划算。`AtomicFile` 的语义正是我们要的：写临时文件 → `finishWrite()` 成功才重命名到目标位置 → `failWrite()` 失败则删临时文件、原文件不受影响。
  ```ts
  const af = new fileIo.AtomicFile(path)
  const s = af.openWrite()
  try { s.writeSync(content); s.closeSync(); af.finishWrite() } catch (e) { af.failWrite() }
  ```
- **触发时机**：停止输入 3 秒 / 页面隐藏 / 返回键拦截 / 形态切换前
- **大目录遍历**放 TaskPool，不占 UI 线程。`fs.listFileSync` **无分页游标**（一次性返回 `string[]`，只有 `listNum` 限制条数），上千文件要在子线程里分批处理，别在主线程一次性构建大数组；**按后缀过滤只能自己写**——支持 `fileFilter` 的 `listFileExt` 是 API 26 才有，我们用不了
- 编码统一 UTF-8，换行统一 LF

### 4.4 同步：GitHub 双向

> **2026-10-30 路线更新**：优先验证并采用 Native libgit2；设备验证或数据保护证明不可行时再评估 isomorphic-git 等备选。下方 Web 架构是现有实现与历史证据，不再是当前首选；[v0.3 需求](releases/v0.3/需求文档.md)为当前执行范围。

**历史方案**：在 Web 组件内运行 isomorphic-git（纯 JS 实现），支持 clone / pull / commit / push。手机端必须能回写，所以单向导入方案作废。库规模在数百篇量级，性能顾虑不成立。

不采用更轻的 Git Data API 的原因：既然要回写，完整 git 语义（本地历史、diff、分支）带来的收益超过那点额外成本，且冲突可以用"推分支"优雅解决。

#### 架构要点

1. **运行位置**：Web 组件加载 `resources/rawfile/gitbridge/index.html`（单文件内联，含打包好的 isomorphic-git + 桥接层，268 KB）。isomorphic-git 只做计算、不依赖 DOM，因此即使 M0.5 的编辑器 spike 失败、编辑端降级到 `TextArea`，这条链路依然可用。
2. **文件系统桥接**（核心工作量）：isomorphic-git 接受自定义 `fs` 对象，实现 `readFile / writeFile / readdir / mkdir / rmdir / stat / lstat / unlink / rename`，内部转发到 ArkTS，由 `@ohos.file.fs` 操作沙箱 `vault/`。**单一数据源必须留在沙箱**，不要在 Web 侧另存 IndexedDB 副本。
3. **网络（结论已修正）**：~~isomorphic-git 用 fetch 直连 GitHub~~ —— 早期假设 GitHub 支持 CORS，实测不成立：`github.com` 的 git 服务端点（`info/refs`、`git-upload-pack`）**不返回 CORS 头**，WebView 内 fetch 会被同源策略拦掉。因此改为注入**自定义 http client**，把请求转发给 ArkTS 的 `@ohos.net.http`，天然不受 CORS 限制。`module.json5` 已补 `ohos.permission.INTERNET`。
4. **认证**：PAT（fine-grained，Contents 读写）。**当前暂存在 preferences（不安全）**，必须迁移到 **Asset Store Kit**：`@kit.AssetStoreKit` 的 `asset.addSync/querySync`，**无需申请任何权限**；敏感值只能放 `asset.Tag.SECRET`（加密位），`ALIAS` 不加密、只作检索键。多库场景下 **alias 用 `vault:<库id>:token`**，每个库单独存一份。（读取时未找到会抛 `24000002`，需捕获。）
5. **性能**：跨语言 fs 调用是主要开销。JS 侧做写缓冲，达到阈值（128 个文件 / 4 MB）才批量提交，避免逐文件跨桥；首次 clone 给进度条。

**通道分工（核实后新增）**：`runJavaScript` 的脚本长度上限官方未记载，且返回值是 string，100KB 级文本往返有明显序列化开销，**不适合做数据通道**。因此：

- 控制指令（init / clone / 状态查询）→ 继续走 `runJavaScript` + `javaScriptProxy`
- **大文本与 git packfile → 必须改走 `WebMessagePort`**（`createWebMessagePort()`，支持 ArrayBuffer）

**桥接不放在 Worker 里（原计划已修正）**：核实后确认 `javaScriptProxy` 是"注入到 window 对象"，而 **Worker 是独立全局作用域、没有 window，访问不到注入对象**。要 Worker 化就得在 Worker 与主线程之间再架一层 `postMessage` 中转，复杂度不划算。**MVP 先放主线程**（数百篇量级可接受），实测不够再优化。

**git 计算容器的承载方式**：不要用 1×1 像素的隐藏 Web 组件。官方为"页面保活"提供的是 **`NodeController` + `NodeContainer` 动态挂载/卸载 Web 节点**（离线 Web 组件），用它承载 git 容器。

#### 桥接协议

- 通道：JS→ArkTS 用 `javaScriptProxy` 注入的 `window.__arkts.postMessage(json)`；ArkTS→JS 用 `runJavaScript` 调 `window.__gitBridge.onResult(id, ok, payloadB64)`。
- 所有路径与二进制内容一律 base64，规避中文路径、二进制报文在 JSON / 脚本传参时被破坏。
- payload 统一是「JSON 文本再做一次 base64」，从而不含引号与换行，避免脚本注入与转义问题。
- fs 操作路径一律是 vault 内相对路径，ArkTS 侧校验并拒绝 `..` 与绝对路径。
- 工作区 md 文件走 `tmp + rename` 原子写；`.git` 内部文件不做原子写（git 自身有完整性保障，且对象文件极多，原子写开销大）。
- `unlink` 做成幂等：isomorphic-git 结束时会删未必存在的 `.git/shallow`。

#### 已验证 / 待验证

#### 多托管平台

桥接层走的是标准 git smart HTTP，与平台无关，换 URL 即可。已实测：

| 平台 | 公开库 | 认证方式 | 备注 |
| --- | --- | --- | --- |
| GitHub | 支持 | `Bearer <PAT>` | 用户名留空 |
| Gitee | 支持 | `Basic(用户名:私人令牌)` | **不支持 Bearer**；私有库必须填用户名 |
| 自建 GitLab | 理论支持 | `Basic(用户名:令牌)` | 未实测 |

> Gitee 的坑：对"仓库不存在"和"私有库未认证"**都返回 401**（不是 404），排查时容易误判。
> SyncPage 已对 401/404/网络错误做了人话翻译。

**已验证**（`web/gitbridge/test/node_smoke.mjs`：用 node 伪造 ArkTS 后端，把打包产物真跑一遍）。
GitHub 与 Gitee 均已成功 clone 并 checkout 出文件。过程中修掉三个真坑：

1. `channel` 与调用方**重复解了一次 base64**，导致 `atob(undefined)`。
2. http 响应体**必须包成异步块迭代器**——直接给裸 `Uint8Array` 会被 `getIterator` 当成逐字节迭代（`Uint8Array` 自带 `Symbol.iterator`），表现为 `EmptyServerResponseError`。
3. isomorphic-git 的 `StreamReader` **强依赖 `Buffer`**（源码注释 #1855），WebView 里没有这个全局，已注入 `buffer` polyfill。

**待真机验证**：`WebMessagePort` 在 `resource://rawfile/` 页面上是否可用；`NodeContainer` 承载的离线 Web 组件内 JS 是否正常执行。

**关于"拦截方案"（暂缓，仅记录）**：官方更推荐的做法是 `onInterceptRequest` 拦截请求、原生层代发、`WebResourceHandler.didReceiveResponseBody(ArrayBuffer)` 流式回填——这样 isomorphic-git 继续用原生 fetch，**JS 侧代码零改动**，且支持流式、不占内存峰值。听起来比我们现在的手动转发更优雅，**但 MVP 暂不迁移**，原因是它有一个未验证的致命前提：push 走的 `git-receive-pack` 是 **POST + 大二进制 body**，而 `onInterceptRequest` 回调能否完整拿到 POST 请求体，官方答复未覆盖。我们现有的转发方案 POST body 由 JS 侧自己构造、不受此限制，且已在 node 冒烟测试中真实 clone 成功。**决策：保留现有方案，先验证 POST body 可行性再评估迁移。**

#### 同步流程：读 main，写 main，冲突推分支

1. pull（fetch + 判断本地与远端是否分叉）
2. 无分叉 → 手机改动 commit 后直接 push 到 `main`
3. 分叉但可自动合并（不同文件，或同文件不同区域）→ 自动 merge → push `main`
4. **分叉且真冲突** → 把手机改动 commit 并 push 到 `xt2` 分支，本地 main 重置到远端最新；同时把手机版本另存到 `drafts/conflicts/`，UI 标注"这篇有未合并改动，已推送到 xt2 分支"
5. PC 端 `git merge xt2` 解冲突并推回 main；手机下次 pull 拿到合并结果，清除冲突标记

这样手机上**不需要任何合并 UI**，冲突永远不丢数据，解冲突交给 PC 端熟悉的 git 工具。

> 注意：git 无法把"未解决的冲突状态"直接 push（冲突是本地索引状态，不是可推送对象）。推到独立分支是达成同一目的的标准做法，而且比带 conflict marker 的文件更干净——PC 端看到的是两次正常提交。

#### 为什么不采用"生成冲突副本"

生成冲突副本 = 远端版本另存为 `xxx (远端版本).md`，本地保留手机版本，两边都在本地，回 PC 再挑。问题在于：① 库里多出待清理文件；② 它只是"留在本地不推"，解决不了"把改动推上去"。既然要双向，推分支更彻底。

`drafts/conflicts/` 保留手机版本仅用于"手机上还能看到自己写的内容"，不是冲突解决方案本身。

### 4.5 多库管理

  name: string        // 显示名

  dir: string         // filesDir/vaults/<id>

**生命周期**

| 操作 | 行为 |
| --- | --- |
| 首次启动 | 创建空白「我的笔记」个人库与预置共享样例的「曜石笔记教程」；首次设教程库为当前库。既有注册表 / 库目录不自动迁移或覆盖 |
| **新建本地库** | 用户输入名称 → 建 `vaults/<名称>`，默认为空库，创建后自动切为当前库；本地库可以建任意个 |
| 导入仓库 | 新建 `vaults/<仓库名>` → clone → 完成后自动切为当前库 |
| **改名** | 显示名与目录名同步修改（见下方「名称规则」）；Git 库的 remote / branch 不变，同步不受影响 |
| 切换库 | 只换当前目录；各库最近打开的文件分别记住 |
| 删除本地库 | 二次确认 → 整个目录连内容删除，不可恢复（UI 提示先导出） |
| 移除 Git 库 | 二次确认 → 只删本地目录（含 `.git`），**远端仓库不受影响**，可重新导入 |

### 4.5.1 名称规则与改名

**显示名 = 目录名，不做分离映射。** 理由：导出到 PC 时目录结构自解释，不需要额外查映射表。代价是改名要动文件系统，所以必须把实施顺序定死。

**字符消毒**（新建与改名同一套规则）：

1. 过滤 `/ \ : * ? " < > |` 与控制字符
2. 去掉前导点（防 `..` 逃逸出 `vaults/`）
3. 去首尾空白
4. 消毒后为空 → 拒绝，UI 实时提示（不要等点了保存才报错）
5. 重名 → 自动加 `-2` / `-3` 后缀；新建本地库时名称预填「本地笔记 N」

**改名的实施顺序**（顺序错了会丢状态）：

```
1. 禁止本库的同步与编辑（置锁）
2. fs.rename 改目录
3. 注册表更新 id / name / dir
4. 迁移所有按 id 索引的状态：文件树缓存、最近打开、草稿、冲突副本
5. 刷新 UI
```

任一步失败则整体回滚（目录改回去、注册表不动），不允许出现"目录改名了但注册表还是旧 id"的半状态。

**Git 库改名**：`remote` 与 `branch` 是库级字段，不随目录名变化，改名后 pull/push 照常。但 UI **必须明说"只改手机上的文件夹，远端仓库名不变"**——否则用户会以为动了远端而不敢改。

**删除的两种语义必须分开讲清楚**，这是最容易出数据事故的地方：删本地库 = 内容真没了；移除 Git 库 = 手机上没了，远端还在，重新导入即可。确认弹窗的文案、按钮颜色、是否默认提示"先导出"，三者都要区分。

**隔离规则**

- 新建笔记、最近打开、草稿恢复、搜索索引（v1.1）**全部按库隔离**
- 跨库移动文件不做（尚未分配版本）
- 当前库 id 存 preferences，冷启动时恢复；库被删后自动回落到列表第一个库

**对已有代码的影响**

- `GitFsBackend` 的 root 已经可注入（当初为抽库留的口子），改成传 `vaults/<id>` 即可，每个库一个实例
- `GitBridgeController.init(gitDir, token)` 需要加 `username`，且每次操作前按当前库初始化；clone 时目标目录即新库目录
- 新增 `VaultRegistry`：库列表 CRUD + 当前库 id 持久化 + 首次启动建本地库
- `SyncPage` 语义从"同步本库"改为"导入新库"；库级别的 pull/push 入口放在库管理卡片上
- token 按库存（不同库可能是不同平台），仍待迁关键资产存储服务

## 8. 验收标准（Definition of Done）

> 2026-10-25：默认本地库首次附带共享样例；其他新建库仍为空。2026-10-31 起，全新安装改为个人库与教程库分离，详见 [首次安装知识库决策](open_questions.md)。下列 Git 相关验收归 v0.3 后置执行，本地能力继续验收；小艺的集成路线已在 2026-10-27 明确，但仍不阻塞本地开发。

> **测试方式（2026-10-23 用户决定）**：不在模拟器上主动制造崩溃、强杀进程或写入中断。恢复与失败处理使用单测，通过可控时钟、存储失败注入和重新创建服务实例验证；模拟器仅验证正常编辑、保存、切换和重新打开。单测不代表真实进程中断或设备级原子性已验证；历史实测记录保留。

- 单屏 / 双屏 / 三屏展开三档布局均正确，无控件溢出；形态切换后文字、图片与交互区不出现意外裁切、拉伸或错位（长标题按既有单行省略规则处理）
- 折叠展开切换后：当前笔记不变、滚动位置偏差不超过一屏
- 1000 篇笔记的目录下，文件树滚动不掉帧
- 打开 100KB 的 Markdown 文件耗时 < 1s
- 草稿恢复单测：构造正式保存前已持久化的草稿状态，重新创建服务实例后能正确恢复，不串库、不覆盖更新内容
- 写入失败处理单测：注入写入/完成失败，验证失败清理与原内容保护；继续使用 AtomicFile，不安排模拟器写入中断实验
- 全新安装后不配任何远端，能直接新建并编辑笔记（本地库可用）
- 新建本地库后是空库且能立即新建笔记；改名后目录名与显示名一致，库内笔记不受影响
- Git 库改名后 pull/push 照常，远端仓库名不变
- 中文名的库能正常创建、改名、删除，导出到 PC 后目录名不乱码
- 从私有 GitHub 仓库导入成功后，库列表多出一个目录，本地库内容不受影响
- 导入中途断网重试不产生半初始化的 `.git`；失败则新目录整体回滚，不留垃圾
- 删除本地库需二次确认且删除后不可恢复；移除 Git 库后重新导入能完整还原
- 手机上改一篇笔记后 push 成功，PC 端能拉到该提交
- 人为制造冲突（PC 与手机改同一处）后，手机改动完整出现在 `xt2` 分支，本地不丢内容
- 暗色模式下编辑区与预览区均正常
