## 1. 目标与边界

### 1.1 一句话定义

一个运行在华为 XT2 上的本地 Markdown 笔记应用：打开笔记库 → 浏览文件树 → 编辑 Markdown → 查看渲染结果，且在单屏态与三屏展开态下都能用。

> **设计真源**：v2 是唯一现行设计入口；v1 设计稿与旧版测试保持删除，不恢复、不归档、不建立根路径兼容入口。旧稿只从 Git 历史只读对照；M4.10 的 P2 按 [v0.9 v1 退出门禁](releases/v0.9/需求文档.md)核验。

> **编辑模式边界**：简单与专业模式共用单栏、双栏和专注布局；分栏 / 专注按钮只改变布局。简单模式复用专业模式预览渲染并可直接编辑排版正文；专业模式额外提供每个正文栏的源码编辑 / 预览切换。自动验证、构建与设备验收分别记录在 [v1.7](releases/v1.7/验收记录.md) 和 [v1.8](releases/v1.8/验收记录.md)。

> **分享形态**：单篇 Markdown 图片分享输出一张完整连续长图，见 [v1.9](releases/v1.9/需求文档.md)；单篇图片水印另见 [v1.25](releases/v1.25/需求文档.md)，验收状态分别以各版本记录为准。

### 1.2 MVP 必须做到

> **范围与前置**：本地 Agent View 不需要做；v0.7 的 Agent 工作区、会话 / 工具功能与 App 集成均不属于当前交付，未提交初稿保留但不继续接线。v0.6 小艺基线已确认完成；v1.16 是独立的本地 Wiki 后端扩展，不接平台、不改 UI。Git v0.3 属外部依赖队列，排在本地版本之后，不作为本地功能开发前置。各版本领取顺序见 [实施总清单](releases/实施总清单.md)。

> **2026-11-03 Git 界面范围调整**：[v1.23](releases/v1.23/需求文档.md) 暂隐 Git 导入 / 同步入口与待推送角标，远端链接分享保持可用；用户随后决定通过 [v1.26](releases/v1.26/需求文档.md) 恢复前述入口。v0.3 仍为 push-only；恢复入口不代表 API24 / XT2 或真实服务商验收完成。

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| F0 | 本地笔记库 | 全新安装创建空白“我的笔记”个人库和预置样例的“曜石笔记教程”，首次进入教程库并打开《快速上手》；后续恢复用户上次选择和工作区；无需远端即可使用，本地库可再新建任意个 |
| F2 | Markdown 编辑 | 源码编辑，中文输入流畅，撤销可用 |
| F3 | 预览渲染 | 标题、列表、表格、代码块、引用、图片、任务列表、行内样式 |
| F4 | 保存与恢复 | 自动保存与草稿恢复；异常恢复逻辑用单测验证 |
| F5 | 三形态适配 | 单屏态 / 双屏态 / 三屏展开态各自布局正确，切换时当前笔记不丢 |
| F6（后置） | 导入 Git 仓库 | 填仓库地址与令牌，把远端库拉成 `vaults/<仓库名>`，与本地库并存 |
| F7 | 库管理 | 多库切换、新建本地库、改名（沙箱库同步目录名，外部库只改应用内名称）、本地库删除、Git 库移除本地副本；每个库独立同步 |
| F8 | 小艺本地笔记操作 | v0.6 基线由用户确认完成；另有 v1.16 本地 Wiki 后端扩展，范围与状态见其[需求文档](releases/v1.16/需求文档.md) |

**库是第一等公民**：一个库 = `vaults/` 下的一个目录。本地笔记是其中一个库，导入的每个 Git 仓库各自也是一个库。这样设计的原因是——如果强制先配 GitHub 才能用，装完应用是个空壳；而如果只做一个混合目录，本地笔记和被跟踪的仓库会互相污染。

### 1.3 明确不做（MVP 之后）

全文搜索、双链 `[[wikilink]]` 与反链面板、关系图谱、标签与每日笔记、模板、插件系统、PDF 与附件预览。其中搜索和双链已分别规划到 v1.1 / v1.2，其余仍在需求池。

**跨库检索同样不做**：搜索与双链只在当前库内生效，切库要重新搜（索引层规划在 v1.1）。

**两处设计要预留**（成本为零，事后补会很痛）：
笔记路径统一由一层「库内相对路径 → 绝对路径」的解析器产出（意图执行器与 UI 共用，别各拼一遍字符串）；
以及 AI 写文件同样必须走 `AtomicFile`（官方示例的 TRUNC 覆盖写违反我们的原子写硬约束）。

其余功能不做的共同理由：它们的前提都是**全库索引**，而索引层本身是独立的工作量。先跑通"单文件闭环"，再谈"库级别智能"。

## 2. 形态与断点

XT2 的三折叠意味着断点不是两档而是三档，这是本应用与普通手机 App 的核心差异。

> 官方三折叠 / 阔折叠 UX 设计指南的存档与对照结论见 `docs/三折叠_UX设计指南.md`（图文笔记被官方点名为三折叠价值场景；官方图文比例建议不覆盖我们的折痕避让约束）。

| 形态 | 断点 | 窗口宽度 | 布局 | 组件实现 |
| --- | --- | --- | --- | --- |
| 单屏态（外屏） | sm | < 600vp | 单栏：编辑器或预览二选一，底部分段切换 | `Navigation` Stack |
| 双屏态 | md | 600–840vp | 双栏：文件树抽屉 + 编辑/预览 Tab | `Navigation` Auto + `SideBarContainer` Overlay |
| 三屏展开态 | lg | ≥ 840vp | 三栏：文件树常驻 + 编辑 + 预览 | `Navigation` Auto + `SideBarContainer` Embed + 内容区左右分栏 |

### 2.1 断点获取方式

不能写死设备类型，必须在运行时按窗口宽度判断：

```ts
// EntryAbility.onWindowStageCreate
const win = windowStage.getMainWindowSync();
win.on('windowSizeChange', (size) => {
  const widthVp = px2vp(size.width);          // 必须换算成 vp
  AppStorage.setOrCreate('breakpoint', widthVp < 600 ? 'sm' : widthVp < 840 ? 'md' : 'lg');
});
```

页面侧用 `@StorageProp('breakpoint') bp: string = 'lg'` 消费，布局按 `bp` 分支。

### 2.2 形态切换的状态保持

折叠/展开只触发窗口尺寸变化，UIAbility 不重建，但布局会重排。必须保证三件事不丢：

1. 当前打开的笔记（存 `AppStorage` 或 `NavPathStack` 状态）
2. 编辑器光标位置与滚动位置（Web 方案下需要显式保存 `scrollTop` 与 selection，切换后回填）
3. 未保存的编辑内容（落盘或草稿临时文件）

### 2.3 默认分栏、拖动与折痕标注

当前按窗口宽度响应布局，不以物理屏数或折叠枚举直接决定布局。默认双栏等分、三栏各 1/3；等分不等于真实折痕位置，不承诺所有栏边界压在折痕上。折痕接口和实测边界只链接 [api_notes A2 / A6](harmonyos/api_notes.md)，不在本文复制旧 API 推断。

- 笔记页可拖分栏、导航宽度继承、独立编辑宽度、持久化和重置以 [v0.7 7.22–7.23](releases/v0.7/需求文档.md) 为准；v1.0 只回归。
- lg 导航默认 1/3，编辑与预览均分剩余宽度；收起导航后的编辑/预览宽度按独立状态处理。单屏横屏规则与真实双屏规则按同一版本条款分别验收，不从原型预设猜设备形态。
- 每个可见栏至少 240vp 是当前设计起点；拖动、恢复保存值与旋转均受窗口宽度约束，不将其称为平台硬限制。
- 折痕只作标注，不参与动态栏宽计算；不再安排“真机校准后改为物理屏宽常量表”。布局约束与组件选型依据见 [已定决策](open_questions.md) 和 [API 笔记](harmonyos/api_notes.md)。

## 3. 编辑器与渲染方案

### 3.1 关键判断

**无论选哪条路线，预览渲染都建议使用 Web 组件**（Markdown 的表格、代码块、嵌套列表用 ArkUI 自绘成本过高）。三条路线的真正分歧只有一个：**编辑端放不放进 WebView**。

### 3.2 方案对比

Web 预览消毒的源码现状和待验证项见 [实现备注](engineering/库身份与安全边界.md#2-web-预览实现备注)。

| 维度 | A：Web + CodeMirror 6 | B：ArkTS 原生 + Web 预览 | C：Native C++ + 自绘 |
| --- | --- | --- | --- |
| 编辑体验上限 | 高（高亮、多光标、代码块语言包开箱即用） | 中（无语法高亮，TextArea 纯文本） | 中（取决于编辑端用 A 还是 B） |
| 开发量 | 中（打包 + 桥接） | 低 | 高（解析 + 渲染 + 样式全自研） |
| 主要风险 | WebView 中文输入法与光标、resize 闪烁、桥接开销 | 无高亮，长文滚动需自优化 | MVP 阶段投入产出比低 |
| 大文档性能 | 依赖 WebView，需实测 | 可控 | 最好 |
| 结论 | **MVP 推荐** | 降级预案 | 后置到优化阶段 |

### 3.3 方案 A 早期设计

> 以下是早期方案，不代表 M0.5 已完成或最终选型已通过。当前 spike 证据与待验项见 [v0.2 需求文档](releases/v0.2/需求文档.md)；预览安全现状见 [安全边界](engineering/库身份与安全边界.md#2-web-预览实现备注)。

**决策**：采用方案 A（Web 组件 + CodeMirror 6），并在 M1 之前完成 WebView 编辑可行性验证（spike）。spike 不通过则编辑端退回 `TextArea`（方案 B），预览端维持 Web 渲染不变。

资源布局：

```
entry/src/main/resources/rawfile/editor/
  index.html
  editor.js      # CodeMirror 6 + Markdown 语言包 + marked 等，vite 打包为 IIFE；消毒状态见安全边界
  editor.css
```

通信约定：

- ArkTS → Web：`runJavaScript('setContent(...)')`、`setSelection(...)`、`setScrollTop(...)`
- Web → ArkTS：`javaScriptProxy` 注入 `NativeBridge.onChange(patch)` / `onSave()` / `onScroll(...)`
- **禁止每次编辑都全文往返**，内容变化用增量 patch；首次加载才传全文

降级预案：若第一周的 WebView 编辑可行性验证（中文输入法 / 光标 / 滚动 / 折叠切换 resize 四项）不通过，编辑端退回 `TextArea`，预览端维持 Web 渲染，即方案 B。

## 4. 存储设计

> 当前身份及状态键以 [库身份与安全边界](engineering/库身份与安全边界.md) 为准；下方目录图为历史示意，不代表当前物理布局。存储决策见 [决策总表](open_questions.md)。

### 4.1 目录

以下为沙箱库的历史示意；v1.5 还支持关联已授权外部目录，详见 [v1.5 需求文档](releases/v1.5/需求文档.md)。沙箱路径通过 `UIAbilityContext.filesDir` 获取。

```
filesDir/
  vaults/                     # 库根目录，每个子目录 = 一个独立库
    我的笔记/                  # 首次启动创建的空白个人库
      .obsidian/              # 可选，PC 端 Obsidian 配置目录；导入时原样保留
    曜石笔记教程/              # 首次启动创建并预置共享样例，首次设为当前库
      00_开始/快速上手.md
    obsidian-vault/           # 从 GitHub 导入的库，目录名 = 仓库名（重名加 -2）
      .git/
      ...
  .index/                     # 后续搜索/双链索引（MVP 预留，不实现）
  drafts/                     # 编辑中草稿，按库分目录，异常退出可恢复
databaseDir/
  app.db                      # 应用元数据（最近打开、UI 偏好）
preferencesDir/
  app_prefs.xml               # 断点、主题、字体、当前库 id、库注册表
```

单个库内部就是一棵普通文件树，与 PC 端 Obsidian 的 vault 结构一致——这一点很重要：**导出到 PC 时目录不用转换**。

### 4.1.1 为什么是「库根 + 子目录」而不是单一 vault

- **开箱即用**：不配 GitHub 也能记，装上就能写。强制先同步等于把应用变成空壳。
- **互不污染**：本地随手记和被 git 跟踪的笔记分开，不会出现 `git status` 里混进一堆不想推的草稿。
- **各库独立**：remote、branch、token、同步频率都是库级别的；一个库同步失败不影响其他库。
- **身份与名称分开**：`vaultKey` 为稳定内部身份；现有 `vaultId` 可随名称改变。各状态当前使用的键和迁移缺口见 [状态对照](engineering/库身份与安全边界.md#1-库身份与状态键)。

### 4.2 写入策略（要点）

- **原子写：改用官方 `fileIo.AtomicFile`（API 15+，我们 API 24 可用）**，替换原设计的自研 `tmp + renameSync`。
  原因是核实后发现 **`renameSync` 在目标已存在时是否覆盖、是否原子，官方文档均未记载**——把笔记完整性押在未记载的行为上不划算。`AtomicFile` 的语义正是我们要的：写临时文件 → `finishWrite()` 成功才重命名到目标位置 → `failWrite()` 失败则删临时文件、原文件不受影响。
  ```ts
  const af = new fileIo.AtomicFile(path)
  const s = af.openWrite()
  try { s.writeSync(content); s.closeSync(); af.finishWrite() } catch (e) { af.failWrite() }
  ```
- **触发时机**：停止输入 3 秒 / 页面隐藏 / 返回键拦截 / 形态切换前
- **大目录遍历**放 TaskPool，不占 UI 线程。`fs.listFileSync` **无分页游标**（一次性返回 `string[]`，只有 `listNum` 限制条数），上千文件要在子线程里分批处理，别在主线程一次性构建大数组；**按后缀过滤只能自己写**——支持 `fileFilter` 的 `listFileExt` 是 API 26 才有，我们用不了
- 编码统一 UTF-8，换行统一 LF

### 4.3 备份

工程已生成 `EntryBackupAbility`（backup extension）与 `backup_config.json`，MVP 阶段即可配置备份 `vault/` 目录，走系统备份恢复通道。

### 4.4 Git 同步

当前路线为 Native libgit2，已定决策速查见 [同步方案](open_questions.md)，范围和证据见 [v0.3 需求及验收记录](releases/v0.3/需求文档.md)。源码已接入状态、暂存、提交、fetch 和 push：手机将当前本地分支的提交推送到远端 `xt2`，推送前重新 fetch；远端 `xt2` 不存在时尝试创建，存在时仅在远端提交等于本地 HEAD 或是其祖先时允许推送，不强推。若已有 `xt2` 与本地分叉或远端领先，拒绝覆盖并提示在 PC 处理；若无分支写权限，由远端拒绝，应用报告失败，不保证自动解决。用户在 PC 端负责检查和处理 `main` 与 `xt2` 的合并及分叉；手机不自动合并、重置或对已有库 pull / checkout。真实服务商权限拒绝的具体提示、生产 UI 和目标设备行为仍待验。

令牌放 Asset Store 的 SECRET，当前 alias 按 `vaultId`；旧明文清理和改名迁移的限制见 [状态与安全边界](engineering/库身份与安全边界.md)。Web isomorphic-git 仅为备选，重新启用须遵循 [AGENTS.md](../AGENTS.md) 的桥接约束并重新验证。

### 4.5 多库管理

**数据模型**（MVP 存 preferences，`app.db` 建表尚未分配版本）：

```ts
interface Vault {
  id: string          // 当前显示名 / 调用标识；沙箱库也用作目录名
  vaultKey: string    // 注册表中的稳定内部身份
  type: 'local' | 'git'
  dir: string         // filesDir/vaults/<id>
  remote?: string     // git 库才有
  branch?: string
  createdAt: number
  lastSyncAt?: number
  lastSyncCommit?: string
}
```

**生命周期**

| 操作 | 行为 |
| --- | --- |
| 首次启动 | 全新安装创建空白「我的笔记」个人库与预置共享样例的「曜石笔记教程」，首次设教程库为当前库并打开《快速上手》；后续恢复上次工作区。既有注册表 / 库目录不自动迁移或覆盖 |
| **新建本地库** | 用户输入名称 → 建 `vaults/<名称>`，默认为空库，创建后自动切为当前库；本地库可以建任意个 |
| 导入仓库 | 新建 `vaults/<仓库名>` → clone → 完成后自动切为当前库 |
| **改名** | 沙箱库同步修改显示名与目录名；外部库只改应用内名称；Git 的 remote / branch 不变，令牌迁移失败需重新填写 |
| 切换库 | 只换当前目录；各库最近打开的文件分别记住 |
| 删除本地库 | 二次确认 → 整个目录连内容删除，不可恢复（UI 提示先导出） |
| 移除 Git 库 | 二次确认 → 只删本地目录（含 `.git`），**远端仓库不受影响**，可重新导入 |

### 4.5.1 名称规则与改名

沙箱库的 `vaultId` 与目录名相同；外部库改名只改变应用内标识，不修改用户目录。两者的稳定身份均为注册表中的 `vaultKey`。

**字符消毒**（新建与改名同一套规则）：

1. 过滤 `/ \ : * ? " < > |` 与控制字符
2. 去掉前导点（防 `..` 逃逸出 `vaults/`）
3. 去首尾空白
4. 消毒后为空 → 拒绝，UI 实时提示（不要等点了保存才报错）
5. 重名 → 自动加 `-2` / `-3` 后缀；新建本地库时名称预填「本地笔记 N」

**改名与失败边界**：沙箱库先改目录，再更新内存注册表并持久化；外部库不改用户目录。令牌按旧 / 新 `vaultId` 迁移，失败时提示重新填写。各项状态并未全部完成迁移；这些步骤不是单一事务，进程中断或持久化失败时不承诺整体回滚。具体状态与待验项见 [状态对照](engineering/库身份与安全边界.md#1-库身份与状态键)。

**Git 库改名**：`remote` 与 `branch` 是库级字段，不随目录名变化，改名后仍使用原 remote / branch；同步与令牌迁移须分别验收。但 UI **必须明说"只改手机上的文件夹，远端仓库名不变"**——否则用户会以为动了远端而不敢改。

**删除的两种语义必须分开讲清楚**，这是最容易出数据事故的地方：删本地库 = 内容真没了；移除 Git 库 = 手机上没了，远端还在，重新导入即可。确认弹窗的文案、按钮颜色、是否默认提示"先导出"，三者都要区分。

**隔离规则**

- 新建笔记、最近打开、草稿恢复、搜索索引（v1.1）**全部按库隔离**
- 跨库移动文件不做（尚未分配版本）
- 当前库 id 存 preferences，冷启动时恢复；库被删后自动回落到列表第一个库

**对已有代码的影响**

- `GitFsBackend` 的 root 已经可注入（当初为抽库留的口子），改成传 `vaults/<id>` 即可，每个库一个实例
- `GitBridgeController.init(gitDir, token)` 需要加 `username`，且每次操作前按当前库初始化；clone 时目标目录即新库目录
- 新增 `VaultRegistry`：库列表 CRUD + 当前库 id 持久化 + 首次启动建本地库
- `SyncPage` 语义从"同步本库"改为"导入新库"；库级别的 pull/push 入口放在库管理卡片上
- token 按库存入 Asset Store；改名和旧明文清理的边界见 [状态对照](engineering/库身份与安全边界.md#1-库身份与状态键)

## 6. 关键交互流程

0. **首次启动**：全新安装建空白「我的笔记」和带共享样例的「曜石笔记教程」→ 首次进入教程库并打开《快速上手》；后续恢复上次选择和工作区。已有安装不自动迁移或覆盖
1. **冷启动**：读库注册表并恢复会话 → 扫描当前库并读取上次打开的笔记 → 等当前布局可见的编辑器 / 预览桥接完成初始内容下发后，一次显示最终工作区；恢复期间不先显示默认布局、空编辑器再切换到笔记。笔记正文仍从库读取，不写入会话快照
2. **打开笔记**：读取全文 → 传给编辑器 → 预览侧异步渲染
3. **编辑保存**：CodeMirror 变化通知经 300ms trailing debounce、简单模式预览编辑经 180ms debounce 后到达 ArkTS；ArkTS 再安排 800ms 自动保存。保存触发后，先将待保存内容及正式内容基线写入应用私有草稿，再由 `NoteService` 原子写入正式笔记；正式保存成功后清理匹配快照。重开时仅在正式内容仍等于基线时恢复。该快照不是逐键日志，防抖及草稿提交前不承诺零丢失；详见 [草稿恢复验收](releases/v1.7/验收记录.md)。
4. **形态切换**：`windowSizeChange` → 更新断点 → 布局重排 → 回填光标与滚动位置
5. **返回拦截**：有未保存内容时弹出提示，避免直接丢内容

## 8. 验收标准（Definition of Done）

> 全新安装为个人库与教程库分离，详见 [首次安装知识库决策](open_questions.md)。下列 Git 相关验收归 v0.3 后置执行，本地能力继续验收。

> **测试边界**：不在模拟器上主动制造崩溃、强杀进程或写入中断。恢复与失败处理使用单测，通过可控时钟、存储失败注入和重新创建服务实例验证；模拟器仅验证正常编辑、保存、切换和重新打开。单测不代表真实进程中断或设备级原子性已验证。

- 单屏 / 双屏 / 三屏展开三档布局均正确，无控件溢出；形态切换后文字、图片与交互区不出现意外裁切、拉伸或错位（长标题按既有单行省略规则处理）
- 折叠展开切换后：当前笔记不变、滚动位置偏差不超过一屏
- 1000 篇笔记的目录下，文件树滚动不掉帧
- 打开 100KB 的 Markdown 文件耗时 < 1s
- 草稿恢复单测：构造正式保存前已持久化的草稿状态，重新创建服务实例后能正确恢复，不串库、不覆盖更新内容
- 写入失败处理单测：注入写入/完成失败，验证失败清理与原内容保护；继续使用 AtomicFile，不安排模拟器写入中断实验
- 全新安装后不配任何远端，能直接新建并编辑笔记（本地库可用）
- 新建本地库后是空库且能立即新建笔记；沙箱库改名后目录名与显示名一致；外部库只改应用内名称；库内笔记不受影响
- Git 库改名后仍使用原 remote / branch；同步与令牌迁移须分别验收，远端仓库名不变
- 中文名的库能正常创建、改名、删除，导出到 PC 后目录名不乱码
- 从私有 GitHub 仓库导入成功后，库列表多出一个目录，本地库内容不受影响
- 导入中途断网重试不产生半初始化的 `.git`；失败则新目录整体回滚，不留垃圾
- 删除本地库需二次确认且删除后不可恢复；移除 Git 库后重新导入能完整还原
- 手机上改一篇笔记后 push 成功，PC 端能拉到该提交
- 验证非快进拒绝时，须确认本地提交保留且远端未被覆盖，不预设分叉时推送成功；策略与验收见 [§4.4](#44-git-同步) 和 [v0.3 验收](releases/v0.3/需求文档.md#6-验收记录)。
- 暗色模式下编辑区与预览区均正常
