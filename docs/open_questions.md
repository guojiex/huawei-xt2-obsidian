### Q1. 三栏布局用官方 `FoldSplitContainer` 还是自绘？—— ✅ 已定：**自绘**（2026-10-17）

用户先拍板"用官方 `FoldSplitContainer`"，但查完官方参数表后发现**该组件不适用**，故改走自绘。三条硬伤：

1. **它的"三分栏"不是三列横排** —— 实际结构是 `extra` 作为右侧**贯穿列**，`primary` / `secondary` 在左侧**上下堆叠**（`verticalSplitRatio` 控上下高度、`horizontalSplitRatio` 控左右宽度）。横排只有 2 列，而我们要的是三块物理屏横排的「文件树 | 编辑器 | 预览」。
2. **比例只能选预设枚举** —— `PresetSplitRatio` 只有 `LAYOUT_1V1`(1:1) / `LAYOUT_3V2`(3:2) / `LAYOUT_2V3`(2:3)，**没有 1:1:1，也不支持任意值**；带 extra 时默认 `LAYOUT_3V2`，右侧只占 2/5。
3. **它是为双折叠悬停态设计的** —— 二分栏时只有 `verticalSplitRatio`（上下分），连"列表 | 详情"左右分栏都不是它的默认形态。

> 附带事实：导入路径是 `import { FoldSplitContainer } from '@kit.ArkUI'`（不是独立的 advanced 包）。

**当前方案**：默认等分、折痕只标注；不再沿用“真机校准后替换为物理屏宽常量表”的历史计划。实测结论见 [api_notes A6](harmonyos/api_notes.md)，可拖规则按上方已定决策与 v0.7 执行。

### Q5. AI 编辑笔记时，git 版本记录走哪条出路？（自动 commit 暂缓，不阻塞本地操作）

| 出路 | 做法 | 代价 |
| --- | --- | --- |
| **A. commit 入队、延迟执行** ⭐推荐 | 意图执行器写完文件后把「待 commit 路径 + 消息」写进队列文件；App 回前台、Web 就绪后由主线程消费 | 反馈文案要改成「已修改，版本待提交」；撤销也要等提交后 |

| C. 放弃意图内 git，改文件级备份 | 写前复制 `.bak` / 自建轻量历史目录 | 失去「改过什么」的历史查询；备份目录污染 vault |

**我的推荐**：先问鸿蒙 **F-C**（后台执行时 ArkWeb 是否可用），拿到答案再拍板——

| --- | --- |
| 拆成 `vaultId` + `path` 两个参数 ⭐推荐 | 大模型更不容易填错；但要补一个 `ListVaults` 意图让智能体知道有哪些库 |
| 编码成单个 `noteId`（`<库id>::<相对路径>`） | 一个参数搞定，但字符串长、大模型容易漏字符 |

2026-10-25：v0.6 首期采用显式 `vaultId` + `path`，与现有库内解析器对齐；不依赖 Git 版本记录，正式平台参数声明仍须核实。
