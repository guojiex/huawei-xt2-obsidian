# 冷启动性能优化（2026-11-15）

> 性能 profile + P1 修复记录。**纯代码修复豁免**（2026-11-15 用户决定，见
> [releases/README.md §0](../releases/README.md)）：不占版本需求、不立版本目录。
> 全部数据来自 **Windows x86_64 模拟器**（EMUC0，API 24 镜像），**不能外推到
> API 24 / XT2 真机**；真机验收由用户手动执行（既定决策）。

## 1. 问题：4 个工作区 Web 挡在冷启动首帧关键路径上

冷启动时间线（修复前，v1.63 构建，模拟器）：

| 锚点 | 相对时间 |
| --- | --- |
| fork（APPSPAWN） | 0–100ms |
| `JsUIAbility call js, name: onCreate` | 337ms |
| `onWindowStageCreate` | 457ms |
| `LoadContent: [NAPI]` | 505ms |
| `AceRouter: LoadPage Success` | 1015ms |
| `CreateNWeb NWebId: 1–4, size 1*1` | ~1570–1900ms |
| webs visible | ~2990ms |
| **首帧（`WMSMain: NotifyCompleteFirstFrameDrawing`）** | **2586ms** |

归因：左右栏的 4 个 `EditorWebView` / `PreviewWebView`（**不是** `GitBridgeView`
——同步已走 Native libgit2，该组件无挂载点）在 `build()` 即挂载；ArkWeb 初始化 +
渲染进程 fork 实测 ~1.5s，且 WMS 首帧会等可见 Web surface 的首帧 —— 首帧被整段
拖到 2.59s。`LoadPage` 到首帧之间 1.57s 基本全是 chromium。

## 2. 修复：延迟挂载（`WORKSPACE_WEB_MOUNT_DELAY_MS = 1500`）

`Index.ets`：

- `@State workspaceWebsMounted`：4 个 Web 挂载点（`EditorPane` / `PreviewPane` /
  `RightWorkspacePane` 两处）包 `if (this.workspaceWebsMounted)`；
- `aboutToAppear` 里 `setTimeout(..., WORKSPACE_WEB_MOUNT_DELAY_MS)` 置 true，
  `aboutToDisappear` 清理定时器。

为什么安全：

- 会话恢复本就在 `aboutToAppear` 启动（`initializeWorkspaceSession()`），桥接层
  「页面就绪前收到的指令先进队列，ready 后按序补发」—— 延迟期下发的 `setContent`
  不丢；
- `waitForInitialWorkspaceSurfaces()` 只等 `waitUntilReady()`（`notifyReady` /
  `notifyUnavailable` 解锁，无超时）—— 遮罩（v0.9 9.12）等 Web 就绪的语义不变，
  只是整体后移；无死锁路径（定时器必然触发）；
- `onReady` → `initializeWorkspaceSession` 有 `workspaceSessionRestoreStarted`
  幂等护栏，延迟挂载不会双推内容。

取值依据：`aboutToAppear → 首帧提交` 实测 577–931ms；`delay=1000` 时定时器与首帧
最薄只差 **15ms**（余量 +15/+291/+379ms 三次实测），1500 保住余量。**该常量是
XT2 真机调参入口**：真机若首帧更早，可适当下调；若 Web 落回首帧树（首帧退回
~2.5s），上调即可，失败模式是退回旧行为、无崩溃风险。

## 3. 修复后实测（模拟器，同机同库）

| 指标 | 修复前 | 修复后（3 次冷启动） |
| --- | --- | --- |
| `LoadPage Success` | 1015ms | 630–810ms |
| **首帧** | **2586ms** | **1160–1741ms** |
| 定时器 vs 首帧余量 | — | +909ms（1500ms 档） |
| NWeb 创建位置 | 首帧前（挡路） | 首帧后（33.300 vs 首帧 32.264） |
| Web 页面就绪（内容可呈现） | ~4.0–4.5s | ~3.8–4.9s |

- 首帧提前 **~0.9–1.4s**：首帧只渲染启动遮罩；
- 内容就绪时间基本持平（web 初始化只是从「首帧前」挪到「首帧后」，总时长不变），
  遮罩期内不可交互的体验前后一致；
- 功能 sanity：layout 树确认文件树 + 左右预览 Web 正常渲染、遮罩已褪、无 JS 错误。

## 4. 同轮 profile 的其余结论（均无泄漏 / 无异常）

- **交互**（hitrace，fling/点击负载）：~54–55fps，帧间隔 p50=15.7ms；
  UI 线程 `FlushTask` avg 0.50ms / max 8.5ms；ArkUI 帧监视
  `layout:0 render:0 property:1`；fling 期主线程 CPU avg 6.8% / max 14.8%。
- **内存**：冷启动主进程 220.7MB PSS，热态主 + render 合计 ~420–440MB；
  18 次笔记开合探针：主进程持平、render 收敛 —— **无泄漏**。
- **空闲**：两进程 0.0% CPU、零 vsync；隐藏 NWeb 每 vsync ~0.32ms（可忽略）。
- 已知小刺（未修，非本修复范围）：打开笔记一次性 ~95ms 主线程卡顿（可后续异步化）。
