# 分享预览渲染性能优化（PDF / 长图）

> 交接文档：给接手优化的 agent。**先 profile 再改代码，不要跳步改捕获逻辑。**
> 适用对象：分享流程的「PDF 预览」与「长图预览」，两条路径共用同一套捕获机制。
> 规则定位：**纯代码修复豁免**（2026-11-15，见 [../releases/README.md §0](../releases/README.md)）——
> 不改 UI 的性能修复不占版本需求、不立版本目录；动机与数据写进提交信息和 `docs/`。

## 0. 一句话现状

慢不在 Markdown 渲染，而在**「N 段严格串行截屏 + 每段多次全幅像素搬运」**：

```
N 段（页数）× 每段串行 await：
  ① setShareCaptureScrollTop → Web 滚动 + 双 rAF + 固定 64ms 死等
  ② getComponentSnapshot(waitUntilRenderFinished:true)  ← 整组件表面截图
  ③ readPixelsToBuffer → 全幅 ArrayBuffer（宽×高×4 字节，实测可达 ~8MB）← 仅用于旧帧检测
  ④ 逐字节比对 buffer（最坏扫全数组）
  ⑤ crop + scale + readPixels + writePixels ← 长图合成
  ⑥ crop + JPEG packToFile(quality:92)（PDF 路径）
```

N 段全部 `await`，没有任何一段并行。

## 2. 长期规则（不可违背，别当历史删掉）

1. **旧帧校验不能删**。`captureSegmentVerified` 是 v1.53 为修 XT2「一页渲染成两页 / 两页重复」加的，
   现语义是「两段快照像素完全相同即判旧帧 → 重拍，重试耗尽明确报错而非静默输出重复内容」。
   **只能换更廉价的比对实现，不能去掉校验本身**，也不能容忍任何会静默放行的近似比对。
2. **验证必须真机 XT2**。Windows 模拟器的像素/GPU 行为与真机差异大，性能数据**不能外推**（参照
   `docs/engineering/冷启动性能优化.md` 的同类声明）；模拟器只用于编译/逻辑回归。
3. **隐私红线（AGENTS.md 硬约束 16）**：笔记内容禁止进任何埋点/上报。性能打点只允许写
   **耗时数字、段号、尺寸、重试次数**这类元数据，禁止打正文、标题、文件名、路径。
4. **打点可开关**。诊断期 hilog 必须能用开关关掉，交付前默认关闭，不留每帧日志开销。
   （现有 `ShareDbg` 已是「临时调试…后移除」注释，沿用这个约定。）
5. **不改视觉**。本次是纯性能修复；任何涉及颜色/圆角/字号/间距的改动都要走版本需求（硬约束 17）。

## 3. 第一步：先加分段打点，跑出真实数字（默认入口，待用户确认后执行）

**不要在拿到数字前动捕获循环。** 现有日志没有耗时，无法区分是截图慢、读像素慢还是 JPEG 慢。

### 3.1 打点位置 —— ✅ 已落地（2026-11-19，编译通过）

在 `ShareFlowPanel.ets` 两个主循环每段内打了 3 个 `Date.now()` 时间戳，走现有 `ShareDbg` tag：

```
t0 ── bridge.setShareCaptureScrollTop(...) ──> t1   // ① Web 滚动 + 双 rAF + 64ms
t1 ── captureSegmentVerified(prev) ──────────> t2   // ②+③+④ 截图与旧帧校验
t2 ── crop + appendSegment / writeJpegTo ───> t3   // ⑤⑥ 像素搬运与编码（tailMs）
```

**开关**：文件顶部 `const SHARE_PERF_TRACE: boolean = true`（诊断期 true，交付前改 false）。
打点方法 `traceShareSegment(...)`，开关关闭时零开销；日志只含 stage/段号/耗时数字，无笔记内容。
`ShareSegmentCapture` 加了 `attempts: number` 字段承载旧帧重试次数。

实际日志格式（grep `ShareDbg` 抓 `pdf seg=` / `long seg=`）：

```
ShareDbg: pdf seg=<i>/<N> waitMs=<t1-t0> snapMs=<t2-t1> tailMs=<t3-t2> retries=<attempt>
ShareDbg: long seg=<i>/<N> waitMs=<t1-t0> snapMs=<t2-t1> tailMs=<t3-t2> retries=<attempt>
```

（`tailMs` = 文档早先写的 `encodeMs`，长图路径含 crop+scale+合成，PDF 路径含 crop+JPEG。）

### 3.2 Web 侧补充（可选，定位 ① 内部）

在 `index.ts:2921` 的 `setShareCaptureScrollTop` 里记 `performance.now()`，拆出
「滚动生效」与「双 rAF + 64ms 死等」各自耗时。改的是 Web 产物，改完要重新构建 mdpreview。
**本轮未做** —— 先看 3.1 的 `waitMs` 是否已是瓶颈，是再补。

### 3.3 跑法

用一篇**足够长**（≥10 段）的真实笔记，真机 XT2 上跑长图和 PDF 各一次，收集：

- 每段的 `waitMs / snapMs / tailMs`，取均值与最大值；
- 总耗时与段数的比值（判断是线性放大还是某段异常）；
- `retries` 是否 >0（旧帧重试是不是主要放大器）。

**决策规则**：哪一段占比最大就先优化哪一段。典型预期（需实测确认）：
`snapMs`（③ 全幅读像素）和 `tailMs`（⑥ JPEG / 长图合成）是大头，`waitMs` 里 64ms×N 是确定性浪费。

## 4. 第二步：优化方案（按性价比排序，改前对照 §2 规则）

### P1 — 旧帧检测换成廉价比对（收益最大，风险最高，必须保留语义）

- **改**：`ShareFlowPanel.ets:558` `readSegmentBuffer` + `:566` `segmentBuffersIdentical`
  + `:586` `captureSegmentVerified` 的入参/返回值。
- **做法**：截图后不再读整幅 `ArrayBuffer`。改成对同一 `PixelMap` 取**小尺寸采样**（如先 `scale`
  到 32×32 再 `readPixelsToBuffer`，或只 `readPixels` 顶部 1 行 + 中部 1 行的采样带），
  比对成本从 `O(w*h)` 降到 `O(数百)`。
- **正确性要求**："两帧相同"的判据不能被削弱到漏判旧帧。连续两段的合法快照在采样区域也应不同
  （现有注释 `:583` 的论证对采样区同样成立）。采样方案要先在已知会复现旧帧的场景上验证仍能触发重试。
- **连带**：`ShareSegmentCapture.buffer` 的类型/含义会变，两处调用循环（`:650` / `:807`）同步改。

### P2 — 去掉每段 64ms 死等，改条件触发

- **改**：`web/mdpreview/src/index.ts:2935` 的 `setTimeout(..., 64)`。
- **做法**：双 rAF 后直接返回；由 §4 P1 的旧帧检测承担"没出新帧"的兜底——命中旧帧时
  `captureSegmentVerified` 已有 180ms 退避重试，不需要每段无条件先睡 64ms。
- **风险**：双 rAF 后立刻截图可能更容易命中旧帧→重试。必须用 §3 的 `retries` 数字确认
  「省下 64ms×N」大于「新增重试×180ms」才保留。若净收益为负则回退。
- **注意**：`:2933` 的注释说明了这 64ms 是旧帧根因的补丁，删除前务必确认 P1 的检测仍可靠。

### P3 — JPEG 编码降质 / 并发

- **改**：`NoteImageShareService.ets:116 / :142` 的 `quality: 92`。
- **做法**：预览缩略图用较低质量（如 82~85）即可；但**导出给用户的最终 PDF/长图不能降质**，
  要区分「预览用」与「导出用」两条路径——先确认当前 `writeJpegTo` 的产物是最终导出
  （`:853` 注释：确认分享后才合成 PDF），若是则**不要降质**，只考虑并行化多个 `ImagePacker`。
- **前置**：先由 §3 的 `encodeMs` 确认编码确实是瓶颈，否则不动。

### P4 — 长图合成避免逐段两次全幅拷贝

- **改**：`NoteImageShareService.ets:72` `appendSegment`（`:82~:101`）。
- **做法**：现流程是 `source.scale()` → `readPixels(ArrayBuffer)` → `destination.writePixels(ArrayBuffer)`，
  每段两次全幅搬运。若当前 SDK（本机已升到 API26）提供 PixelMap 直接区域拷贝/drawImage 的接口，
  改走该路径省掉 JS 侧 buffer 往返。**接口存在性必须先用隔离探针实测编译**（见 §5.2），不许凭记忆写 API 名。

### P5 — 复用 buffer

- 若 P1 后仍需 `ArrayBuffer`，把每段 `new ArrayBuffer(...)` 改为循环外分配一块复用，避免 N 次大对象分配/GC。

## 5. 验证方法

### 5.1 功能回归

- 长图 / PDF 各跑一篇长笔记，确认：**无重复页、无缺页、末页水印正常、页缝无重复内容**
  （这些是 53.10/53.12/53.13 修过的 bug，改动后最容易回归）。
- 必须触发一次旧帧重试路径确认仍报错而非静默放行：可临时在 `captureSegmentVerified` 里
  强制 `prevBuffer` 用当前 buffer 验证 `attempt>=4` 抛错分支。

### 5.2 新 API 引入：隔离探针法（项目已验证有效）

本机 SDK 已是 **HarmonyOS 26.0.0 / API26**（`compatibleSdkVersion: 6.1.1(24)`）。要验证某个
SDK 符号/组件能否编译：

1. 建独立探针文件 `entry/src/main/ets/XxxProbe.ets`，`import` 并 `void 符号` 引用。
2. **必须把探针挂到入口可达链**：在 `entry/src/main/ets/pages/Index.ets` 加一行 `import './XxxProbe'`。
   孤立的探针文件不会被 ArkTS 编译（只编入口可达文件），不挂就"通过"是假象。
3. 反证：先 `import` 一个不存在的符号，构建应报 `has no exported member`——证明编译链路生效。
4. 正证：换回真实符号，构建应 `BUILD SUCCESSFUL`。
5. 验后**精确撤销**探针文件和 `Index.ets` 那一行，`git diff` 确认无残留。

（J-1 的 `UIDesignKit` 已用此法验过，结论见 `docs/harmonyos/api_notes.md` J-1。）

### 5.3 性能数据采信

- **真机 XT2** 数据为准。
- 用 DevEco Insight 时可参考项目已有的 `.insight` 解析法：htrace 事件时间戳是 boot ns 的 varint，
  墙钟换算用 `time_snapshot` 的 **pc_time ↔ boot_time** 配对（不要用 real_time）；
  B/E 切片按 **(pid, cookie, 线程名)** 分栈；**排除 `SamplingThread` 自身开销**。
- 对比优化前后用同一篇笔记、同一台设备、同样的冷/热状态，否则数据不可比。
