# 分享预览渲染性能优化（PDF / 长图）

> 交接文档：给接手优化的 agent。**先 profile 再改代码，不要跳步改捕获逻辑。**
> 适用对象：分享流程的「PDF 预览」与「长图预览」，两条路径共用同一套捕获机制。
> 规则定位：**纯代码修复豁免**（2026-11-15，见 [../releases/README.md §0](../releases/README.md)）——
> 不改 UI 的性能修复不占版本需求、不立版本目录；动机与数据写进提交信息和 `docs/`。

## 0. 一句话现状

慢不在 Markdown 渲染，而在**「N 段严格串行截屏 + 每段多次全幅像素搬运」**：

```
N 段（页数）× 每段串行 await：
  ① setShareCaptureScrollTop → Web 滚动 + 双 rAF + 固定 64ms 死等
  ② getComponentSnapshot(waitUntilRenderFinished:true)  ← 整组件表面截图
  ③ readPixelsToBuffer → 全幅 ArrayBuffer（宽×高×4 字节，实测可达 ~8MB）← 仅用于旧帧检测
  ④ 逐字节比对 buffer（最坏扫全数组）
  ⑤ crop + scale + readPixels + writePixels ← 长图合成
  ⑥ crop + JPEG packToFile(quality:92)（PDF 路径）
```

N 段全部 `await`，没有任何一段并行。

## 2. 长期规则（不可违背，别当历史删掉）

1. **旧帧校验不能删**。`captureSegmentVerified` 是 v1.53 为修 XT2「一页渲染成两页 / 两页重复」加的，
   现语义是「两段快照像素完全相同即判旧帧 → 重拍，重试耗尽明确报错而非静默输出重复内容」。
   **只能换更廉价的比对实现，不能去掉校验本身**，也不能容忍任何会静默放行的近似比对。
2. **验证必须真机 XT2**。Windows 模拟器的像素/GPU 行为与真机差异大，性能数据**不能外推**（参照
   `docs/engineering/冷启动性能优化.md` 的同类声明）；模拟器只用于编译/逻辑回归。
3. **隐私红线（AGENTS.md 硬约束 16）**：笔记内容禁止进任何埋点/上报。性能打点只允许写
   **耗时数字、段号、尺寸、重试次数**这类元数据，禁止打正文、标题、文件名、路径。
4. **打点可开关**。诊断期 hilog 必须能用开关关掉，交付前默认关闭，不留每帧日志开销。
   （现有 `ShareDbg` 已是「临时调试…后移除」注释，沿用这个约定。）
5. **不改视觉**。本次是纯性能修复；任何涉及颜色/圆角/字号/间距的改动都要走版本需求（硬约束 17）。

## 3. 第一步：先加分段打点，跑出真实数字（默认入口，待用户确认后执行）

**不要在拿到数字前动捕获循环。** 现有日志没有耗时，无法区分是截图慢、读像素慢还是 JPEG 慢。

### 3.1 打点位置 —— ✅ 已落地（2026-11-19，编译通过）

在 `ShareFlowPanel.ets` 两个主循环每段内打了 3 个 `Date.now()` 时间戳，走现有 `ShareDbg` tag：

```
t0 ── bridge.setShareCaptureScrollTop(...) ──> t1   // ① Web 滚动 + 双 rAF + 64ms
t1 ── captureSegmentVerified(prev) ──────────> t2   // ②+③+④ 截图与旧帧校验
t2 ── crop + appendSegment / writeJpegTo ───> t3   // ⑤⑥ 像素搬运与编码（tailMs）
```

**开关**：文件顶部 `const SHARE_PERF_TRACE: boolean = true`（诊断期 true，交付前改 false）。
打点方法 `traceShareSegment(...)`，开关关闭时零开销；日志只含 stage/段号/耗时数字，无笔记内容。
`ShareSegmentCapture` 加了 `attempts: number` 字段承载旧帧重试次数。

实际日志格式（grep `ShareDbg` 抓 `pdf seg=` / `long seg=`）：

```
ShareDbg: pdf seg=<i>/<N> waitMs=<t1-t0> snapMs=<t2-t1> tailMs=<t3-t2> retries=<attempt>
ShareDbg: long seg=<i>/<N> waitMs=<t1-t0> snapMs=<t2-t1> tailMs=<t3-t2> retries=<attempt>
```

（`tailMs` = 文档早先写的 `encodeMs`，长图路径含 crop+scale+合成，PDF 路径含 crop+JPEG。）

### 3.3 实测结果（2026-11-19，真机 XT2）

**样本**：用户手写笔记 `sh=36177 vh=747 vw=360 n=49 dpr=3`，PDF 共 63 段；
真机 `192.168.3.61:45005`，连跑两轮，共采到 **125 条** `pdf seg=` 打点。
长图路径**无数据**——该笔记高宽比约 100:1，v1.90 在几何预检阶段就拒绝并引导 PDF，
根本没进捕获循环（这正说明方案 A 生效；要测长图打点需换一篇中等长度笔记）。

| 指标 | 常态段（n=124） | 含重试段（n=1, seg=29） |
|---|---|---|
| `waitMs` | avg 93.8 / med 93 / p90 106 / max 136 | 184 |
| `snapMs` | avg 72.8 / med 71 / p90 96 / max 137 | **635** |
| `tailMs` | avg 68.3 / med 63 / p90 91 / max 223 | 84 |
| 三段和 | avg **235** | 903 |

- **墙钟**：第 1 轮 62 段 14.1s，第 2 轮 63 段 15.5s ≈ 63 × 235ms —— 严格线性放大，无隐藏开销。
- **三段几乎均分**（94 / 73 / 68），推翻先前"snapMs（全幅读像素）是大头"的假设。
- **`waitMs` 里的固定 64ms 占 68%**，63 段累计约 **4.0s**，是最大的确定性浪费。
- **旧帧重试极罕见**：125 段仅 1 次（0.8%）；代价集中在 `snapMs` 635ms（正常 73ms + 180ms 退避 + 重截图）。

**当时据此决定先做 P2（去 64ms 死等）**——理由：收益确定（~4.0s / 63 段 = 26%），
并假定重试率即使升到 5% 仍净赚。**这个假定被 P2 实测彻底推翻，见 §3.4。**

### 3.4 P2 实测结果 —— 净亏，已回退（2026-11-20 真机 XT2）

装含 P2 的 HAP（v1.91 / `67af2fa`）重跑**同一篇**笔记，63 段：

| 指标 | P2 前（§3.3） | P2 后 |
|---|---|---|
| 墙钟 | 15.5s | **43.4s（+2.8×）** |
| 旧帧重试率 | 0.8%（1/125） | **87%（55/63）** |
| 常态 `waitMs` | 94ms | 30ms（确实降了） |
| 常态 `snapMs` | 73ms | 41ms |
| 重试 `snapMs` | 635ms | 674ms |

**结论：删 64ms 省下 ~4s，但旧帧重试从 0.8% 飙到 87%**，55 次重试 × 每次 snapMs 多 ~633ms
≈ 35s，远超省下的 4s。**那 64ms 是 XT2 渲染服务合成表面的必要等待，不是冗余死等**——
双 rAF 只保证 DOM/JS 层渲染完，ArkWeb 合成表面还没更新，故快照必取到旧帧、触发重试。
已回退（恢复 64ms），v1.91 的 P2 路线作废。

**根本教训**：`waitMs` 的 64ms 与旧帧重试是**强耦合**的——用"稳态重试率 0.8%"去外推
"去掉等待后重试率仍低"是错的，因为重试率本身就是等待喂出来的。任何动这段等待的方案
（含缩短而非删除）都必须先按"等待→重试率"的因果重新评估，不能只算省下的绝对毫秒。

### 3.5 v1.92 试验：PDF 逐页快照降分辨率（scale=0.5，2026-11-20 真机复测：性能通过）

- **起因**：用户 2026-11-20 问「有什么办法优化，或者预览就少预览几页」。先澄清
  **「少预览几页」不省总时长**：`composePdf()` 复用的就是预览时截的逐页 JPEG，只截前 K 页
  必须在点确认后补截剩余页，总时长不变且多出交互/失败回滚（只有「多数预览不导出」才划算）。
  真正没试过且风险可控的是降**截图像素量**（`snapMs`+`tailMs` 合计约 8.9s / 63 页）。
- **做法**：`componentSnapshot.get(id, { waitUntilRenderFinished: true, scale })`——
  SDK `@ohos.arkui.componentSnapshot.d.ts:414` 的 `SnapshotOptions.scale`（`@since 12`，API24 可用），
  官方注释明示「高 scale 会增加截图耗时甚至失败」，反向即降 scale 省时。
  `ShareFlowPanel.ets` 新增 `PDF_SNAPSHOT_SCALE = 0.5`，由 `captureSegmentVerified` 第二参数透传；
  **PDF 循环传 0.5，长图循环固定 1.0**（长图 `longImageGeometry` 依赖原始截图尺寸推算
  96 MiB 预算 / 640px 下限，降 scale 会破坏几何）。
- **为何安全（比例运算）**：PDF 循环里的 A4 宽高比校验、页间尺寸一致性校验、
  `cropPx = imageInfo.size.height * sliceVp / pageHeightVp`、按 `pageAspects` 贴图合成，
  全是按比例的，等比缩放不改变结果；`exportFromPageImages` / `writeJpegTo` 无绝对尺寸假设。
- **已验**：签名 HAP `BUILD SUCCESSFUL`（2026-11-20 09:07，零 ArkTS ERROR），
  `test_pdf_pagination` 38/38（新增 4 条源级断言锁定 scale 透传与长图 1.0）。
- **真机复测（2026-11-20 09:16 / 09:17，同一台 XT2、同一篇 63 页笔记，连跑两轮共 126 条）**：

  | 指标 | 基线 scale=1.0（§3.3） | v1.92 第 1 轮 | v1.92 第 2 轮 |
  |---|---|---|---|
  | `waitMs` | 93.8 | 93.1 | 93.8 |
  | `snapMs` | 72.8 | **36.7** | **39.5** |
  | `tailMs` | 68.3 | **20.9** | **27.9** |
  | 三段和 | 235 | 150.7 | 161.1 |
  | 墙钟 63 页 | 14.1~15.5s | ≈9.5s | **10.0s**（09:17:06.811→09:17:16.822） |
  | `retries` | 0.8%（1/125） | 1/63 | 0/63 |

  `snapMs` −46~49%、`tailMs` −59~69%、单页 235→151/161ms、墙钟 **约 15.5s→10.0s（−35%）**；
  `waitMs` 与重试率**无劣化**（P2 的覆辙没有重演）。**性能侧判定通过**。
- **但本版还不能宣布整体验收通过**：用户复测后反馈「预览的一页很短」，属新的页几何/清晰度
  观察，见 §3.6。P6 常量先保持 0.5，待 §3.6 判定后再决定保留或回退。
- **回退/调值判据**：下降不明显、等待/重试劣化、或清晰度/页几何不可接受 → 常量改回 1.0 或整版回退；
  结果照实回填本节与 `docs/releases/v1.92/需求文档.md` §6。
- **已知风险**：低分辨率下旧帧检测「两段像素完全相同」的判据仍需成立，按 §5.1 触发一次
  重试路径确认不静默放行。

### 3.6 2026-11-20 新增观察：「预览的一页很短」与几何打点

- **现象**：装含 v1.92 的 HAP 跑同一篇 63 页笔记后，用户反馈 PDF 分页预览里每页看起来很短。
- **先排除 scale**：PDF 循环里 A4 宽高比校验、页间尺寸一致性校验、
  `cropPx = imageInfo.size.height * sliceVp / pageHeightVp`、`pageAspects = width / cropPx`
  全是**比例运算**，等比缩放的 `scale` 在分子分母里消去；`NotePdfExportDevice.exportFromPageImages`
  按 `pageAspects` 贴图也无绝对尺寸假设。故理论上 `scale=0.5` 只降像素密度、不改页面几何。
- **更可能的既有成因（与 v1.92 无关）**：`web/mdpreview/src/pdfPagination.mjs` 按段落贪心分页，
  `tops[i+1] − tops[i]` 是「本页切片高」；小块放不下整块下移（`:78` 分支）时切片远短于整页。
  端侧 `ShareFlowPanel.ets:878` 把页图裁到 `cropPx`，而 `SharePdfPreviewDialog.ets` 自 2026-11-18
  起是 **A4 白纸衬底 + 页图顶对齐**（该处注释已记「XT2 实测『每页都很短』」，当时修的是把
  「矮胖条」换成 A4 纸，不是把内容拉长）。于是短切片页在纸面上只占上半截、下方留白 →
  视觉上「一页很短」；最终 PDF 同样按 `pageAspects` 贴顶，这部分留白是刻意的自然分页留白。
- **未排除的平台风险**：`SnapshotOptions.scale` 在 XT2 上是否只缩小输出位图、不改截图覆盖区域，
  `api_notes.md` 无明文结论。若它截到的是组件的一部分，页图内容也会被截短。
- **判定方式（已加打点，不改行为）**：PDF 循环新增 `pdfgeo` 日志，开关仍为 `SHARE_PERF_TRACE`：

  ```
  ShareDbg: pdfgeo start pages=63 scalePct=50 pageVp=<整页 vp 高>
  ShareDbg: pdfgeo i=<i>/<N> w=<截图宽 px> h=<截图高 px> fillPct=<切片高/整页高 %> cropPx=<裁后高 px> aspectMilli=<宽/高×1000>
  ```

  判据：① `w/h` 约为 `pageVp × dpr × 0.5`（scale 生效且等比）、`aspectMilli ≈ 707`（A4）
  → 截图几何正常；② 大量页 `fillPct < 60` → 「短」来自分页切片，与 scale 无关，P6 保留，
  是否改分页另议；③ `fillPct ≈ 100` 但 `h` 明显偏小或 `aspectMilli` 偏离 707 →
  scale 平台行为异常，按 §4 P6 把常量回退为 `1.0`。
- 打点为诊断期临时代码，随 §6 最后一条与其余 `ShareDbg` 打点一起删除。
- **判定结果（2026-11-20 09:34 轮，新 HAP，63/63 页）**：全部页 `w=570 h=807`（= 380×538vp ×
  dpr3 × 0.5）、`aspectMilli=706`（A4=707）、`fillPct=100`、`retries=0`。判据 ①② 通过、
  ③ 不成立 → **scale 几何无损，P6 保留**；用户澄清「短」= 每页正文内容少，归因见下条。
- **「每页内容少」的根因（与本优化无关，是页宽自适应设计）**：`pdfgeo start pageVp=538`
  说明页宽被窗口钳到 380vp。`updatePdfPageSize`（2026-11-11 修复，字段注释 :122~:128）
  的约束是**捕获层必须待在窗口布局内**——窗口高不足页高时 `#content` 视口被压矮、
  分页高度补不齐，故页宽 ≤ 700vp 且不超窗口宽高。XT2 窄窗 380vp → 页宽 380、页高 538，
  每页容量小、页数多。**零代码解法：展开三折叠（宽窗）再导出，页宽自动升到 700vp 上限**；
  若要任意形态固定 700vp 大页，需让捕获层脱离窗口布局约束，属 UI 行为改动，
  已登记需求池候选（`requirements_backlog.md` 分享域）。

### 3.7 v1.93：固定 700vp 大页 —— 页数与总时长的双重收益（2026-11-20 真机 XT2）

- **做法**：捕获页尺寸改固定 `700×991vp`（`PDF_TARGET_PAGE_WIDTH_VP` /
  `PDF_TARGET_PAGE_HEIGHT_VP`），捕获层 `Stack` + `clip(false)` + 定尺寸 `PreviewWebView`，
  **不依赖窗口尺寸**；视口与目标不符时自动降级回 2026-11-11 的窗口自适应口径
  （`degraded=1`）。详见 `docs/releases/v1.93/需求文档.md`。
- **实测（窄窗 win=380×814vp，同一篇 63 页笔记，两轮各 20 页）**：

  | 指标 | v1.92（380×538vp） | v1.93（700×991vp） |
  |---|---|---|
  | 页数 | 63 | **20** |
  | 单页 `wait/snap/tail` | 93 / 37 / 21 ms | 83 / 42 / 44 ms（像素 ×3.4，单页只涨 1.4 倍） |
  | 总墙钟 | ≈10.0s | **≈3.4s**（提速约 3 倍） |
  | retries | 0~1 / 63 | 0/20（首轮）；**7/20（紧接的连续第二轮）** |

- **平台结论（重要，写进 `api_notes.md`）**：ArkWeb **不会**把超出窗口的组件视口压矮——
  `vpW=700 vpH=991 degraded=0`，2026-11-11「分页高度不足」的旧病不复现。
  静态先验也一致：长图宽度 `'wide'`=720vp 在窄窗下今天即可用。
- **遗留观察项**：连续第二轮重试率升到 7/20（`snapMs` 尖峰 563~691ms）。重试上限 4 次兜底，
  两轮均正常产出 20 页、无内容重复，**正确性不受影响**；成因（连续导出后的内存/合成压力
  vs 偶发）待查——需隔一段时间再跑一次「首轮导出」对照。
- **收益归因**：v1.92 的 `scale=0.5` 与 v1.93 的大页**可叠加**（前者降像素密度，后者降页数），
  两者都已验证；不要因为 v1.93 达成就把 `scale` 回退到 1.0。

## 4. 第二步：优化方案（按性价比排序，改前对照 §2 规则）

> **当前执行状态（2026-11-20）**：P2 已回退作废；**P6（v1.92）已真机复测通过并保留**
> （`scale=0.5`，15.5s→10.0s，§3.5），且与 **v1.93 固定 700vp 大页**（§3.7）叠加后
> 63 页→20 页、总时长 **≈3.4s**。P1/P3~P5 尚未评估；P1 的「采样比对」思路与 scale 可叠加
> 但先不叠加，避免一次改两处无法归因。

### P1 — 旧帧检测换成廉价比对（**实测后降为次要**：常态 snapMs 仅 73ms；仍保留语义要求）

- **改**：`ShareFlowPanel.ets:558` `readSegmentBuffer` + `:566` `segmentBuffersIdentical`
  + `:586` `captureSegmentVerified` 的入参/返回值。
- **做法**：截图后不再读整幅 `ArrayBuffer`。改成对同一 `PixelMap` 取**小尺寸采样**（如先 `scale`
  到 32×32 再 `readPixelsToBuffer`，或只 `readPixels` 顶部 1 行 + 中部 1 行的采样带），
  比对成本从 `O(w*h)` 降到 `O(数百)`。
- **正确性要求**："两帧相同"的判据不能被削弱到漏判旧帧。连续两段的合法快照在采样区域也应不同
  （现有注释 `:583` 的论证对采样区同样成立）。采样方案要先在已知会复现旧帧的场景上验证仍能触发重试。
- **连带**：`ShareSegmentCapture.buffer` 的类型/含义会变，两处调用循环（`:650` / `:807`）同步改。

### P2 — 去掉每段 64ms 死等 —— ❌ **已尝试并回退（v1.91 立→撤，2026-11-20）**

- **尝试**：删 `web/mdpreview/src/index.ts` `setShareCaptureScrollTop` 的 `setTimeout(..., 64)`，
  双 rAF 后直接返回，旧帧兜底交给端侧 `captureSegmentVerified`（v1.91 / `67af2fa`）。
- **实测**：墙钟 15.5s→43.4s、重试率 0.8%→87%，净亏（详见 §3.4）——64ms 是必要的合成等待。
- **回退**：源码恢复 64ms 等待（保留"曾尝试并回退"的注释防重犯）；测试断言恢复"必须有 64ms"；
  rawfile 产物重建回含 64ms。v1.91 代码变更撤销，仅留版本文档与本节记录教训。
- **结论**：⛔ **不要再提议删这段等待**。双 rAF ≠ 合成表面就绪；要优化 `waitMs` 得从
  "让合成更早就绪"入手（如减少 Web 内容复杂度），而非直接砍等待。P1/P3~P5 仍未评估。

### P3 — JPEG 编码降质 / 并发

- **改**：`NoteImageShareService.ets:116 / :142` 的 `quality: 92`。
- **做法**：预览缩略图用较低质量（如 82~85）即可；但**导出给用户的最终 PDF/长图不能降质**，
  要区分「预览用」与「导出用」两条路径——先确认当前 `writeJpegTo` 的产物是最终导出
  （`:853` 注释：确认分享后才合成 PDF），若是则**不要降质**，只考虑并行化多个 `ImagePacker`。
- **前置**：先由 §3 的 `encodeMs` 确认编码确实是瓶颈，否则不动。

### P4 — 长图合成避免逐段两次全幅拷贝

- **改**：`NoteImageShareService.ets:72` `appendSegment`（`:82~:101`）。
- **做法**：现流程是 `source.scale()` → `readPixels(ArrayBuffer)` → `destination.writePixels(ArrayBuffer)`，
  每段两次全幅搬运。若当前 SDK（本机已升到 API26）提供 PixelMap 直接区域拷贝/drawImage 的接口，
  改走该路径省掉 JS 侧 buffer 往返。**接口存在性必须先用隔离探针实测编译**（见 §5.2），不许凭记忆写 API 名。

### P5 — 复用 buffer

- 若 P1 后仍需 `ArrayBuffer`，把每段 `new ArrayBuffer(...)` 改为循环外分配一块复用，避免 N 次大对象分配/GC。

### P6 — PDF 逐页快照降分辨率（✅ **v1.92 已落地并真机复测通过**，保留）

- **改**：`ShareFlowPanel.ets` 顶部 `PDF_SNAPSHOT_SCALE = 0.5` + `captureSegmentVerified` 第二参数
  `snapshotScale` 透传到 `get(id, { waitUntilRenderFinished: true, scale })`。
- **做法与边界**：PDF 循环传 `0.5`、**长图循环固定 `1.0`**（长图几何依赖原始截图尺寸）；
  等比缩放不影响 A4 比例校验 / 页间尺寸校验 / 按比例算的 `cropPx`。详见 §3.5。
- **依据**：`snapMs`(73) + `tailMs`(68) ≈ 141ms/页 × 63 ≈ 8.9s 都与像素量成正比；
  SDK `SnapshotOptions.scale` `@since 12` 可用，官方自述「高 scale 增加截图耗时」。
- **正确性要求**：旧帧检测语义不变（仍需按 §5.1 触发一次重试确认）；不动 `waitMs`（P2 教训）。
- **风险**：PDF 页清晰度下降（贴图是屏幕截图非矢量）；若底层实现是「全尺寸渲染后再缩」，
  则只省 `readPixels` 与 JPEG 编码、不省截图本身——**这正是打点要区分的**：看 `snapMs` 是否同步下降。
- **回退**：常量改 1.0 或整版撤销，照实回填 §3.5 与 v1.92 需求文档 §6。

### 5.2 新 API 引入：隔离探针法（项目已验证有效）

本机 SDK 已是 **HarmonyOS 26.0.0 / API26**（`compatibleSdkVersion: 6.1.1(24)`）。要验证某个
SDK 符号/组件能否编译：

1. 建独立探针文件 `entry/src/main/ets/XxxProbe.ets`，`import` 并 `void 符号` 引用。
2. **必须把探针挂到入口可达链**：在 `entry/src/main/ets/pages/Index.ets` 加一行 `import './XxxProbe'`。
   孤立的探针文件不会被 ArkTS 编译（只编入口可达文件），不挂就"通过"是假象。
3. 反证：先 `import` 一个不存在的符号，构建应报 `has no exported member`——证明编译链路生效。
4. 正证：换回真实符号，构建应 `BUILD SUCCESSFUL`。
5. 验后**精确撤销**探针文件和 `Index.ets` 那一行，`git diff` 确认无残留。

（J-1 的 `UIDesignKit` 已用此法验过，结论见 `docs/harmonyos/api_notes.md` J-1。）
