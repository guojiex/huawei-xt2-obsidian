# 数据驱动页面：单一真源与离线生成

> 本仓库可复用的技术储备。适用于共享样例、版本记录等内容随代码发布、App 与原型需要同源的页面；不引入在线 CMS 或通用页面引擎。

## 两个已落地实例

| 数据 | 人工维护的真源 | 生成入口 | 生成产物 | UI |
| --- | --- | --- | --- | --- |
| 样例笔记 | `sample_vault/notes/` + `manifest.json` | `tools/generators/build_sample_vault.py` | `SampleVaultData.ets`、原型标记区 | 原型文件树/正文、App 首装副本 |
| 版本记录 | `changelog.json` | `tools/generators/build_changelog.py` | `ChangelogData.ets`、`CHANGELOG.md`、原型标记区 | 关于最近 3 条、离线完整记录 |

两个脚本独立维护，使用相同原则；不为两个内容类型创建通用 schema 或配置平台。

## 版本信息的边界

- 安装包版本唯一真源仍是 `AppScope/app.json5`；App 运行时从自身包信息读 versionName/versionCode，接口见 [api_notes H 组](../harmonyos/api_notes.md)。
- `changelog.json` 的版本是阶段记录标识，不能覆盖运行时包版本，也不表示已经发版。原型包版本由脚本只读提取自 app.json5，去掉另一份手写常量。
- 状态使用 `in_progress`（开发中）、`implemented`（已实现未发布）、`pending`（暂缓未发布）、`released`（已发布）。只有实际发布后才写 released；日期是记录日期，未发布条目不能伪装成发布日期。
- 记录按数值版本降序排列。**用户可见条目 = 非 `internal` 且非 `pending`**：关于展示最近 3 条，完整页面展示全部可见记录；`internal` 条目与 `notes` 备注只进 `CHANGELOG.md`，不进 App 与原型。它们共用 App 的 ChangelogList，避免 UI 复制后发生漂移。
- `changes` 只写已实现、面向用户的功能；验收状态、待验项、skip 记录等内部信息写进 `notes`。App 端不渲染任何状态标签。
- 完整记录在 App 内离线查看，顶栏与系统返回回到设置；没有浏览器、联网更新检查或数据采集。

## 数据格式

```json
{
  "schemaVersion": 1,
  "entries": [
    {
      "version": "0.5.0",
      "date": "2026-10-25",
      "status": "in_progress",
      "title": "共享样例与数据管理",
      "changes": ["已实现、面向用户的变化。"],
      "notes": ["内部备注：验收状态与待验项，只进 CHANGELOG.md。"],
      "internal": false
    }
  ]
}
```

生成前校验版本唯一、三段数值版本、合法日期、合法状态与非空内容。记录正文是纯文本：ArkUI 使用 Text，原型用 textContent 创建节点，不能将数据直接作为 innerHTML；内嵌脚本还必须转义 `<`、U+2028、U+2029，防止 `</script>` 提前闭合。

## 维护与验证流程

1. 只修改真源。新版本先有版本需求，完成可描述的改动后再写更新记录；规划中的功能不伪装成已交付。
2. 执行对应生成器；不要手改生成的 ETS、Markdown 或原型标记区。脚本只替换自己的标记区，保留原型的其他 UI 工作。
3. 提交前执行：

```bash
python3 tools/generators/build_sample_vault.py --check
python3 tools/generators/build_changelog.py --check
PYTHONDONTWRITEBYTECODE=1 python3 tools/tests/test_changelog.py
node --test tools/tests/test_sample_vault.mjs
```

4. 修改了 UI 组件还要运行工程构建。生成检查、单测、编译、原型目视与设备验收分开记录；生成正确不等于设备渲染通过。
5. 真源与生成产物一起提交。检查 Git diff，确认不包含个人笔记、签名凭据、日志或无关工作。只改 changelog 不会自动发布、改包版本或打 tag。
6. 发布时依照 [版本规则 R9](../releases/README.md)，修改包版本及对应日志状态，重新生成，再完成 tag 与版本索引。

`--check` 重新在内存中生成预期产物，再与文件逐字比较；发现过期就失败，不静默修改工作区。这样可在本地或未来 CI 中发现“改了源数据却忘记重新生成”。它也验证原型包版本是否随 app.json5 同步。

## 后续复用方法

遇到新的内容页面，先确认：是否适合静态发布、谁维护真源、哪些客户端消费、当前值是否必须来自运行时。只为实际重复的数据提取源文件，保留现有组件和 token；不将业务状态、敏感数据或设备运行信息固化进静态生成物。

若以后抽成 skill，应封装“定位真源 → 校验 → 定向生成 → --check → 构建与验收 → 检查提交范围”的工作流，并保留项目特定路径和 API 约束。本篇与实际脚本是当前可直接复用的依据。
