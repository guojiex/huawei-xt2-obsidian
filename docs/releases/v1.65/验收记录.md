# v1.65 验收记录

> 更新：2026-11-15。v1.65 需求（65.1–65.5）已随 1.9.0 发布；本文补记发布后发现的
> 屏保名言轮换缺陷（用户 XT2 真机报告）及其修复。

## 65.3 缺陷修复：屏保轮换正文冻结、首换抢跑（2026-11-15）

### 现象（XT2 真机报告 + API26 模拟器复现）

用户报告（真机，名言轮换间隔设 15 秒）：同一句名言刚逐字浮现完，马上又重新浮现一遍，
完全没有按 15 秒间隔轮换。模拟器（Huawei_TripleFold，`127.0.0.1:5555`，默认 30 秒档）
复现出比报告更严重的形态：

- 名言**正文**从进入屏保起一直冻在入场那句（实测「他山之石，可以攻玉。」）；
- **出处**却在正常轮换（王维《终南别业》→ 荀子《劝学》→ …），正文与出处张冠李戴；
- 首次「重浮」发生在进入屏保约 3.8 秒时（入场编排刚播完 ~0.5 秒后），与间隔档位无关。

### 根因（三个独立缺陷叠加）

1. **轮换数据源不是状态变量 —— ForEach 不感知换句。** 名言逐字渲染的
   `ForEach(this.quoteLineChars, …)` 数据源 `quoteLineChars` 是普通私有字段（无 `@State`）。
   ArkUI ForEach 对非状态数据源只渲染一次：换句后即使整组重赋值，ForEach 也不会重新
   diff，正文节点永远停留在入场那句；而出处是直接绑定 `quote.source` 的单一 `Text`，
   随组件重渲染正常更新——于是正文冻住、出处乱配。
2. **ForEach 位置 key 按位置复用旧节点。** 逐字 / 分句两层 ForEach 的 key 只含行列下标
   （`'startup-quote-' + lineIndex + '-' + index`）。即便数据源可观察，换句后新旧两句在
   同一位置生成相同 key，ArkUI 按 key 复用旧 `Text`、不重跑 itemGenerator，正文同样
   冻结。修复时实测：只把 key 加上 `quoteIndex` 而不动数据源，正文依旧冻结——
   两处必须一起修。
3. **首次轮换无视间隔档位。** `ScreenSaver.firstRotateDelay = Startup.minHold +
   Startup.enterDur = 3800ms` 是固定值：入场编排约 3.3 秒播完，0.5 秒后即触发首次
   换句。叠加缺陷 1/2 后，用户看到的就是「同一句名言刚显示完马上又浮现一遍」。

### 修复（`StartupMask.ets` / `Tokens.ets`）

- `quoteLineChars` 挂 `@State`；`applyQuote` 改为局部拼完完整数组后**一次性**赋值
  （避免赋半截数组触发多次 diff 抖动），`quoteLineOffsets`、`quoteCharCount` 同步重算。
- 两层 ForEach 的 key 全部加入 `quoteIndex`（`'startup-quote-' + this.quoteIndex + …`），
  换句强制重建正文节点。
- 首次换句改为入场编排播完（组件内既有 `holdMs`）后再等一个完整轮换间隔：
  `scheduleRotate(this.holdMs + this.quoteIntervalMs)`；减动效路径无入场编排，直接
  `scheduleRotate(this.quoteIntervalMs)`。删除已无引用的 `ScreenSaver.firstRotateDelay`
  token。
- 契约测试 `tools/tests/test_screensaver_design.mjs`：65.3/65.5 断言更新，新增 65.7
  锁定 `@State` 数据源、key 形状、一次性赋值与首换时机。
