# 版本化开发规则（`docs/releases/`）

> 这里是**版本交付档案**的唯一存放处。
> **每一个版本 = 一个目录，目录名就是版本号；每个版本目录里必须有需求文档。**

---

## 0. 一句话规则

**任何落码，都必须能对应到某个版本目录里的某条需求。**
需求池里没分配进版本的需求 = 不许开工；版本目录里没有的需求 = 不许顺手做。

---

## 1. 目录约定

```
docs/releases/
├── README.md              ← 本文件：规则 + 版本索引（唯一入口）
├── v0.1/
│   └── 需求文档.md         ← 【必须】本版本做什么、怎么算做完
├── v0.2/
│   └── 需求文档.md
└── v0.3/
    └── 需求文档.md
```

| 文件 | 是否必须有 | 放什么 |
| --- | --- | --- |
| `需求文档.md` | ✅ **必须** | 本版本的范围、需求清单、完成判定、**明确不做**、验收记录 |
| `设计说明.md` | 按需 | 本版本涉及架构决策时才写（**且结论要链接回 `docs/harmonyos/`**） |
| `验收记录.md` | 按需（发布后补） | 需求文档写不下时单独开；真机实测值优先写这里 |
| `实现提示词*.md` | 按需 | 把本版本（或其中一段）交给**其他 Agent** 实现时的自包含提示词（见 R10）。<br>现有：`v0.1/实现提示词.md`、`v0.1/实现提示词_2.7次级页面返回.md`、`v0.2/实现提示词_M0.5spike.md` |

> **代码不分版本目录。** 源码只有一份（`entry/`），版本由 git 分支与 tag 管理。
> 本目录只放「这个版本承诺交付什么、实际交付成什么样」的档案 —— 不复制代码。
>
> ⚠️ **范围以本目录的需求文档为准。** 某些版本另有执行计划（例：v0.1 的执行计划在
> `spec/v0.1_skeleton_vault/{spec,plan,tasks}.md`），它只描述「怎么做」，**不是承诺记录**；
> 两者冲突时**以 `需求文档.md` 为准**，并回来修订其中一边。

## 2. 规则（R1–R9）

### R1 一个版本一个目录，目录名即版本号

格式 `v<MAJOR>.<MINOR>`（两位制，如 `v0.1`、`v1.0`）。
`app.json5` 的 `versionName` 与之对应：`v0.1` → `"0.1.0"`；`versionCode` 单调递增。

### R2 版本号语义

| 变更 | 版本怎么动 |
| --- | --- |
| MVP 完结前的每个阶段 | `0.x` 递增（`v0.1` → `v0.2` → `v0.3`） |
| MVP 完结（对外可用） | `v1.0` |
| 新增功能、向后兼容 | `+MINOR` |
| 改数据结构 / 库目录布局 / 破坏兼容 | `+MAJOR` |
| 只修 bug、不动功能 | 就地为当前版本补 `验收记录.md`，**不开新版本** |

### R3 先有需求文档，再落码

开新版本 = 先建目录 + 先写 `需求文档.md`，**写完之后才允许动手写代码**。
严禁「先写一堆代码，回头补一份文档」——那样文档永远对不上实际交付。

### R4 需求只能从需求池分配进来

版本目录**不许凭空新增需求**。流程固定为：

```
docs/requirements_backlog.md（需求池：所有想做的）
        │  挑选 + 排优先级
        ▼
docs/releases/vX.Y/需求文档.md（本版本承诺交付的）
        │  落码
        ▼
验收 → 发布 → 冻结
```

新冒出来的需求：**先回池子登记**，再决定塞进当前版本还是下一个。
（当前版本还没发布且改动很小时可以吸收，但必须同步更新需求文档，不 silently 加。）

### R5 结论只准链接，不准复制

版本文档里涉及的三类内容**一律链接，不复制**：

- 鸿蒙行为结论 → `docs/harmonyos/api_notes.md`
- 已定决策 → `docs/open_questions.md` 的已定决策总表
- 整体架构与里程碑 → `docs/mvp_design.md`

理由同知识库铁律：结论会被推翻，抄一份就漏改一处。

### R6 每个版本都要写「明确不做」

这是防范围膨胀的关键一节。写清楚本版本**不做什么、为什么不做**，
比写"要做什么"更能防止中途加塞。

### R7 版本发布后冻结

版本发布（打 tag）后：

- `需求文档.md` **不再改**（它是对外承诺的历史记录）
- 遗留问题与新需求 → 写进 `验收记录.md` 或回流需求池，**进下一个版本**
- 要改已发布版本的需求 = 承认计划失败，先写清楚原因再改（保留痕迹）

### R8 版本与里程碑（M 编号）的映射

`docs/mvp_design.md` 里的 **M0 / M0.2 / M1…** 是**开发顺序**，
版本号是**交付单元**。每个版本的需求文档必须写明「本版本包含哪些 M 阶段」。

> 约束：**一个 M 阶段不得跨版本拆分**（要么整个进某版本，要么整体推迟）。

### R9 发布动作

发布一个版本 = 三件事：

1. 补齐该版本目录的验收记录（`需求文档.md` 第 6 节）
2. 同步 `app.json5` 的 `versionName` / `versionCode`
3. 打 git tag `vX.Y`，并在下方索引表把状态改成「已发布」

### R10 交给其他 Agent 实现时，用版本目录里的 `实现提示词.md`

把某个版本外包给另一个 Agent（DevEco 内置 Agent、别的 AI Coding Agent）时：

- **先在该版本目录写 `实现提示词.md`**，再让对方干活 —— 不要临场口述需求
- 提示词必须**自包含**：对方看不到我们的历史对话，要自带环境事实（API 24 / ArkTS / 包名）、必读文件清单、**防编造约束**
- **必写的一条**：禁止凭记忆编造 HarmonyOS API；查不到就用报告列出来，不许用猜测实现覆盖
- 版本需求文档有实质变更时，同步修订该版本的提示词（否则双方口径会漂）

模板见 `v0.1/实现提示词.md`（v0.1 已有一份，可直接照它的结构改）。

> 提示词**按「可独立交付的一段工作」拆**，不强制一个版本只有一份：
> 补丁（`实现提示词_2.7次级页面返回.md`）与前置关卡（`实现提示词_M0.5spike.md`）各自成文，
> 因为它们的验收方式与风险等级都和主体不同。

## 3. 需求文档模板（每个版本目录一份）

```markdown
# vX.Y 需求文档

> 状态：规划中 / 开发中 / 已发布
> 对应里程碑：M? / M?

## 1. 版本定位
（一句话：这个版本交付什么、交付给谁用）

## 2. 完成判定
（一句话，可验收。写完能回答"这个版本做完没有"）

## 3. 需求清单
（从需求池分配过来的条目，写明来源章节与验收点）

## 4. 明确不做
（本版本排除什么、为什么）

## 5. 技术约束与依赖
（链接到 docs/harmonyos/ 与已定决策，不复制结论）

## 6. 验收记录
（发布后填：真机实测结果、遗留问题、下一步）
```

## 5. 与其他文档的分工（别写错地方）

| 文档 | 回答什么问题 |
| --- | --- |
| `docs/requirements_backlog.md` | 我们**想做**什么（未分配的需求池） |
| `docs/releases/vX.Y/需求文档.md` | 这个版本**承诺交付**什么 |
| `docs/mvp_design.md` | 整体**怎么做**、按什么顺序做（里程碑） |
| `docs/harmonyos/` | 鸿蒙的**行为结论**（技术真源） |
| `docs/open_questions.md` | 哪些**已定**、哪些**待拍板** |
| `AGENTS.md` | 在这个仓库里**怎么干活**（硬约束、命令、坑） |
