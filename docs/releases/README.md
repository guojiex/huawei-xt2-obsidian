# 版本化开发规则（`docs/releases/`）

> **范围**：v0.6 小艺本地笔记操作由用户确认完成，证据见验收记录。2026-11-06 用户另行授权 v1.16 小艺 Wiki 本地后端继续实现、不改 UI；平台集成仍关闭。历史排期与进度不在本文档维护，需要时查 Git 历史。

> **2026-11-01 真机验收责任**：API24 / XT2 真机验收由用户手动执行，Codex 不连接 XT2、不安装或操作真机验收包。自动测试、构建和模拟器结果按各自类别记录，不能代替真机证据；用户提供实测结果后再回填结论。

> 这里是**版本交付档案**的唯一存放处。
> **每一个版本 = 一个目录，目录名就是版本号；每个版本目录里必须有需求文档。**
>
> 应用市场准备状态与材料缺口见 [上架准备清单](上架准备清单.md)；该清单是内部盘点，不代表已提交。

## 0. 一句话规则

> **测试边界**：不在模拟器上主动制造崩溃、强杀进程或写入中断。恢复与失败处理使用单测，通过可控时钟、存储失败注入和重新创建服务实例验证；模拟器仅验证正常编辑、保存、切换和重新打开。单测不代表真实进程中断或设备级原子性已验证。

**任何落码，都必须能对应到某个版本目录里的某条需求。**
需求池里没分配进版本的需求 = 不许开工；版本目录里没有的需求 = 不许顺手做。

> **质量保障资产豁免（2026-11-07 用户决定）**：自动化测试（含 UI 测试基建与用例）、
> 构建脚本、文档维护属于质量保障 / 工程基建，**不占用版本需求、不单独立版本目录**；
> 但新增 UI 用例必须对应 [模拟器回归用例](../testing/模拟器回归用例.md) 并登记进
> [UI自动化测试.md](../testing/UI自动化测试.md)。产品功能改动仍按本节规则走版本需求。

## 2. 规则（R1–R9）

### R1 一个版本一个目录，目录名即版本号

格式 `v<MAJOR>.<MINOR>`（两位制，如 `v0.1`、`v1.0`）。
⚠️ 目录名是**内部迭代编号**；`app.json5` 的 `versionName` **不与它对应**（2026-11-09 纠正）：
`versionName` 跟随**对外版本**——真源是 `changelog.json` 的 `version` 字段（用户在关于页看到的版本），
一个对外版本可跨多个内部迭代；`versionCode` 单调递增。

### R2 版本号语义

| 变更 | 版本怎么动 |
| --- | --- |
| MVP 完结前的每个阶段 | `0.x` 递增（`v0.1` → `v0.2` → `v0.3`） |
| MVP 完结（对外可用） | `v1.0` |
| 新增功能、向后兼容 | `+MINOR` |
| 改数据结构 / 库目录布局 / 破坏兼容 | `+MAJOR` |
| 只修 bug、不动功能 | 就地为当前版本补 `验收记录.md`，**不开新版本** |

### R3 先有需求文档，再落码

开新版本 = 先建目录 + 先写 `需求文档.md`，**写完之后才允许动手写代码**。
严禁「先写一堆代码，回头补一份文档」——那样文档永远对不上实际交付。

### R4 需求只能从需求池分配进来

版本目录**不许凭空新增需求**。流程固定为：

```
docs/requirements_backlog.md（需求池：所有想做的）
        │  挑选 + 排优先级
        ▼
docs/releases/vX.Y/需求文档.md（本版本承诺交付的）
        │  落码
        ▼
验收 → 发布 → 冻结
```

新冒出来的需求：**先回池子登记**，再决定塞进当前版本还是下一个。
（当前版本还没发布且改动很小时可以吸收，但必须同步更新需求文档，不 silently 加。）

### R5 结论只准链接，不准复制

版本文档里涉及的三类内容**一律链接，不复制**：

- 鸿蒙行为结论 → `docs/harmonyos/api_notes.md`
- 已定决策 → `docs/open_questions.md` 的已定决策总表
- 整体架构与里程碑 → `docs/mvp_design.md`

理由同知识库铁律：结论会被推翻，抄一份就漏改一处。

### R6 每个版本都要写「明确不做」

这是防范围膨胀的关键一节。写清楚本版本**不做什么、为什么不做**，
比写"要做什么"更能防止中途加塞。

### R7 版本发布后冻结

版本发布（打 tag）后：

- `需求文档.md` **不再改**（它是对外承诺的历史记录）
- 遗留问题与新需求 → 写进 `验收记录.md` 或回流需求池，**进下一个版本**
- 要改已发布版本的需求 = 承认计划失败，先写清楚原因再改（保留痕迹）

### R8 版本与里程碑（M 编号）的映射

> **2026-11-02 用户决定**：版本号只作编号，优先级只看 [实施总清单](实施总清单.md)，不从版本号或历史 M 编号推断开发顺序。发布状态仍以 tag 与验收记录核对，决定速查见 [Q10](../open_questions.md#q10-版本号与优先级--已决定m-阶段拆分约束已取消2026-11-05)。

每个版本需求文档仍写明包含哪些 M 阶段。历史规则要求一个 M 阶段不得跨版本拆分；**2026-11-05 用户决定取消该约束**，版本可按需求编号拆分，见 Q10。此前以 M 编号表达开发顺序的描述不再作为排期依据。

### R9 发布动作

发布一个版本 = 四件事：

1. 补齐该版本目录的验收记录（`需求文档.md` 第 6 节）
2. 同步 `app.json5` 的 `versionName` / `versionCode`
3. 更新 `changelog.json` 对应版本记录、日期和状态，运行 `python3 tools/generators/build_changelog.py`；`--check` 必须通过
4. 打 git tag `vX.Y`，并在下方索引表把状态改成「已发布」

### ~~R10 交给其他 Agent 实现时，用版本目录里的 `实现提示词.md`~~ —— 已废止（2026-11-02）

废止理由：实现提示词是需求文档的第二份副本，需求一变就要同步两处，历史上已经出现口径漂移；
而它真正不可替代的那几条（自包含环境事实、禁编造 API）**本来就该写在需求文档里**。

现行做法：**外包某个版本 = 直接给该版本的 `需求文档.md`**。
- 需求文档必须自包含到能被别人接手：环境事实（API 24 / ArkTS / 包名）、范围与**明确不做**、完成判定；
- 缺哪条就补进需求文档，**不另开提示词文件**；
- 「禁止凭记忆编造 HarmonyOS API，查不到就列进报告」这条继续有效，出处是 `AGENTS.md` 硬约束 18 与 `docs/harmonyos/api_notes.md`。

## 3. 需求文档模板（每个版本目录一份）

```markdown
# vX.Y 需求文档

> 状态：规划中 / 开发中 / 已发布
> 对应里程碑：M? / M?

## 1. 版本定位
（一句话：这个版本交付什么、交付给谁用）

## 2. 完成判定
（一句话，可验收。写完能回答"这个版本做完没有"）

## 3. 需求清单
（从需求池分配过来的条目，写明来源章节与验收点）

## 4. 明确不做
（本版本排除什么、为什么）

## 5. 技术约束与依赖
（链接到 docs/harmonyos/ 与已定决策，不复制结论）

## 6. 验收记录
（发布后填：真机实测结果、遗留问题、下一步）
```
