### 6.2 ⚠️ 疑似缺陷 #1：长图预览顶部黑带（真机定性中）

- **现象**（x86 模拟器，3 次生成复现，浅色×2 + 深色×1）：长图分享预览图顶部出现纯黑横带（约占全高 30-35%，边界平直），高度逐次不同；信息行正常显示尺寸与主题，预览整体未报错。
- **定位**：黑带在生成产物 JPEG 本体内，非 UI 遮挡（布局树 Image 节点 `[91,916][917,2002]`，黑块横跨组件全宽）。ShareDbg 日志 `initial sh=710 vh=710 vw=360 n=1`：单段截图，`getComponentSnapshot(waitUntilRenderFinished)`（ShareFlowPanel.ets:590）返回的 PixelMap 顶部未合成 —— 疑似隐藏捕获层 Web 首帧纹理未就绪即截图，时序竞争。
- **检测盲区**：53.10 旧帧校验只比对「本段 vs 上一段」，首段 prevBuffer=null 无内容校验，黑帧静默通过。
- **历史对照**：v1.53（2026-11-11）同模拟器 19 段长图成功；其后 6dea075（同源渲染）/ 44787b4（首帧分块冷启优化）动过渲染链路，不能排除回归。
- **定性状态**：x86 证据不外推（AGENTS.md）；用户在 XT2 真机手测中。若真机复现 → 进 85.3 修复（首段黑帧检测 + 重试，参照 53.10 模式）；若仅模拟器 → 登记为模拟器限制，不占 85.3。

### 6.3 85.3 缺陷 #2：删除笔记误报「删除失败」（根因闭环，修复已落码，2026-11-20）

- **现象**（XT2 真机，拒审 2.1.2.1 引用面）：删除笔记弹
  `删除失败 code=-1 message=Init error. The WebviewController must be associated with a Web compo`（17100001），
  **但笔记实际已入回收站**——事务成功、视图清空一步失败被误报为整体失败。
  2026-11-19 19:51:24 / 19:59:26 两次真机失败（审核场景复现）；同日及次日三轮复现均成功。
- **根因**（排除法 + 归档日志交叉定位，详见 [api_notes AK 组](../../harmonyos/api_notes.md)）：
  启动瞬态（早期 `px2vp` 换算异常）→ 初始断点错误 → `windowSizeChange` 纠正 →
  `NoteWorkspaceShell` 单屏分支翻转 → 编辑器 Web 结构性销毁重建（旧 web 1-4 → 新 5-8）→
  `EditorBridge` 持旧 WebviewController → 删除后 `setContent('')` 抛 17100001 →
  `toastRegistryError` 把已成功的删除误报成失败（`code=-1` 因该异常无数字 code 字段）。
  触发时段 hilog 归档已被系统配额清理，瞬态细节不可恢复；「渲染服务携带 NWebId」假说被
  排除（未 bind 的桥静默跳过，不可能抛 17100001）。
- **修复**（两层，2026-11-20 落码）：
  1. **根治**：`EditorWebView` 补 `aboutToDisappear` + `boundImpl` + `EditorBridge.unbind`
     （所有权校验），bind 重放条件改 `impl === undefined`——对齐 `PreviewWebView` 已验证模式，
     重挂后新实例重放内容，stale controller 不复存在。
  2. **防御**（审核缺陷直接对策）：`doTrashFile` / `doDeletePath` 把「清空视图」从删除事务
     隔离（事务成功 → refreshFileTree / 撤销条先行），清空失败仅 `logPaneClearFailure` 记日志——
     `moveToTrash` 成功后不存在任何路径能再弹「删除失败」。
- **验证**（修复版 x86_64，Windows 模拟器，1008×2232）：
  - 标准删除回归 ✅：r5.md 滑删 → 确认 → `TrashService 项目已移入回收站` + 撤销条显示 +
    左栏清空 + **无错误弹窗**；
  - 回收站恢复 ✅：`回收站项目已恢复`，文件树还原；
  - remount 场景：模拟器无折叠/旋转能力，无法确定性触发分支翻转；修复正确性依据为
    根治（对齐 PreviewWebView 已验证同型实现）+ 防御（`moveToTrash` 成功后不存在再弹
    「删除失败」的代码路径），x86 证据不外推 API24 / XT2；
  - 构建：arm64-v8a 与 x86_64 双架构 BUILD SUCCESSFUL；arkts_check 无新增问题。
- **涉及文件**：`components/EditorWebView.ets`（unbind/boundImpl/aboutToDisappear/bind 重放）、
  `pages/Index.ets`（doTrashFile / doDeletePath 事务隔离 + logPaneClearFailure，
  删除 DBGSTACK 临时插桩）。

### 6.4 85.1 缺陷 #3：快切键盘态结果列表塌缩（修复已落码，2026-11-20）

- **现象**（x86_64 模拟器，单屏 1008×2232）：快切面板点搜索框弹键盘后，弹窗塌缩成
  「标题 + 搜索框」（实测 shell 高 396px），scope 分段（当前库/全部库）、模式行、表头、
  **结果列表全部从布局树消失**（layoutWeight 压为 0 高）——输入 `readme` 时用户看不到任何
  结果行，核心搜索流程被阻断；收起键盘后结果正常（README 命中）。
- **根因**（算术交叉验证）：模拟器 IME 走 WM 层窗口收矮——页面容器已收至键盘上缘
  （`windowSizeChange` → `windowHeightVp` ≈ 454vp，**已不含键盘区**），同时
  `avoidAreaChange` 仍发布 903px 的 `keyboardInsetPx`。`UtilityDialogShell.dialogMaxHeight`
  对内联宿主把 `keyboardInsetVp`（301vp）从**已收窄的** `windowHeightVp` 里再扣一次：
  (454−301)×0.86 ≈ 132vp = 396px，与实测 shell 高度完全吻合 → 内容列 layoutWeight(1)
  分到 0 剩余空间 → 列表压没。v1.73 引入该扣减针对的是 **CustomDialog** 宿主
  （页面级避让对 CustomDialog 不生效，api_notes L-21「弹窗自成一系」），而快切是页面
  Stack 内的**内联**宿主——扣减条件与宿主类型不匹配。
- **修复**（2026-11-20 落码）：`UtilityDialogShell` 新增 `layoutAvoidsKeyboard` 参数
  （默认 false，19 个 CustomDialog 调用方行为不变），为 true 时 `dialogMaxHeight`
  跳过 `keyboardInsetVp` 扣减；唯一内联调用方 `QuickSwitcher` 传 true。
- **验证**（修复版 x86_64，Windows 模拟器，1008×2232，键盘弹起输入 `readme`）✅：
  搜索框（`readme` + 光标）/ 当前库·全部库分段 / 文件名与路径·正文 / 搜索结果计数 1 /
  **README 结果行（含「打开」）全部可见且位于键盘上方**（结果行 y=1067-1121，键盘顶 1348；
  对照修复前：同场景仅剩 396px 塌缩条，列表节点全部从布局树消失）。
  证据：wz_qswfix.jpeg / layout_wz30.json。
- **涉及文件**：`components/UtilityDialogShell.ets`（layoutAvoidsKeyboard + 扣减条件）、
  `components/QuickSwitcher.ets`（传参）。
- **关联观察（不在本缺陷范围）**：模拟器上 CustomDialog 宿主（如 Git 导入弹窗）键盘态
  同样存在双扣（窗口收窄 + inset 扣减），短弹窗（自然高 < 396px）不可见影响，实测 Git
  导入全流程（远程/分支/令牌/提交）可用；真机行为另见 api_notes AL1。
