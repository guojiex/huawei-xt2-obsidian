# v1.9 单篇笔记图片分享改为一张连续长图

状态：需求与实现已落地；长图定向测试、全仓 Node 回归、生成器检查和混合工作树 HAP 构建通过。模拟器、API24 / XT2 与接收端未验，未完成设备验收、未发布。本版是独立体验优化，不改变 v1.7 主线和 v1.8 专注模式修复的排期。

## 1. 来源与范围

来源：需求池「单篇笔记图片分享输出为一张连续长图」，由用户于 2026-11-01 提出。

仅调整用户选择**单篇 Markdown 笔记 → 图片**时的图片生成与分享结果。v0.8 原需求曾要求长文按输出限制分图；本版将当前单篇图片交付规则改为一张连续长图，保留其余图片 / Markdown / ZIP / 文本格式、文件夹与知识库分享范围。

## 2. 需求清单

| 编号 | 要求 |
| --- | --- |
| 19.1 | 按当前编辑器内容快照渲染整篇笔记，保留现有预览能力及库内本地图片；不得因视口高度把交付物拆成多张图片，也不得静默截断末尾内容。 |
| 19.2 | 预览中明确显示一张完整长图；用户确认后，Share Kit 只接收一个 JPEG 图片记录。取消预览不分享文件，返回格式选择仍可选择 Markdown / ZIP 或其他现有格式。 |
| 19.3 | 捕获可按屏幕视口分段，但分段必须在应用内按原顺序拼成一张 PixelMap / JPEG。单张 PixelMap 控制在 96 MiB 应用预算内，超出时对整张图等比缩小并在预览提示；缩小后宽度低于 640 px 时说明无法生成清晰长图，并建议改用 Markdown / ZIP。不得拆页或丢内容。尺寸依据与 API 起始版本见 [API 笔记 O3](../../harmonyos/api_notes.md#o3-单篇分享长图像素合成与尺寸限制)。 |
| 19.4 | 长图生成仅使用当前笔记快照与当前库可读的本地图片；生成失败或取消时清理本次未完成临时目录，不修改源 Markdown、不记录笔记内容。生成进度可显示内部合成分段进度，但预览与系统交接始终为单张图片。 |
| 19.5 | v2 原型与说明明确表达「单张连续长图」；保留深浅主题、三形态分享入口、取消 / 失败状态和现有 token 规范。设计稿不替代原生及接收端验收。 |

## 3. 完成判定

- 长度跨越多个预览视口的笔记，完整内容合成在一个 JPEG 中；文件只有一个图片 URI，系统分享只有一个 JPEG record。
- 长图预览呈现一张可纵向浏览的图片，并标明「1 张长图」。
- 正常尺寸不缩放；超出像素预算时整图按相同比例缩小；低于最小宽度、内存分配或编码失败时给出原因和 Markdown / ZIP 替代方式，不拆分、不截断。
- 自动验证、HAP 构建、API26 模拟器、API24 / XT2 和目标应用接收分别记录；面板打开不能代替接收人读取证据。

## 4. 明确不做

- 文件夹或整个知识库生成长图。
- 图片水印、社媒尺寸模板、上传托管、自动发送。
- 扩展 Markdown 语法渲染；公式、Mermaid 等沿用现有预览能力。
- 修改 v0.8 已有验收记录或把本地代码状态写成设备验收 / 发布完成。

## 5. 技术约束

- 只使用 API ≤24 的 HarmonyOS 接口；实现依据、PixelMap 128 MB SDK 上限和 API 起始版本集中记录于 [API 笔记 O3](../../harmonyos/api_notes.md#o3-单篇分享长图像素合成与尺寸限制)。API 声明不代表 API24 / XT2 运行时行为已验。
- 捕获仍采用满足 Web 组件尺寸约束的视口级快照；将 BGRA 像素行写入同一目标 PixelMap 后再编码 JPEG。所有尺寸、stride、裁切与末段高度必须校验。
- 临时文件继续使用当前 `VaultRegistry.sharePath` 私有缓存与过期清理策略；不拼接沙箱绝对路径，不访问库外图片。
