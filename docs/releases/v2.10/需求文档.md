# v2.10 需求文档 —— 应用备份排除 .git 与恢复后重新关联远端

> 状态：已交付（2026-11-24），设备侧验收待 XT2 真机执行
> 来源：需求池 C 节「应用备份排除 .git 与恢复后重新关联远端」。用户 2026-11-24 提出：应用备份把每个 Git 库的 `.git` 全量打包，体积随提交历史失控（大库备份动辄翻倍）；拍板**备份无条件排除所有 `.git`**，代价（恢复后本地历史丢失）由配套的「重新关联远端」承接——远端才是笔记内容的真源。

## 1. 版本定位

现状（v1.66 起）：`ApplicationBackupService.copyTree` 会把 `.git` 目录完整复制进备份（凭据文件被 `isGitConfigFile` / `isGitCredentialFile` 清洗，但对象库 / 历史全保留）。恢复侧 `restoreFromBackup` 只回填笔记与注册表元数据（remote / branch / pushBranch），Git 令牌要求重填（AssetStoreKit 不入包）。

问题：①`.git` 体积不可控，备份 / 恢复时长与 ZIP 体积被历史大小绑架（v2.8 提高上限后更明显）；②`.git` 属远端可重建数据，备份它收益低；③一旦排除 `.git`，恢复出的 Git 库缺 `.git`，同步弹窗的 `repositoryState` 会失败，用户没有任何自救通道。

本版两件事：**备份无条件排除 `.git`**（含旧备份含 `.git` 的恢复兼容）+ **恢复后缺 `.git` 的库可在同步弹窗一键「重新关联远端」**（reattach：本地重建 `.git` 并接回远端，不重 clone、不动工作区文件）。

## 2. 完成判定

- 新备份包内**任何路径都不含 `.git`**（含子目录）；恢复新备份后 Git 库笔记正常打开，同步弹窗识别缺 `.git` 并展示「重新关联远端」卡片。
- 填远端地址（默认库注册的 remote）+ 凭据后点「重新关联」：成功后弹窗回到正常同步态（分支 = 库注册分支、ahead 显示本地改动）；本地笔记文件一个字节不动。
- 失败（网络 / 认证 / 远端缺分支）给出可读错误，可原地重试；中断重试幂等（半成品 `.git` 续跑而非报错）。
- 已有可用 `.git` 的库不出现该卡片；reattach 对已有提交的库显式拒绝。
- 定向测试（native fixture + ArkTS 行为级）全过、相关回归零新增失败；`arkts_check` 零错误 + 双 ABI native 编译通过 + 签名 HAP 构建通过。

## 3. 需求清单

来源：[需求池 C 节](../../requirements_backlog.md)

### 10.1 备份无条件排除 `.git`

- `ApplicationBackupService.copyTree` 目录分支：名等于 `.git` 的目录（任意层级）一律跳过，不复制、不报错；同时跳过名为 `.git` 的同名文件（worktree/文件形态）。子目录里的嵌套 `.git` 同样排除（子模块 / 手误场景）。
- 凭据清洗三件套（`isGitConfigFile` / `isGitCredentialFile` / `sanitizeGitConfig`）与 `copyTree` 的 `scrubGitConfig` 参数随 `.git` 整体排除而失去意义，一并删除（trash / drafts / agent 等所有 copyTree 调用点同步去掉实参）。
- **恢复兼容**：旧版本备份（含 `.git`）恢复路径零改动——恢复时 `.git` 照常落盘（copyTree 只约束备份方向），恢复后是可用仓库，不触发 reattach。
- 用户可见文案同步（见 10.4）。

### 10.2 native `reattach` 操作

- `gitAction` 的 `operation` 增加 `'reattach'`；`Git2ActionOptions` 增加 `remoteUrl?: string`（两份 `Index.d.ts` 同步）。
- 入参约束：`remoteUrl` 在 reattach 时必填，须为 `http(s)://` 且拒绝内嵌凭据（复用 `url_has_embedded_credentials`），≤8192 字节；`targetBranch` 必填（取库注册的 clone 分支，非 pushBranch）。
- 执行语义（幂等，全程持 `g_clone_mutex`）：
  1. `git_repository_open_ext` 失败 → `git_repository_init`（bare=0）；open 成功且 HEAD unborn → 续跑（重试路径）；open 成功且 HEAD 已有提交 → 拒绝：「已存在可用的 Git 仓库，无需重新关联」；
  2. origin：`git_remote_lookup` 失败则 `git_remote_create`，已存在则 `git_remote_set_url` 指向新 `remoteUrl`；
  3. 复用 `fetch_target_branch`：远端必须存在 `refs/heads/<targetBranch>`，缺失报「远端没有分支 X」；fetch 进 `refs/remotes/origin/<targetBranch>`（进度走 `PROGRESS_PHASE_FETCH`）；
  4. `git_branch_create`（force=1，幂等）在 `refs/heads/<targetBranch>` 指向 `refs/remotes/origin/<targetBranch>`；`git_repository_set_head("refs/heads/<targetBranch>")`；
  5. index 对齐：**不用 `git_reset`**——显式 `git_repository_index` + 取 HEAD commit 树 `git_index_read_tree` + `git_index_write`，让 index = HEAD 树、工作区文件不动（本地笔记对远端表现为未提交改动）。
- 失败保留已初始化的 `.git`（不在 C 侧写递归删除），网络 / 认证 / 分支缺失失败后原地重试幂等。
- 认证复用 `acquire_credentials`（username/password 或 bearer）；取消机制复用 clone 的取消标志。

### 10.3 同步弹窗「重新关联远端」UI

- `GitSyncDialog` 在 `refreshLocalStatus`（`repositoryState`）报「仓库打不开」类错误时，用 `fileIo.accessSync(vaultDir + '/.git')` 复核：`.git` 缺失 → 进入 `missingGit` 卡片态（替代原裸报错）。
- 卡片：说明文案（备份不含 Git 历史，重新关联即可从远端接回，本地笔记不受影响）+ 远端地址输入（默认 `entry.remote`，可改）+ 凭据编辑器（复用现有 credential editor，含 bearer / 用户名密码两模式）+「重新关联」按钮。
- 执行：调 `gitAction({ operation: 'reattach', ... })`，进度与既有 fetch 进度展示一致；成功后刷新 `repositoryState` 回正常同步态；失败错误就地展示，可重试。
- **不出现条件**：`.git` 存在（哪怕损坏）或库非 Git 库（`entry.remote` 为空且非 git 类型）时维持现状。

## 4. 明确不做（本版）

- **不做重 clone**：reattach 不下载全量历史到工作区（fetch 走远端跟踪分支即可），不提供「重新克隆」按钮（已有 Git 库导入流程可另走）。
- **不做合并 / 迁移本地历史**：reattach 只接远端；用户若在别处有本地 `.git` 想并回来，属 PC 侧 git 操作，不在端内做。
- **不做 `.git` 损坏修复**：`.git` 存在但损坏（open 失败但 access 成功）维持现状裸报错，不自动删 `.git` 转 reattach（删用户数据需显式确认，本版不引入该交互）。
- **不做自动 reattach**：不监听恢复完成自动触发，用户在同步弹窗手动发起。
- **不改 v2.8 ZIP 上限**：排除 `.git` 后备份体积天然回落，上限维持 10000 条目 / 1GB / 128MB。
- **原型不做 reattach 卡片**：原型无备份恢复流程可演示，仅同步既有备份文案三处。

## 5. 红线

- **本地笔记文件零改动**：reattach 全程不 checkout / 不 reset 工作区（10.2 第 5 步显式避开 `git_reset`），用户笔记内容与 mtime 不受影响。
- 失败不清空、不删除用户任何数据；半成品 `.git` 保留供重试。
- `remoteUrl` 拒绝内嵌凭据（与 clone 同口径），凭据只走参数通道。
- 笔记内容、路径、远端地址不进埋点（硬约束 16）。
- 备份方向排除 `.git`，恢复方向对旧备份保持兼容——不写「恢复时删 `.git`」逻辑。
