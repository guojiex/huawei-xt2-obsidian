# v1.40 设计说明 —— Markdown 真源与 RDB 搜索索引双写

> 状态：2026-11-07 设计稿，尚未实现。范围与完成判定以 [需求文档](需求文档.md) 为准；已定产品取舍见 [决策总表](../../open_questions.md)，平台能力只引用 [api_notes AC 组](../../harmonyos/api_notes.md#ac-组rdb-全文索引2026-11-07-官方文档与-sdk-声明核对)。

## 1. 数据归属与接入边界

```text
编辑 / 创建 / 改名 / 回收站 / 小艺单篇工具
                |
                v
        现有 NoteService / VaultAccess
                |
                v
        Markdown 文件提交成功 --------> 保存成功
                |
                v
         RDB 待处理任务 / 增量索引
                |
                v
        App 搜索 / 跨库搜索 / SearchNotes
```

Markdown 是唯一真源；RDB 中保留当前已索引版本的正文副本和分词索引，两者短时间内可以不同。数据库只服务搜索，不参与编辑载入、正式保存、预览、Git 或导出。数据库中的正文不能用于恢复或覆盖 Markdown。

索引逻辑继续由 `FullTextSearchService` 承担，共用现有保存 / 删除 / 恢复 / 路径变更通知；`CrossVaultSearchService` 改为逐库查询持久索引，不再为非当前库临时建内存索引。设备数据库操作可作为该服务的存储适配边界，测试注入替身；不新增通用 Repository / 插件框架。小艺 `SearchNotes` 复用同一路径，`QueryNotes` 和名称搜索不改走 FTS。

## 2. 持久数据

使用一个 App 私有 `search.db`，交给 RDB 按 Context 管理物理位置，不能硬编码沙箱路径。所有笔记相关查询强制带 `vaultKey`；切库只切查询范围，不删库、不清空表。数据库、WAL 等辅助文件不进入 `.md` 库、分享 ZIP 或 Git。

| 逻辑表 | 主要数据 | 作用 |
| --- | --- | --- |
| `search_meta` | schema 版本、分词配置版本 | 识别缓存是否可复用；不含用户正文 |
| `search_vaults` | `vaultKey`、初始化完成状态、最近完整对账时间、扫描代次 | 逐库初始化、对账与错误隔离；运行时每次重新检查访问资格 |
| `search_documents` | `docId`、`vaultKey`、库内相对路径、大小、mtime、正文 hash、索引代次 | `(vaultKey, path)` 唯一；hash 取实际提交到索引的原文，不以 mtime 代替版本 |
| `search_fts` | `rowid=docId`、标题、Markdown 正文 | 标准 FTS 内容表，正文只在该表保存一份，再加分词倒排数据；不在元信息表重复存正文 |
| `search_pending` | `vaultKey`、路径、任务代次 | 持久标记需要重读源文件的路径；不保存待重放的旧正文 |

正文初版保存原始 Markdown，不先增加渲染 / 清洗依赖；搜索片段可以据其生成，但展示前要读源文件验证，见 §6。数据库是可重建的持久派生数据，不是长期唯一资产；不是系统临时目录中的即用即删文件。建库采用平台内置加密配置，版本声明和运行边界见 AC 组，实际配置需实施时按 API24 SDK 复核。

## 3. 加载、构建与对账

| 时机 | 行为 | 是否全库重新分词 |
| --- | --- | --- |
| 首次对某库做正文搜索 | 打开数据库、分批遍历并建立该库正文索引；先保持名称搜索和笔记操作可用 | 是，该库尚无索引 |
| 正常重启后首次搜索某库 | 直接复用已有 RDB；后台恢复 pending，并对该库分批做一次完整正文 hash 对账 | 仅 hash 变化、新增的文件 |
| 同进程再次搜索 / 切回已核对库 | 复用索引，处理新增 pending；普通切库不触发全量重建 | 否 |
| App 内文件提交成功 | 合并该路径任务，更新最新版本；不为每个按键建任务 | 仅受影响文件 |
| 恢复前台、外部变更或文件刷新 | 元信息快速检查；无法确定期间变化或外部改动时，安排完整 hash 对账 | 仅实际变化文件 |
| schema / 分词配置不兼容，或库索引损坏 | 使相应缓存失效，分批重建；重建中不返回该失效版本 | 是，明确的恢复 / 升级路径 |

**重启复用不等于零读取。** 当前 `VaultFileStat.mtimeSec` 只有秒精度，同秒等长修改会绕过 `mtime + size` 判断。因此本版基线是每库每进程首次使用时，在后台读取正文核对 hash；相同内容不再分词或写数据库。持久索引让首次查询可以复用已有结果，并节省全量建表 / 分词 / 索引写入，但仍有后台文件读取成本。以后若要省去该读取，须有覆盖外部修改和异常退出的可靠变化证据后另行优化。

扫描分批让出执行线程，合并同库重复请求；只在用户实际查询库或已打开库有变更时工作，不启动全部库预索引。跨库搜索仍按库逐一推进，不同时全库读入内存。分批大小与调度策略实施时测量确定，不把开发机耗时当设备指标。

仅完成了一次扫描不代表获得了外部目录的原子快照。扫描期间的 App 内修改按任务代次继续处理；外部应用仍可在扫描后修改文件，对账时间只是可观察的校验点。

## 4. 单次写入与失败补偿

尚未初始化且从未进行正文搜索的库，不因普通文件保存主动建全文索引；首次搜索从当前文件建立完整基线。以下增量流程针对已经建立或正在建立索引的库。

1. 捕获稳定库身份和路径，经现有访问层提交 Markdown 或文件操作；不为索引预写而延迟文件提交。
2. 文件失败时不发布拟写入的索引正文。文件成功即确定原有保存结果，然后为受影响路径登记带代次的 pending；这两步之间的进程中断由下次完整 hash 对账补齐。
3. 索引任务异步从源文件重读当前状态，不使用可能已经过期的编辑缓冲或排队正文。
4. 在一个 RDB 事务里更新元信息、FTS 和对应 pending。只允许处理匹配代次的任务；旧任务不能删除新 pending 或覆盖较新结果。数据库事务不包含 Markdown 写入。
5. 索引失败保留 pending，当前会话标记索引待更新并合并重试；不回滚文件，也不把文件保存成功改成失败。RDB 连 pending 都写不进去时，文件保存仍成功，该库搜索转为不可用 / 待恢复；下次成功打开数据库后的完整 hash 对账补齐断点。

索引恢复只重新读取现状：同路径发生连续保存、中途删除或改名时，不按旧操作列表回放旧正文。进程中断发生在“文件成功、数据库未提交”的间隙，由 pending 和下次对账恢复；即使数据库事务成功，也不会回写文件。

每库任务顺序只约束该进程内的调度。若多个入口运行于不同进程，须通过 RDB 事务校验任务代次并防止旧结果提交，必要时重读后重试；不把内存锁宣称为跨进程或跨应用的 Markdown 写保护。

## 5. 各种文件操作

| 文件操作 | 索引处理 |
| --- | --- |
| 新建 / 保存 | 成功后读取当前文件，更新正文 hash、标题和 FTS |
| 改名 / 移动 | 原、新路径都登记；以实际目录核对新旧存在状态；文件夹操作逐项更新后代，不创建正文副本文件 |
| 移入回收站 / 永久删除 | 文件操作成功后删除正文与 FTS 条目；`.trash` 等隐藏目录不入索引 |
| 从回收站恢复 | 以最终恢复路径读取内容并索引，不假设恢复回原名称 |
| 小艺单篇编辑 / 撤销 | 沿现有 NoteService 接口通知，不能私下直接维护另一套 RDB 数据 |
| ZIP / Git / 本地库导入 | 完成库登记后标为未初始化，第一次正文搜索时建立索引；不索引未登记 staging 目录 |
| 外部应用修改 | 通过统一访问层轮询 / 对账，不假设系统提供可靠变更事件，依据见 [api_notes T8](../../harmonyos/api_notes.md) |
| 删除库 / 应用重置 | 清理对应正文、FTS、pending 和元信息；清理失败不使已移除库重新可搜索，重开后按注册表清理孤儿索引 |

扫描必须区分“完整看到了全部文件”与“被上限截断 / 部分读取失败”。当前访问层存在遍历节点数和深度上限，实施时需通过统一访问层补充完整性标记；没有完整清单时不能把未出现的路径当作已删除。可确认不存在的路径才可清除缓存；授权失效或读取错误不是文件不存在。

## 6. 搜索语义与结果状态

正文搜索按原生中文分词后的关键词处理，普通输入按文本转义后绑定查询参数，不直接开放任意 FTS 操作符。接受与旧字符子串结果不同；不为兼容旧命中额外跑内存引擎或逐篇扫描。分词配置优先系统自研分词器的短词模式，适配与已知限制只见 AC 组；不支持所需分词能力时明确报告正文搜索不可用，名称搜索不受影响。

元信息表以 `vaultKey` 限定候选；保留现有调用方结果的路径与片段字段。App / 小艺 / 跨库调用方共用索引状态，而不是分别构建缓存。名称优先及稳定路径排序先沿现有契约，不借迁移增加相关度排序产品需求。

内部结果须同时携带 `indexState`（`building / checking / ready / error`）、`indexComplete` 和对账时间：

- 新库构建中可返回已索引部分，但不能把它表达为完整零结果；调用方沿现有进度 / 错误通路处理。
- 已有库后台对账时可以返回缓存候选，明确 `indexComplete=false`；新写或外部新增的笔记在对账完成前可能尚未出现。
- 候选返回前检查库当前可访问，并重读候选文件验证 hash。文件消失、内容已变或不可读时，不返回旧正文片段，将可恢复项加入更新队列；这只能排除陈旧命中，不能弥补索引未更新导致的漏检。
- 本地 pending 处理完且该轮完整对账成功，才标本轮完整；`ready` 不表示已阻止外部后续修改。
- 数据库失败与权限错误不是空结果；不同库独立失败，跨库搜索沿既有跳过 / 不完整语义处理。
- 小艺工具新增状态须单独计算 6000 UTF-16 输出预算，`truncated` 继续只表达返回预算裁剪。未登记平台意图的边界保持。

## 7. 隐私、回收与回退

本版明确允许本地正文缓存。数据库正文按与笔记相同的敏感等级保护，不写日志、不进诊断复制、分享、Git 或埋点；不把路径、标题和 hash 当可上报的无敏感元信息。

外部授权失效时排除该库全部缓存结果，不得借数据库继续展示撤销访问后的正文；恢复授权后重新对账。删除注册库、重置或显式重建时同步清理相应缓存；数据库释放磁盘页和删除残留的边界需按平台行为实测，不承诺安全擦除。搜索缓存无需作为笔记备份来源。

RDB 损坏时只重建派生索引，不能清用户库、草稿、回收站或操作前像。单库索引问题只失效该库；如果整个 `search.db` 无法恢复，则重新创建搜索数据库，各注册库首次查询时再分别重建，不假称其他库缓存仍可保留。旧版本代码若仍使用内存搜索，Markdown 仍可独立使用；本版不新增运行时双引擎切换开关。

## 8. 实施顺序与验证

1. 先做原生 RDB 适配与隔离合成样本验证：建库重开、中文 / 英文 / 数字、短词、无命中、单字边界、重复更新、正文与元信息事务、分词支持性检测。
2. 替换共享全文索引并接现有文件成功通知；验证文件失败 / 索引失败、快速连续保存、旧任务、同名跨库、文件夹改名 / 删除及恢复。
3. 补首次构建、重启复用、pending 重放、同秒等长修改 hash 对账，以及目录截断 / 授权失败不误删；故障与服务重建用隔离注入，不在设备上制造写中断。
4. 接 App 当前库、跨库和小艺工具状态契约，验证结果片段来自当前文件、不完整状态与预算不混淆。
5. 构建及适用模拟器结果单独记录；API24 / XT2 由用户手动验收。测量首次构建时间、重开首查、后台对账耗时、增量延迟、峰值内存、正文 / 索引 / 日志磁盘占用。测试库不得超过遍历能力后仍宣称完整，规模扩大须同时验证完整性标记。

本次未执行上述测试；设计不预填性能收益、数据库体积或设备通过结论。
