# v2.8 需求文档 —— ZIP 安全上限全局提高（导入与应用备份共用口径）

> 状态：已交付（2026-11-23 立项并当日交付；真机验收待用户反馈）
> 来源：需求池 C 节「ZIP 安全上限全局提高（10000 条目 / 1GB 总量 / 128MB 单文件）」。用户 2026-11-23 提出大附件库备份被安全上限卡住，核实上限为应用常量（非系统限制）后拍板「全局提高」。版本号说明：v2.7 已被并行会话的「笔记属性面板 UI 对齐 #blockSheet 设计稿」占用，本需求顺延 v2.8。

## 1. 版本定位

v1.36 §6 定下的 ZIP 安全上限（5000 条目 / 512MB 解压总量 / 64MB 单文件）沿用至今，含大附件（视频 / 录音 / 高分辨率图片）的知识库在「完整应用备份」导出与「ZIP 新建库导入」两端都会被 `over_limit` 拒绝。本版把上限全局提高到 10000 条目 / 1GB 总量 / 128MB 单文件；两个端口共用 `ZipImportService.DEFAULT_LIMITS` 单点，不拆备份专用限制。

依据：2026-11-23 官方答复（[问答存档](../../harmonyos/qa/2026-11-23_zlib流式inflate状态语义_API24.md)、[api_notes Y4](../../harmonyos/api_notes.md)）确认 API ≤ 24 无系统级逐条目解压接口、无强制限额，自绘容器解析 + 逐条目流式 inflate 路线合理——上限纯属应用防御常量（防 ZIP 炸弹 / 防内存失控），提高数值不引入平台风险。

## 2. 完成判定

`DEFAULT_LIMITS` 四项按 §3 定值落地；ZIP 导入（`Index` `chooseZipBackup`）与应用备份（`ApplicationBackupService.APP_BACKUP_LIMITS` 引用同一对象）自动跟随，无第二处数值；`test_zip_import.mjs` 新增 v2.8 防线（值 + 源 + 行为三断言）全过、既有测试零回归；`arkts_check` 零错误 + 签名 HAP 构建通过。

## 3. 需求清单

来源：[需求池 C 节](../../requirements_backlog.md)

### 28.1 上限定值变更（单点）

| 字段 | v1.36 §6 | v2.8 | 说明 |
| --- | --- | --- | --- |
| `maxEntries` | 5000 | 10000 | 条目数上限 |
| `maxTotalUncompressed` | 512MB | 1GB | 解压后总量上限 |
| `maxSingleUncompressed` | 64MB | 128MB | 单文件解压后上限 = 单条目峰值内存 |
| `maxNameBytes` | 1024 | 1024 | 不变（条目名长度防御与路径安全同量级） |

- 只改 `ZipImportService.DEFAULT_LIMITS`（4 个数值 + 注释）；`ApplicationBackupService.APP_BACKUP_LIMITS` 与 `Index` 导入调用均引用该对象，零改动自动跟随。
- 报错文案不写数值（「超出大小上限」类措辞），零 UI 文案改动。

## 4. 明确不做（本版）

- 不拆「导入」与「备份」两套上限（用户拍板全局口径）。
- 不改流式解压与内存模型：单条目仍整块 inflate 进一个 `ArrayBuffer`（`ZlibRawInflate` `new ArrayBuffer(expectedSize)`），128MB 上限即单条目峰值内存成本；低配设备 OOM 风险由上限本身兜底。
- 不动 `maxNameBytes`（1024）。
- 不动其余防御检查：ZIP64 / 加密 / 符号链接 / 多盘分卷 / 不安全条目名 / 空间预检（`no_space`）。
- 不动服务层完整性权威校验（返回字节长度 + CRC32 双重核对）。

## 5. 红线

- 上限仍是应用防御常量：只提数值，不删任何防御分支。
- 无 UI 改动，不涉及 token 红线；笔记内容不进埋点（硬约束 16）。

## 6. 技术约束与依赖

- 改动面：`entry/src/main/ets/model/ZipImportService.ets`（`DEFAULT_LIMITS` 4 行 + 注释）、`tools/tests/test_zip_import.mjs`（新增 v2.8 测试）、本需求文档、需求池 C 节、实施总清单登记。
- 无新增权限；无数据结构变化；无 UI 改动；不触碰 native / web 产物。
- 内存成本：单条目上限翻倍即解压峰值内存翻倍（64→128MB 连续 `ArrayBuffer`，XT2 可承受）；压缩载荷读取仍整块、CRC32 仍全量计算，单条目耗时随文件大小线性增长，由导入 / 备份既有进度与取消机制覆盖。
