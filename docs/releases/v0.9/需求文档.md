# v0.9 需求文档 —— v2 UI 全面迁移与原稿归档

> 状态：实施中（2026-10-27 用户要求）；没有日历交付日期承诺。
> 来源：需求池 [L-01–L-06](../../requirements_backlog.md#l-v2-ui-全面迁移与原稿归档2026-10-27已分配-v09)。
> 对应里程碑：新增 M4.10，完整归本版；既有 M0–M8 的功能承诺与验收记录不重新分配。

## 1. 版本定位

以设计稿 v2 为统一 UI 方向，完成原稿有效能力的等价迁移、原生 UI 对齐与旧稿归档。v2 是设计代次，App 交付版本是 v0.9。本版只改原型、原生 UI 和迁移文档；沿用已有业务服务与保存逻辑，不扩建或重构业务层。

最新有效交互见 [v2 设计说明](../../prototype/v2/设计说明.md)；其中存在修订历史，应以后续明确替代的规则为准。本版实施时先整理成单一现行说明，旧修订留作记录，不靠堆叠覆盖条款解释当前行为。

## 2. 完成判定

[迁移验收清单](迁移验收清单.md)中每个当前有效功能均有 v2 入口、实际行为、回归结果与对应原生落点；单 / 双 / 三屏、90° 旋转、浅深色和窄栏无遗漏与溢出。v2 不再依靠旧稿提供当前功能或生成数据；原生 UI 与基线一致，原功能不回退。完成正式入口切换与归档，才能标记本版完成。

分阶段验收：原型行为与视觉、原生构建 / 单测、模拟器、API24 / XT2、分享接收端、发布分别记录。模拟 DOM 检查不能代替浏览器视觉，API26 记录不能代替 API24 / XT2，原型中的示意不能算原生实现。

### 3.1 执行顺序与门禁

1. **P1 盘点与补齐原型**：清单对照 → v2 缺项补齐 → 现行设计说明收口。保留旧稿作为对照，不提前归档。
2. **P2 建立唯一设计入口**：完成浏览器多形态回归、生成与测试迁移；确认所有当前流程在 v2 可用后执行归档和兼容入口切换。归档不是删除历史设计与检查。
3. **P3 原生 UI 对齐**：使用固定后的 v2 基线迁移原生 UI，回归现有服务与保存边界；不得把原型 P1/P2 完成当作 App 完成。
4. **P4 本版收口**：补齐 API24 / XT2 与必要目标应用验证，记录仍未通过的项目；正式发布按版本规则另行执行。

本版为接下来优先 UI 任务；既有本地版本的在途改动与验收证据保留，迁移复用它们，不要求为进入本版先完成所有旧版发布。缺少的真实服务按原属版本承诺补齐或记录依赖，不在本版编造成功状态。v0.3 / v0.6 仍在外部队列。

### 3.2 归档门禁

归档前须逐项满足：

- 当前有效功能没有“仅旧稿有入口”的项目；旧稿中的 Git / 小艺外部待办在 v2 保留状态与需求指向，不伪装可用；历史 Agent 能力按原范围保留在档案。
- 所有当前生成器 / 测试不再写入或依赖旧稿，历史专用测试单独指向归档；版本 / 样例 / 反馈配置没有新增手写第二真源。
- 单 / 双 / 三屏 × 0° / 90° × 浅 / 深色完成真实浏览器检查；窄屏、240px 栏宽、长标题、空态、菜单和键盘均可用。
- 归档资源、内部跳转和原地址兼容入口验证通过；迁移前路径及回退方式写入验收记录。

## 4. 明确不做

- 本轮只修改原型、原生 UI 和迁移文档；不改模型 / 存储 / 分享等业务服务、数据格式、包版本、tag 或发布状态。界面接入只复用已有服务；不得用原型内存行为替代真实原生能力。
- 不把当前 v2 概念稿直接视为全面迁移完成。
- 不恢复已撤下的本地 Agent View，不为 UI 迁移接入真实小艺或推进 Git clone / push；不扩展它们原版本的范围。
- 不新增云协作、第四栏、插件系统、ZIP 导入 / 备份恢复或未分配的 Markdown 能力。
- 不删除历史版本需求和验收证据，不提前移动仍被测试 / 生成器依赖的旧稿。
