# v1.72 需求文档 —— ZIP 导入恢复文件 mtime（方案 B 落地）

> 状态：2026-11-16 用户指定实现并当日改定方案 B。承接 [需求池「ZIP 导入恢复文件 mtime」](../../requirements_backlog.md#b-笔记库级能力共同前提全库索引)与[决策总表 mtime 方案行](../../open_questions.md)。
> 同日曾按方案 A（导出侧 payload `utimes` 回填 + DOS 字段承载）完成实现，用户改定方案 B：**导出侧改写 `yaoshi-mtime.json` 时间表随包分发，DOS 字段降级为兜底**（不再押注 `zlib.compressFile` 的 DOS 字段行为）；导入侧钩子（`setModifiedTime` / `preserveMtime`）两方案同构，未重做。

## 1. 版本定位

不做本需求，ZIP 迁移链路的写作历史就是假的：统计数据不落盘、按文件 mtime 实时重算（v1.51/v1.52），v1.49 排序同样按 mtime——而 ZIP 导入解压出的所有文件 mtime = 解压时刻 → 换机 / 重装后热力图、连写、累计天数全部塌缩到导入当天，时间排序全部失真。

机制大半已存在：`ZipImportService.parse` 已从 central directory 读 DOS 时间进 `entry.modifiedAtMs`（v1.36），`extract` 已支持 `preserveMtime` 钩子（v1.66 应用备份恢复已在用）。方案 B 补齐两处断点：

1. **导出侧**（`ShareArchiveService.prepareZip`，覆盖设置页「导出当前知识库」（v1.37 复用 25.18）与文件夹 / 知识库分享 ZIP）：payload 写完后不逐文件回填 mtime，改为收集「ZIP 内归档路径 → 源文件 mtime」写入 payload 根的 **`yaoshi-mtime.json`** 时间表（普通文件名，确保 `zlib.compressFile` 收录），随 ZIP 一起分发。
2. **导入侧**（`importZipBackup`）：`TempVaultZipWriter` 补 `setModifiedTime`（`fileIo.utimes`，Y5），调用点开 `preserveMtime: true`；`extract` 先读时间表，**命中条目按表回填（毫秒精度），未命中 / 表缺失 / 表损坏逐条回落 DOS 时间**。

## 2. 完成判定

导出侧：设置页导出知识库（或分享知识库 / 文件夹 ZIP）→ 包内含 `yaoshi-mtime.json`，其中每个条目的 `mtimeMs` 等于源文件 mtime（毫秒精度，无 DOS 2 秒损失）。

导入侧：把该 ZIP 经「导入库」导入 → 导入库内文件 mtime 等于时间表记载值 → 统计面板热力图 / 连写 / 累计天数与源库一致，文件树「修改时间」排序与源库一致。

兜底：无时间表的第三方 ZIP（PC 打包的 Obsidian 库等）照常导入（v1.36 既有行为零改动），mtime 按包内 DOS 时间恢复；DOS 也缺失 / 非法的条目保持解压时刻。

回归：ZIP 导入安全校验（路径 / 加密 / 上限 / CRC）、分享内容（图片重写 / 排除内部目录）、v1.66 应用备份导出与恢复链路零改动。API24 / XT2 真机验收待用户。

## 4. 明确不做

- **目录 mtime 不回填**（导出侧 payload 目录、导入侧解压目录均为创建时刻）：统计活跃日与主排序按文件 mtime，目录排序按导入时刻，影响可忽略；`extract` 只写文件条目。
- **DOS 字段不再是自家环路的载重路径**：自家导出不回填 payload mtime（方案 A 的 `restorePayloadMtime` 已随方案 B 移除），包内 DOS 时间即拷贝时刻；`zlib.compressFile` 是否写 mtime 进 DOS 字段（Y 组 ⚠️ 未记载）不再影响自家链路，仅影响第三方 ZIP 的兜底精度。
- Git 导入 per-file 最后提交时间回填（native `utimensat` + libgit2 log）仍为可选二期，未排期。
- 绕过 App 手动拷贝不保护（mtime 口径固有边界，决策总表已记）。
- 单篇笔记 ZIP 分享（`NoteShareService`）不改：面向发给人看，不是迁移链路。
- v1.66 应用备份导出 / 恢复链路不动（`copyTree` 回填与恢复回填已实现；其 parse 用显式 profile，manifest 捕获默认关）。
- 不新增权限、不改 ZIP 导入安全校验与排除规则。

## 5. 技术约束与依赖

- **时间表文件名用普通名 `yaoshi-mtime.json`（不带点前缀）**：`zlib.compressFile` 对点开头文件的收录行为未记载（Y 组），普通 `.json` 文件名确保必被收录；`.json` 在导入分类（v1.36）本就是 'skip' 不解出，时间表自身不会落盘成用户文件。
- **时间表路径口径 = ZIP 内归档路径**：收录文件用库内相对路径、范围外图片用重写后的归档路径，与包内条目名一致；导入侧另按 `topFolder` 做前缀补 / 剥双向注册，兼容「ZIP 整体套一层目录」形态。
- `fileIo.utimes(path, mtime)` since 11 ≤ API 24（[api_notes Y5](../../harmonyos/api_notes.md)）：Epoch **毫秒**，**限沙箱路径**——导入侧回填目标 tempDir 在 `vaultsRoot` 沙箱内，匹配限制；导出侧不再调用 `utimes`。
- `ShareArchiveService` 源文件 mtime 只经 `vaultAccess.stat` 读取（不按 `rootKind` 分叉，硬约束 14）；时间表写在 `sharePath` 沙箱 payload 内。
- hilog 告警只记错误码不记路径（硬约束 16 隐私红线）；时间表内容只有路径与毫秒时间戳，不含笔记内容。
- 防滥用上限：单表解压 ≤ 8MB、单条 mtime ≤ 2100 年、单条路径 ≤ 1024 字符，超限整表 / 单条忽略回落 DOS。
