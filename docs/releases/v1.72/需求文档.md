# v1.72 需求文档 —— ZIP 导入恢复文件 mtime（方案 A 落地）

> 状态：2026-11-16 用户指定实现。承接 [需求池「ZIP 导入恢复文件 mtime」](../../requirements_backlog.md#b-笔记库级能力共同前提全库索引)与[决策总表方案 A](../../open_questions.md)（2026-11-10 拍板）。

## 1. 版本定位

不做方案 A，ZIP 迁移链路的写作历史就是假的：统计数据不落盘、按文件 mtime 实时重算（v1.51/v1.52），v1.49 排序同样按 mtime——而 ZIP 导入解压出的所有文件 mtime = 解压时刻 → 换机 / 重装后热力图、连写、累计天数全部塌缩到导入当天，时间排序全部失真。

方案 A 的机制大半已存在：`ZipImportService.parse` 已从 central directory 读 DOS 时间进 `entry.modifiedAtMs`（v1.36），`extract` 已支持 `preserveMtime` 钩子（v1.66 应用备份恢复已在用）。本版补齐两处断点：

1. **导出侧**（`ShareArchiveService.prepareZip`，覆盖设置页「导出当前知识库」（v1.37 复用 25.18）与文件夹 / 知识库分享 ZIP）：payload 是新写的副本，mtime 默认为拷贝时刻，`zlib.compressFile` 打进 DOS 字段的就是拷贝时刻——写完 payload 后用源文件 mtime 回填，让包内 DOS 时间是真写作时间。v1.66 应用备份导出已在 `copyTree` 里做了同款回填，本版把分享 / 导出链路对齐。
2. **导入侧**（`importZipBackup`）：`TempVaultZipWriter` 补 `setModifiedTime`（`fileIo.utimes`，Y5），调用点开 `preserveMtime: true`，解压写盘后逐条目回填。

## 2. 完成判定

导出侧：设置页导出知识库（或分享知识库 / 文件夹 ZIP）→ 包内条目 DOS 时间等于源文件 mtime（误差 DOS 2 秒精度 + 本地时区口径）。

导入侧：把该 ZIP 经「导入库」导入 → 导入库内文件 mtime 等于包内 DOS 时间 → 统计面板热力图 / 连写 / 累计天数与源库一致，文件树「修改时间」排序与源库一致。

回归：ZIP 导入安全校验（路径 / 加密 / 上限 / CRC）、分享内容（图片重写 / 排除内部目录）、v1.66 应用备份导出与恢复链路零改动。API24 / XT2 真机验收待用户。

## 4. 明确不做

- **目录 mtime 不回填**（导出侧 payload 目录、导入侧解压目录均为创建时刻）：统计活跃日与主排序按文件 mtime，目录排序按导入时刻，影响可忽略；`extract` 只写文件条目。
- Git 导入 per-file 最后提交时间回填（native `utimensat` + libgit2 log）仍为可选二期，未排期。
- 绕过 App 手动拷贝不保护（mtime 口径固有边界，决策总表已记）。
- 单篇笔记 ZIP 分享（`NoteShareService`）不改：面向发给人看，不是迁移链路。
- v1.66 应用备份导出 / 恢复链路不动（`copyTree` 回填与恢复回填已实现）。
- 不新增权限、不改 ZIP 导入安全校验与排除规则。

## 5. 技术约束与依赖

- `fileIo.utimes(path, mtime)` since 11 ≤ API 24（[api_notes Y5](../../harmonyos/api_notes.md)）：Epoch **毫秒**，**限沙箱路径**——本版两处调用点（payload 在 `sharePath`、tempDir 在 `vaultsRoot`）均为沙箱内，匹配限制。
- ⚠️ **`zlib.compressFile` 是否把文件 mtime 写进 ZIP DOS date/time 字段，官方文档未记载**（Y 组无结论）。v1.66 应用备份的「mtime 随包恢复」同样押注此行为且设备验收未做——本版与其共享该风险，列为 API24 设备实测点：导出 ZIP 后解包核对 central directory 时间，或直接走「导出 → 导入 → 统计一致」端到端验收；若实测不保留 mtime，后续版本把 `compressFile` 换成自建 ZIP 写入器（CRC32 / raw deflate / 显式 DOS 时间，机制与 v1.36 手写 inflate 对称），本版导入侧与导出 payload 回填设计均不受影响。
- `ShareArchiveService` 源文件 mtime 只经 `vaultAccess.stat` 读取（不按 `rootKind` 分叉，硬约束 14）；回填目标是沙箱 payload 路径，不对外部目录调用 `utimes`。
- hilog 告警只记错误码不记路径（硬约束 16 隐私红线：路径不进日志的既定口径，见 `ShareArchiveService.readSnapshot` 注释）。
