# v0.3 需求文档 —— 能同步

> **2026-10-30 路线与排期更新**：用户要求重新启动 v0.3，优先验证并采用 Native libgit2；仅在 Native 经验证不可行时评估其他方案。先完成目标设备加载、HTTPS、新库 clone 与已有库数据保护方案的验证，再推进双向同步。现有 Web 实现及证据保留，不能把 PoC 编译通过当作设备或同步验收通过。开发入口见 [Native 优先实现提示词](实现提示词_Native优先.md)。下方与此冲突的旧排期及 PoC 限制为历史记录。

> 历史排期：Git 同步仍在外部依赖队列。本轮包括“新 clone 隔离目录文件写入改造”和用户于 2026-10-27 单独授权的 Native libgit2 N-API 封装 PoC；后者只验证独立模块，不接入 App。commit/push、既有库同步及其他 Git 功能仍后置。

> **状态**：⏳ Native libgit2 已在 API26 模拟器 test HAP 验证加载、系统 CA HTTPS、认证、分支、进度、字节哈希和失败清理；已有库写入保护尚未建立，因此未接入生产同步或对已有库执行 checkout。API24 / XT2 与真实 HTTPS 认证仍待验；当前结论和阻塞见 §6。
> **对应里程碑**：M3.5 + M4
> **版本定位**：把本地库接到远端 Git 仓库上，并把形态适配彻底收口。

## 1. 版本定位

手机端"随手记必须能回写"是硬需求，所以同步不能留到 v2。
这一版把 v0.1 的库模型升级为「本地库 + Git 库并存」，并让形态切换在任何界面下都不丢东西。

⚠️ **本轮只恢复新 clone 的写入改造与隔离验证**。clone 成功仅表示本次新库导入并登记，不代表 commit/push 或完整 Git 同步完成；XT2 / API 24 设备验收仍待后续统一执行，具体结果见 §6。

## 2. 完成判定

> 填入仓库地址与令牌后，能把远端仓库拉成 `vaults/<仓库名>` 并与本地库并存；
> 编辑后能 commit 并 push 到 `xt2` 分支；任意界面下折叠/展开都不丢笔记与光标。

## 3. 需求清单

### 3.1 导入 Git 仓库（M3.5）

**本轮受控写入例外**：新 clone 只落入本次创建的 `vaults/<id>__importing` 未登记目录。该目录不包含既有用户数据，因此其中 Git 元数据、文本、图片和其他二进制文件可通过普通二进制写入保留原字节。当前本机 API 26 SDK 中 `openSync`、`writeSync(ArrayBuffer)`、`closeSync` 的声明标注 `@since 9`，兼容 API 24 的声明依据成立；API 24 / XT2 运行行为仍须单独验收。普通写入没有 `AtomicFile` 回滚保证，失败可能留下半成品，只能清理本次导入目录。clone/checkout、待写队列 flush 和从磁盘重新读取后的 Git 状态校验通过后，才改名并登记。失败或登记持久化失败不得留下可用库；重启时依导入标记清理未完成导入。目录 `renameSync` 不作为已有文件原子覆盖保证。

已有库更新不适用该例外：本地 Markdown 保存继续使用 AtomicFile 字符串路径；Git 后端只可把可无损 UTF-8 往返的文本交给 AtomicFile 字符串写入，不能无损往返的字节在打开目标文件前拒绝。已有库二进制覆盖不在本次实现范围，失败保留旧内容的要求不变。

### 3.4 Native libgit2 N-API 封装 PoC（2026-10-27 用户授权）

实现独立模块 `native/git2_napi/`，导出 libgit2 版本与能力查询，以及支持选分支和进度回调的异步 clone。clone 仅接受绝对路径下的全新目标目录，不得覆盖现有目录；HTTPS 默认使用鸿蒙预设 CA，`caFile` 只作为可选覆盖，凭据由调用者传入。模块与 App、SyncPage、当前 isomorphic-git 桥接均不连接。

本 PoC 验收以 API 24 目标的 arm64 NDK 编译、N-API 模块导出与 libgit2 链接成功为界。不得据此声称 API 24 / XT2 运行通过或替换正式 Git 实现。pull、status、stage、commit、push 和业务认证策略留待后续排期；已有库文件写入保护不属于本模块的 clone 写入例外。
