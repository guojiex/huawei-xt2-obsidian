# v0.3 开发提示词：Native libgit2 优先

你在 `/Users/jiexin.guo/github/huawei-xt2-obsidian` 开发“曜石笔记”：HarmonyOS ArkTS、Stage、API ≤ 24，目标华为 XT2。用户决定重新启动 v0.3 Git 同步，**优先验证并采用 Native libgit2；仅在 Native 经验证不可行时再评估其他方案**。本提示词授权按下述范围开发，不把其他工作区改动算作本任务。

## 开工前

1. 检查分支、远端与工作区；保留并避开其他未提交工作。先读 `AGENTS.md`、`docs/releases/v0.3/需求文档.md`、`docs/releases/实施总清单.md`、`docs/open_questions.md`、`docs/harmonyos/api_notes.md` 的 C1 / S1 和 `native/git2_napi/README.md`。核实当前源码与已有证据，勿假定旧状态仍然成立。
2. Native PoC 已具备版本、能力查询与异步 clone；API 24 目标编译使用 API 26 sysroot，只是编译证据，不代表 API 24、XT2、系统 CA 或完整同步已通过。现有 Web clone 在 API26 模拟器已有记录，不等于 Native 验证。保留 Web 实现和历史记录。
3. 不凭记忆编造 HarmonyOS / N-API 接口；以 SDK、官方资料和本仓库知识库核实最低版本。路径由 Context 与统一解析器提供；敏感凭据使用 AssetStoreKit，不写入日志、URL、普通配置或测试输出。默认使用系统信任，不要求普通用户配置 CA；私有 CA 覆盖仅供特殊环境。

## 实施与验收

1. **先跑通 Native 验证**：以最小、可回退方式将现有模块打包到测试 HAP，验证模块加载、版本与能力、线程回调、HTTPS 系统 CA、认证、分支选择、进度及异步错误。先用隔离测试仓库和全新目录验证 clone；通过哈希比较中文、空文件、图片与 Git 二进制数据，并校验状态和失败清理。不得对现有用户库试验写入，不得把测试 HAP 与生产接入混为一谈。
2. **设计安全的已有库同步**：先分析 libgit2 对工作区与 `.git` 的写入、删除、失败和中断行为，建立可验证的保护与恢复方案；已有笔记或附件不得在失败时变成半成品或丢失。遵循 AtomicFile 约束，不以普通覆盖或自制 tmp + rename 冒充原子替换；如需要调整架构或无法证明保护，停止相关写入并记录具体阻塞，不牺牲已有内容强行通过。
3. **推进 v0.3 双向同步**：在上述边界成立的前提下，接入已有多库注册、按库凭据及同步界面，支持安全的 status、stage、commit、fetch/pull 和 push，保持 `xt2` 冲突策略、前台进度、未推送提示和 `.trash` 排除；先复核分支、远端变化、未提交编辑与冲突语义，避免覆盖或强推，手机端不实现合并 UI。只使用隔离的可写测试远端，不操作用户真实远端数据。
4. 对 401/404、断网、权限、重复操作和写入失败给可操作结果并测试；核对编辑器未保存内容、库切换、形态变化与同步并发的保护。不添加后台同步、自动上传或未排期的功能。
5. 原生路线遇到问题先排查 SDK、打包、系统信任、认证与设备证据；只有形成明确不可行证据或满足客观阻塞条件，才记录原因、影响及备选比较，再评估现有 isomorphic-git 路线。不得因短期调试困难静默切回或删除任一实现。

## 验证与交付

- 分别记录静态检查、单测和受控失败注入、构建、API26 模拟器、API24 / XT2、真实 HTTPS 认证及端到端测试；未运行的项目保持待验。不得主动用模拟器制造崩溃、强杀或写入中断；使用可控故障和重新创建服务实例验证恢复。
- 完整同步至少验证 clone → 编辑 → commit → push、远端变化和冲突、断网恢复、已有库与二进制内容保护、重开恢复、`.trash` 排除；不要把单项 clone 或编译通过等同完整交付。
- 更新 v0.3 验收记录和实施总清单，标明证据、限制、剩余问题；不修改包版本、打 tag 或宣称发布。检查 diff，只提交本任务相关文件，遵循仓库提交规范。
