## 1. 版本定位

支持把用户已有的本地目录**通过授权关联为知识库**（不复制进沙箱）：App 与其他具备授权能力的软件操作同一份真实文件，解决「把现有笔记拿进来」与「外部工具共管同一目录」。

## 2. 完成判定

在 XT2 / API 24 真机上：选择一个已有 Markdown 目录 → 授权 → 注册为知识库，文件树浏览、打开 / 编辑 / 保存全部读写该目录的真实文件；重启应用与设备后授权仍有效；「移除库」只解除关联、不清除磁盘内容。前置核实项（§5）全部有结论后才进入实现与验收；核实不通过则本版回到规划状态重新拍板，不降级硬做。

### 3.1 导入入口与设计验收（2026-10-31）

本节细化 15.1 / 15.2 / 15.5 的界面要求，不新增版本范围。现行设计见 [v2 设计说明 §3](../../prototype/v2/设计说明.md#3-知识库与文件导航) 与 [交互原型](../../prototype/v2/index.html)。

- 知识库选择器与库管理页统一提供「导入库」入口，弹窗可切换「本地目录 / Git 仓库」，默认本地目录。
- **本地目录（本版）**：目录选择卡片调用系统目录选择器；选择后显示目录名，并在授权成功后允许「关联此目录」。取消选择或授权失败不登记知识库，并提供重试入口。
- 导入前明确说明「直接读写原目录，不复制文件」；库列表区分本地目录来源，移除操作使用「解除关联」，确认文案说明原目录与文件保留；改名只改显示名。
- **Git 仓库（v0.3）**：同一弹窗内展示 Git 导入表单，保留仓库地址、分支与安全认证流程；克隆、失败清理和远端数据边界归 [v0.3 §3.1](../v0.3/需求文档.md#31-导入-git-仓库m35)，不作为本版新增 Git 能力。
- 单屏 / 双屏 / 三屏及明暗主题下，来源切换、目录卡片、表单与底部按钮均可访问；小屏和矮窗口允许弹窗内容滚动。

**当前证据边界**：v2 原型已提供两种来源切换、示例目录关联与 Git 地址格式校验；仅修改页面内演示数据，不打开系统选择器、不访问远端、不接收令牌。原型与主题检查 79/79 通过；视觉预览因浏览器本地文件策略受阻，尚未验证。这些证据不代表原生 15.1 / 15.2 / 15.5 完成或设备验收通过。

## 4. 明确不做

- **不做复制导入**：导入语义已拍板为授权关联；「复制到沙箱」保留为需求池 M-02 备选记录，不排期。
- **不做云同步 / 目录同步引擎**：华为云空间与本地目录同步是需求池 C 节并列候选（`open_questions.md` Q8），本版只交付「目录即库」，不实现任何同步。
- **不做多应用并发编辑的自动合并**：只做变更检测与保存保护（15.4）。
- **不自动迁移既有沙箱库**到外部目录；沙箱库全部能力保持不变。
- **不以外推承诺平台能力**：目录选择、持久授权、递归读写等能力以 §5 前置核实结论为准，禁止按 PC / 其他系统经验落码。

## 5. 技术约束与依赖

**前置核实（走 `docs/harmonyos/` 提问流程，未核实前不落码）**，评估清单沿用需求池 M 节，不复制结论：

1. XT2 / API 24 的系统目录选择能力（能否选目录、返回什么形式的句柄 / URI）
2. 所选目录的**持久化授权**：跨应用重启 / 设备重启是否仍可读写；授权撤销、目录移动的行为与恢复路径
3. 递归读写与外部变更感知能力
4. 另一款软件对同一目录的实际访问权限（能看到 Markdown ≠ 能管理完整仓库）

既有约束不变：编辑已有文件走 AtomicFile（`AGENTS.md` 硬约束 15）；令牌只存 AssetStoreKit（硬约束 11）；统一路径解析器保持一层（硬约束 14）。**外部授权路径的接入方式已定案（2026-10-31）**：外部目录**没有绝对路径**，一层解析器在 fd 世界里升级为「统一库访问层」—— 上层只认 `VaultRegistry.accessFor(vaultId)` 返回的 `VaultAccess`，沙箱实现走 fileIo、外部实现走 Native POSIX，**禁止在上层按 `rootKind` 分叉**（硬约束 14 已同步）。详见 §6.2。

### 6.2.4 外部库解除关联的落盘失败保护（2026-11-01）

代码复核发现解除外部库时，Registry 原先会在 Preferences 落盘前清除按 `vaultKey` 隔离的回收站和恢复草稿；若落盘失败，用户仍可能看到库记录，但私有内容已丢失。现将外部库流程调整为：调用方先释放系统持久授权；Registry 暂时从进程内列表摘除该库并以 `persist(true)` 写入 Preferences；只有成功后才丢弃访问器并 best-effort 清理沙箱 trash / drafts。落盘失败时恢复进程内 vault 列表和当前库、忘记已撤权的访问器、保留 trash / drafts 并向调用方返回错误。授权目录始终只解除关联，不递归删除。

- `tools/tests/test_vault_registry_names.mjs` 新增成功次序与 Preferences 失败保护两例；连同外部授权服务定向回归 `node --test tools/tests/test_vault_registry_names.mjs tools/tests/test_external_vault_authorization.mjs` **28/28 通过**。
- Preferences 写入 / flush 与系统持久授权撤销不是同一事务；发生落盘失败时进程内注册表与私有数据保持可恢复，但系统授权已经释放，用户可能需要重新授权才能继续访问该仍登记的外部库。若 `flushSync` 报错但系统实际上已保存新注册表，沙箱私有目录仍被保留；可能留下孤儿私有目录，优先保护数据，不自动删除。
- 本轮 `node --test tools/tests/*.mjs` **400/400 通过**，定向注册表 / 授权测试 **28/28 通过**；`EMU_HDC_PORT=5555 ./tools/emu.sh --run` 构建 unsigned arm64-v8a HAP、覆盖安装并拉起成功。API26 模拟器未选择外部目录，故设备结果只覆盖普通安装启动，不代替 Picker / 持久授权设备验收；API24 / XT2 与发布仍待验。

### 6.3 15.6 私有数据边界（2026-10-31 拍板）

**决策**：App 私有数据**一律落沙箱、按 `vaultKey` 分目录**，一个字节都不写进用户授权目录。
理由两条：① `.trash` / `.draft` 出现在用户的 Markdown 目录里会被 Obsidian、Git、云盘当成普通内容库的一部分，
二是会和 15.5「移除库只解除关联、不清磁盘」直接打架（删库时这些算用户的还是 App 的，说不清）。
按 `vaultKey` 而不是 `vaultId` 分目录是为了让**库改名后仍能定位**（vaultKey 改名不变、复制出新库才重新生成）。

| 私有数据 | 现在在哪 | 改成哪儿 | 说明 |
| --- | --- | --- | --- |
| 回收站 | `<vaultDir>/.trash`（**在库目录里**） | `filesDir/trash/<vaultKey>/…` | 唯一真正会污染外部目录的一项；外部库的删除在沙箱侧留痕、用户目录里只少一个文件 |
| 崩溃恢复草稿 | `filesDir/drafts/<vaultId>/<rel>.draft` | `filesDir/drafts/<vaultKey>/…` | 已经在库外（不污染），只把分段 key 由 `vaultId` 换成 `vaultKey` |
| 令牌 | AssetStoreKit | 不变 | 硬约束 11 |
| 分享临时产物 | `cacheDir/share` | 不变 | 系统按 cacheDir 生命周期回收 |

**草稿的定义澄清**（回答「我们有草稿吗」）：有，但不是用户可见的草稿箱 ——
`NoteDraftService` 存的是**自动保存完成前的崩溃恢复快照**（`{version, baseText, content}`），
且只有正式文件仍与 `baseText` 逐字相同时才允许恢复，防止旧草稿覆盖更新的正式笔记。
它本来就在 `filesDir/drafts/` 下、不在库目录里，所以 15.6 对它的**唯一改动是分段 key 换成 vaultKey**。

**已实现**（2026-10-31）：
1. `VaultPathResolver`：`trashRoot()` = `filesDir/trash`，`trashDir(vaultKey)` / `draftsVaultDir(vaultKey)`
   / `resolveInTrash` / `resolveDraft` 全部改为按 **vaultKey** 拼沙箱路径；`TRASH_SEG` 由 `.trash` 改为 `trash`
   （不再是隐藏段，因为它已经不在用户可见的库里了）。
2. `VaultRegistry`：`trashDirOf` / `absoluteInTrash` / `draftsVaultDirOf` / `draftDirectory` / `absoluteDraftIn`
   在转发处统一 `vaultKeyOf(id)` —— **上层调用点零改动**，仍然只认 vaultId。
3. NoteDraftService.cleanupOrphans：草稿目录名现在是 vaultKey，孤儿判定改为按 key 反查；
   查不到的整棵由 `registry.removeDraftsTreeByKey(key)` 删掉。
4. `VaultRegistry.remove()` 增加 `removePrivateData()`：回收站与草稿随库一起清（**best-effort** ——
   此时库目录已删，抛出去只会造成「磁盘已删、注册表还在」的半状态，比留孤儿目录严重得多）。

**两条拍板记录**：
- **历史决定（2026-10-31，已被 2026-11-01 新决定覆盖）**：当时认为 App 未上架、没有存量用户，
  因而不迁移 `vaultDir/.trash`；开发机残留可删本地安装。该记录保留为历史，不再作为当前迁移策略。
- **当前决定（2026-11-01）**：首次打开回收站时，把库内旧 `.trash` 中的 Markdown 笔记复制到
  `filesDir/trash/<vaultKey>/…`，逐项原子写入并回读校验，**始终保留原 `.trash`**。重名时保留现有沙箱副本，
  为旧条目分配 `-2` 等后缀；失败时不删除源，可重试。历史 TrashService 只接收 Markdown 笔记，其他文件留在原目录。
- **删库即清私有数据**（用户拍板：用户拍板"要清，你都删库了自然应该删掉"）。沙箱库与外部库一视同仁 ——
  用户的笔记按 15.5 原封不动留下，App 自己的回收站 / 草稿没有理由继续占用磁盘。

**回归锁定**：`tools/tests/test_private_data_layout.mjs`（5 例）锁住「回收站不在库目录子树内、
两类私有目录按 vaultKey 分段、路径中不出现隐藏段」；`test_vault_registry_names.mjs` 增 2 例锁住
「删库清理 trash/drafts」与「清理失败不回滚为半状态」。
