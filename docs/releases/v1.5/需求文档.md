# v1.5 需求文档

> 状态：规划中（本机 SDK / 官方资料核实已归档；本轮按目标 skip，等待受限权限决策与 XT2 / API24 验收条件）
> 对应里程碑：新增 M8.2，完整归本版；需求来源为需求池 M 节 M-01 / M-02（`docs/requirements_backlog.md`）。
> 排期：2026-10-31 用户拍板——v0.11 收口后**插队优先**领取本版，v1.4 后移；导入语义为**授权关联外部目录（不复制）**。

## 1. 版本定位

支持把用户已有的本地目录**通过授权关联为知识库**（不复制进沙箱）：App 与其他具备授权能力的软件操作同一份真实文件，解决「把现有笔记拿进来」与「外部工具共管同一目录」。

## 2. 完成判定

在 XT2 / API 24 真机上：选择一个已有 Markdown 目录 → 授权 → 注册为知识库，文件树浏览、打开 / 编辑 / 保存全部读写该目录的真实文件；重启应用与设备后授权仍有效；「移除库」只解除关联、不清除磁盘内容。前置核实项（§5）全部有结论后才进入实现与验收；核实不通过则本版回到规划状态重新拍板，不降级硬做。

## 3. 需求清单

| # | 需求 | 验收点 |
| --- | --- | --- |
| 15.1 | 外部目录选择与持久授权 | 提供目录选择入口；授权范围、跨重启（应用 / 设备）持久性、权限撤销与目录被移动时的行为有明确处理与用户提示 |
| 15.2 | 已有目录关联为知识库 | 识别 Markdown 与附件目录结构；排除清单（`.git`、系统隐藏目录等按既有规则）明确；库注册表记录库类型，与既有沙箱库并存、可切换 |
| 15.3 | 文件树 / 编辑 / 保存走外部目录 | 全部读写经统一「库内相对路径 → 绝对路径」解析器（保持一层解析器原则）；已有文件编辑保存沿用 AtomicFile 硬约束；新建 / 重命名 / 移动 / 删除行为与沙箱库一致 |
| 15.4 | 外部变更感知与保存保护 | 打开 / 保存前检测外部修改，不覆盖他处修改；外部删除 / 移动 / 变更后文件树可刷新，失效笔记有明确处理 |
| 15.5 | 解除关联与删除语义 | 「移除库」默认只解除关联，不清磁盘；应用重置（设置 → 重置所有数据）不连带清空外部目录 |
| 15.6 | 私有数据边界 | 令牌仍存 AssetStoreKit，不写入共享目录；回收站（`.trash`）、草稿等 App 私有数据在外部库上的落位（库内 or 库外）实现前定案并写入本文档 |

## 4. 明确不做

- **不做复制导入**：导入语义已拍板为授权关联；「复制到沙箱」保留为需求池 M-02 备选记录，不排期。
- **不做云同步 / 目录同步引擎**：华为云空间与本地目录同步是需求池 C 节并列候选（`open_questions.md` Q8），本版只交付「目录即库」，不实现任何同步。
- **不做多应用并发编辑的自动合并**：只做变更检测与保存保护（15.4）。
- **不自动迁移既有沙箱库**到外部目录；沙箱库全部能力保持不变。
- **不以外推承诺平台能力**：目录选择、持久授权、递归读写等能力以 §5 前置核实结论为准，禁止按 PC / 其他系统经验落码。

## 5. 技术约束与依赖

**前置核实（走 `docs/harmonyos/` 提问流程，未核实前不落码）**，评估清单沿用需求池 M 节，不复制结论：

1. XT2 / API 24 的系统目录选择能力（能否选目录、返回什么形式的句柄 / URI）
2. 所选目录的**持久化授权**：跨应用重启 / 设备重启是否仍可读写；授权撤销、目录移动的行为与恢复路径
3. 递归读写与外部变更感知能力
4. 另一款软件对同一目录的实际访问权限（能看到 Markdown ≠ 能管理完整仓库）

既有约束不变：编辑已有文件走 AtomicFile（`AGENTS.md` 硬约束 15）；令牌只存 AssetStoreKit（硬约束 11）；统一路径解析器保持一层（硬约束 14，外部授权路径的接入方式在前置核实后定案）。

### 6.1 前置核实进展（2026-10-31）

本机一侧能核实的都核实完了，结论沉淀在 [api_notes T 组](../../harmonyos/api_notes.md#t-组外部目录选择与持久授权2026-10-31v15-前置核实)，逐条证据见 [核实归档](../../harmonyos/qa/2026-10-31_外部目录授权能力_API24.md)。**没有设备实测**，全部为 SDK 声明 / 官方文档依据。

| §5 前置项 | 结论 | 阻塞状态 |
| --- | --- | --- |
| 1 目录选择能力 | ✅ API 24 有官方入口：`DocumentViewPicker.select()`（since 9）+ `DocumentSelectMode.FOLDER`（since 11，syscap `FolderSelection`）。一次只能选一个目录；`authMode` 只用于 2-in-1 设备，手机上无效果 | 不阻塞；实施前用 `canIUse()` 判 syscap |
| 2 持久授权 | ⚠️ `persistPermission` / `activatePermission` / `deactivatePermission` / `revokePermission`（since 11）、`checkPersistentPermission`（since 17）均 ≤ API 24；但**全部**要求 `ohos.permission.FILE_ACCESS_PERSIST` —— 官方 FAQ 写明它是 **ACL 受限权限、APL system_basic**，normal 应用须跨级申请；且**应用 / 设备重启后必须调 `activatePermission()`** 才有权限 | **需用户拍板**：这会让 `module.json5` 首次出现 `INTERNET` 之外的权限，直接改仓库手册硬约束 13 |
| 3 递归读写与外部变更感知 | ❓ `fileIo.openSync(uri)` 接受 URI、`listFileSync` 有 `recursion` 是 SDK 事实；社区示例用「目录 URI → `openSync` → `listFile`」遍历，但这不是官方保证。未验证：授权是否顺延到子文件 / 新建文件、`AtomicFile` 能否作用于目录 URI、外部删除 / 移动后的失败形态 | 需 XT2 / API 24 设备实测 |
| 4 另一款软件共管同一目录 | ❓ `fileshare` 只描述本应用视角的授权；能否被 PC 工具 / 云盘客户端管理取决于目录所在命名空间，不是本 App 授予的权限 | 需选定具体目录场景后实测 |

**本轮没做的事**：没有申请或新增任何权限，没有改 `module.json5`，没有写任何 v1.5 代码，没有调用 Picker。

**由此产生的两个连带待决问题**（都不是本轮能自行决定的）：

1. 若用户不申请 `FILE_ACCESS_PERSIST`，则「持久关联」不成立 —— Picker 的临时授权在应用进程结束后失效。可选退化路线（每次启动重新选一次目录 / 只用沙箱库 + 外部同步）需用户选定后重排本版范围。
2. 即使拍板申请，也要先在设备上跑通一个最小样例（选目录 → 持久化 → 重启 → `activatePermission` → 递归列出 → 编辑保存），再回填上表第 2–4 项；在此之前 15.1–15.6 不落码。
