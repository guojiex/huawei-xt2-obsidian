# v1.17 需求文档 —— 应用内检测更新

> 状态：🟡 原生本地实现完成（2026-11-06），待模拟器与真机验收。**§3.0 前置核实已完成（2026-11-02，方向 A 成立）**；设计稿已合入 v2 原型（2026-11-04）。真实市场更新链路仍需已上架应用与 AGC 调测环境（V10）。执行顺序见 [实施总清单](../实施总清单.md)。
> 对应里程碑：无 M 编号（首发后独立优化，与 v1.10 / v1.13 / v1.14 / v1.15 同类）。

## 1. 版本定位

承接[需求池 I 节「应用内检测更新」](../../requirements_backlog.md)：在「设置与关于 → 关于」里让用户主动检查应用是否有新版本；有新版本时交给系统升级弹框把用户引导到华为应用市场完成更新。面向**已装机、市场侧提醒没注意到**的老用户。

**本版仍排在首发之后**：官方能力要求应用已在市场上架才生效（[api_notes V4](../../harmonyos/api_notes.md#v-组应用内检测更新appgallery-kit-updatemanager2026-11-02)），首发前不可能拿到真实结论。但核实改变了验收预期 —— 按 [api_notes V10](../../harmonyos/api_notes.md) 的联调途径，**不必等市场上出现更高版本**就能在第二版前拿到端到端证据（该途径发布前复核）。

## 2. 完成判定

用户在「关于」页主动点「检查更新」后，四种结果都能得到不误导的用户反馈 —— 检查中、有新版本（系统弹框接管，用户能在市场侧完成更新）、已是最新、检查失败（区分网络 / 不在前台 / 未同意市场隐私协议 / 频控）；全程零新增权限、请求链路不含任何笔记数据、界面不谎报市场版本号。三形态与深浅色可用，API24 / XT2 由用户手动验收。

## 3. 需求与验收

> 接口名、起始版本、枚举与错误码一律链接 [api_notes V 组](../../harmonyos/api_notes.md#v-组应用内检测更新appgallery-kit-updatemanager2026-11-02)，本文不复制结论（R5）。**答复原文里两处口径与本机 SDK 声明不一致，已按 SDK 修正，落码以 V 组为准，不要照转贴的答复写。**

### 3.0 前置核实（已完成，2026-11-02）

- 核实记录：[qa/2026-11-02_应用内检测更新能力答复_API24.md](../../harmonyos/qa/2026-11-02_应用内检测更新能力答复_API24.md) —— 该文件的表头「问题」列即当时向官方问的 7 项，答复与本机 HMS SDK 逐条核对结果同表。
- 结论：**方向 A 成立**（V1 / V2 / V4），方向 B、C 不再实现。本版范围据此裁剪，见下方各节与 §5。

### 3.1 入口与触发

- 入口位于「设置与关于 → 关于」分组内，与版本号、隐私政策入口（v1.11）、反馈邮箱（v0.7 §7.25）同区；视觉沿用 v1.13 分组列表，样式**只引用 token**（硬约束 17）。
- **仅由用户主动点击触发**：官方不建议启动 / 页面加载时频繁调用（V5）。进入关于页不自动请求，D-2 已按此收敛为「仅手动」。
- 请求进行中给可见进行态并禁用重复点击；界面不冻结。前台要求导致的失败按 §3.3 处理。

### 3.2 检查与判定

- 结论只取官方检查结果的「有 / 无新版本」语义（V2）。
- **不读市场侧版本号、不做客户端版本比较**：那两个字段是元服务专用（V3），应用场景的返回值未实测。**界面不得出现「发现 x.y.z 版本」这类我们并不知道的版本号。**
- 本应用当前版本仍按既有规则显示，取运行时自身包信息（[api_notes H 组](../../harmonyos/api_notes.md)，版本号单一真源是 `AppScope/app.json5`）。
- 不自建版本接口、不引第三方 SDK、不抓市场网页、不调 AGC REST。

### 3.3 结果与反馈

- **有新版本**：调用官方系统升级弹框接管引导，用户确认后进入市场更新流程（V4）。弹框 UI 与文案不由我们自定义，跳转不由我们拼（禁止自造 DeepLink scheme）。
  - 弹框显示成功 / 失败两个结果都要有分支：失败时给可执行的兜底提示（见「明确不做」第 1 条约束下，我们**不能**提供第三方下载路径，只能提示用户稍后重试或自行到应用市场操作）。
  - 未安装市场客户端时由系统侧处理，我们不额外实现兜底页。
- **无新版本**：显示「已是最新版本」。**不得**把「未上架 / 查询无结果」当作已确证的最新（V6 无专用状态码），文案避免绝对承诺，附最近一次检查时间。
- **失败**：按 V6 错误码至少区分四类并给不同反馈 —— 网络不可达、应用不在前台、用户未同意应用市场隐私协议、短时间调用过频（频控）。每类可重试，不静默失败，不自动连发成请求风暴；其余错误码归入通用失败并保留码值于诊断信息（不弹原始码给用户）。
- 检查与弹框的抛错列表不同（V6），分支表分别实现，不共用一套错误映射。

### 3.4 频率与冷却

- 无后台轮询、无定时任务、不因启动而发起。
- `checkAppUpdate` 的实际限流阈值官方未记载（V5）。本版实现应用内冷却，**冷却值是工程选择而非官方承诺**，须在代码与本文档注明并在真机观察；建议值 ≥ 60 秒、跨会话持久化与否按 D-3 拍板。

### 3.5 设计稿

- `docs/prototype/v2/index.html` 是**唯一设计真源**：先加原型，覆盖进行 / 有新版本 / 已最新 / 失败（至少网络与频控两态）与入口禁用态，含三形态表现；原型检查通过后再做原生，组件里不散写数值。
- 原型里系统弹框属外部 UI，只画「点确认后由系统弹框接管」的边界与说明，不临摹弹框样式。

### 3.6 验收分层（各层分别记录，不互相代替）

- 自动测试：结果到界面态的映射纯函数、四类失败分支、频控冷却逻辑、入口禁用与重复点击保护、隐私红线（调用参数不含笔记字段）。
- 构建：签名 debug HAP 通过，`@kit.AppGalleryKit` 引入后编译可用（V12 的旁证需由实际构建坐实）。
- API26 模拟器：入口可见性、各态反馈、系统弹框接管与返回后的界面状态、三形态与深浅色。**模拟器上应用未上架，预期只能拿到失败或无结果态，这类证据不得写成「更新链路通过」**。
- 真实链路：按 V10 的调测证书途径（先上架不含本功能的版本）在发布环境验证「检查 → 弹框 → 市场更新」；该条完成前，本版状态不得标「验收通过」。
- API24 / XT2 真机：由用户手动执行。

## 4. 方向（已定）

**A 已选定**：应用内检查 + 结果提示 + 官方系统弹框引导市场更新。B（只引导不结论）与 C（完全依赖市场提醒）作废，相关分支不再实现。已定记录见 [Q11](../../open_questions.md)。

## 5. 明确不做

- **不显示市场侧版本号、不做客户端版本比较**（依据 V3：该字段元服务专用，应用场景返回值未实测）。
- **不自定义或临摹系统升级弹框**，不自行拼市场跳转地址 / scheme（V4）。
- **不自行下载或安装更新包**，不做分片下载、不做跳转安装尝试，不引入侧载与第三方下载渠道（V8；且平台审核禁止引导第三方渠道）。
- **不做强制更新**：平台不提供强更标记（V7），我们不自行实现「不更新不让用」的阻断或最低版本门禁。
- **不自建后台 / 服务器 / 云函数**代查版本，不接第三方更新 SDK。
- **不进埋点、不上报**：不附带笔记内容、标题、文件名、路径、字数、标签（硬约束 16）；不为该功能新增上报链路。
- **不新增权限**（V1 声明无权限要求，硬约束 13）。
- **不做热更或动态下发代码包**。
- 不实现市场提醒的替代品（不推送更新通知、不做启动横幅）。
