# v1.15 需求文档 —— 构建提交号诊断

> 状态：⚪ 规划中；v2 原型展示示例，原生构建元数据、界面和设备验证均未完成。执行顺序见 [实施总清单](../实施总清单.md)。

## 1. 范围

承接[需求池构建提交号诊断](../../requirements_backlog.md)：在“设置与关于 → 通用 → 诊断信息”中显示当前安装包构建时的 Git commit 短 ID，并支持用户主动复制。它帮助区分相同应用版本下的不同构建，不替代 `AppScope/app.json5` 或运行时的版本号。

## 2. 需求与验收

- 构建时从实际参与打包的源码快照获取 commit；正常显示前 8 位。存在参与构建的未提交更改时显示 `<短ID>-dirty`，不能把它误标成对应 commit 的干净构建。具体 dirty 判定范围与时机应覆盖实际参与构建的变更，排除仅由本次构建产生的无关缓存，实施时记录规则并验证。
- 无法获取可信 commit 或变更状态时明确显示“未知”，不使用上一次构建残留值，不阻塞正常构建；CI / 导出源码无 `.git` 的构建也需要覆盖。可显示可信短 ID 但状态未知时，须明确标记状态未知，不能冒充干净构建。
- 在三种形态中从设置进入诊断信息，可见“构建提交”与复制操作；复制只包含显示的构建标识，成功 / 失败有反馈，不复制库路径、笔记或令牌；未知状态不伪造标识。剪贴板 API 及可用范围须先按 API24 核实。
- 验证干净构建、有未提交变更、无法获取元数据三类场景，并核实安装包内显示值与构建输入一致；分开记录自动测试、HAP、模拟器和 API24 / XT2 证据，真机由用户手动验收。

## 3. 明确不做

不修改包版本号或提交历史；不上传构建信息、不加入埋点、不暴露文件路径与笔记内容；不为标识生成而更改用户工作区或强制提交。

## 4. 验收记录

### 4.1 落码（2026-11-02）

- 构建期取值：`tools/generators/build_commit_info.mjs` 跑 `git rev-parse --short=8 HEAD` 与 `git status --porcelain --untracked-files=all -- <参与构建的源码路径>`，输出 `{ commitId, state, label }`。`--check` 自检 hvigor 注入与设置页接线是否还在。
- dirty 判定范围（集中在该生成器 `BUILD_SOURCE_PATHS`，不散落在构建脚本里）：`AppScope`、模块配置与 hvigor 文件、`entry/src/main/{ets,cpp}`、`entry/src/main/resources/{base,dark}`、`web/`、`native/`、`tools/{build.ps1,signing.ps1,abi.ps1,generators/}`。**排除** `entry/src/main/resources/rawfile`（由 `web/` 构建生成，会被本次构建重写）、构建输出目录与已 gitignore 的 `.local/` —— 否则每次构建都会自称 dirty。未跟踪的新增源码算变更。
- 注入方式：`entry/hvigorfile.ts` 在构建时调用生成器，经 `overrides.buildOption.arkOptions.buildProfileFields` 写入 `BuildProfile`（与既有 ABI 注入同一套 `overrides` 机制，命令行与 IDE「运行」都覆盖）。类型依据 hvigor-ohos-plugin 的 `hap-ohos-config.d.ts → ArkOptionsOpt.buildProfileFields?: object` 与 `build-opt.d.ts → ArkOptions.buildProfileFields?: object`（非凭记忆）。
- 为什么不生成 `.ets` 源文件：`BuildProfile` 落在 `entry/build/.../BuildProfile.ets`，**不进工作区**；生成源文件会把值写回源码树，下一次 dirty 判定又会把它自己算成未提交更改。这也满足 §3「不为标识生成而更改用户工作区」。
- 三类结果：clean → `49cba399`；dirty → `49cba399-dirty`；unknown → `未知`。取不到 commit 或变更状态时退化为 unknown，**不沿用上一次构建的值**，也不阻塞构建。短 ID 可信但变更状态取不到时显示 `49cba399（状态未知）`，不冒充干净构建。
- 界面：`SettingsView` 诊断信息区新增「构建提交」行与「复制」，规则在 `entry/src/main/ets/common/BuildCommitInfo.ets`（纯逻辑，Node 可测）。复制只写 `pasteboard.createData(pasteboard.MIMETYPE_TEXT_PLAIN, <标识>)`，成功 / 失败有 toast，未知状态禁用复制并提示「构建提交未知，不复制」；复制内容不含库目录、笔记或令牌。
- 剪贴板 API 按 API24 核实（本机 SDK d.ts，非凭记忆）：`pasteboard` 由 `@kit.BasicServicesKit` 导出；`getSystemPasteboard()` `@since 6`、`createData(mimeType, value)` `@since 9`、`SystemPasteboard.setData(data)` Promise 版 `@since 9`，均不超过 `compatibleSdkVersion 6.1.1(24)`。已知失败码 27787277（并发复制）/ 27787278（禁止复制）走统一失败提示。

### 4.2 证据（2026-11-02）

- `node --test tools/tests/test_build_commit_info.mjs`：**8/8 通过**。覆盖干净构建、已跟踪文件改动、未跟踪新增源码、rawfile 生成产物不算脏、无 `.git` 报未知且不复用旧值、hvigor 接线与「不写工作区」、设置页复制只带标识、纯函数未知态兜底、生成器自检。隔离夹具为临时 git 仓库，未改动本项目工作区。
- `node tools/generators/build_commit_info.mjs` 在本仓库：有未提交改动时 `{"commitId":"49cba399","state":"dirty","label":"49cba399-dirty"}`。
- `tools/build.ps1`：签名 debug HAP `BUILD SUCCESSFUL`；日志 `[build-commit] 构建提交 49cba399-dirty（dirty）`；产物 `entry/build/default/generated/profile/default/BuildProfile.ets` 内含 `buildCommitId/buildCommitState/buildCommitLabel`，与构建日志一致，**安装包内值与构建输入一致已核对**。
- 全仓 `node --test tools/tests/*.mjs`：**520 项、506 通过 / 14 失败**；14 项为改动前既有失败（源码切片锚点漂移），非本轮引入。
- 干净构建与 dirty 构建各跑一次真实构建核对：工作区有未提交改动时日志 `[build-commit] 构建提交 49cba399-dirty（dirty）`；提交后工作区干净时 `[build-commit] 构建提交 148aeecc（clean）`，两次均为 `BUILD SUCCESSFUL`，包内 `BuildProfile` 字段与日志一致。
