# v1.15 需求文档 —— 构建提交号诊断

> 状态：⚪ 规划中；v2 原型展示示例，原生构建元数据、界面和设备验证均未完成。执行顺序见 [实施总清单](../实施总清单.md)。

## 1. 范围

承接[需求池构建提交号诊断](../../requirements_backlog.md)：在“设置与关于 → 通用 → 诊断信息”中显示当前安装包构建时的 Git commit 短 ID，并支持用户主动复制。它帮助区分相同应用版本下的不同构建，不替代 `AppScope/app.json5` 或运行时的版本号。

## 2. 需求与验收

- 构建时从实际参与打包的源码快照获取 commit；正常显示前 8 位。存在参与构建的未提交更改时显示 `<短ID>-dirty`，不能把它误标成对应 commit 的干净构建。具体 dirty 判定范围与时机应覆盖实际参与构建的变更，排除仅由本次构建产生的无关缓存，实施时记录规则并验证。
- 无法获取可信 commit 或变更状态时明确显示“未知”，不使用上一次构建残留值，不阻塞正常构建；CI / 导出源码无 `.git` 的构建也需要覆盖。可显示可信短 ID 但状态未知时，须明确标记状态未知，不能冒充干净构建。
- 在三种形态中从设置进入诊断信息，可见“构建提交”与复制操作；复制只包含显示的构建标识，成功 / 失败有反馈，不复制库路径、笔记或令牌；未知状态不伪造标识。剪贴板 API 及可用范围须先按 API24 核实。
- 验证干净构建、有未提交变更、无法获取元数据三类场景，并核实安装包内显示值与构建输入一致；分开记录自动测试、HAP、模拟器和 API24 / XT2 证据，真机由用户手动验收。

## 3. 明确不做

不修改包版本号或提交历史；不上传构建信息、不加入埋点、不暴露文件路径与笔记内容；不为标识生成而更改用户工作区或强制提交。
