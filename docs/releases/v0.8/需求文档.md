# v0.8 需求文档 —— 笔记、文件夹与知识库分享

> 状态：⚪ 规划中（2026-10-25）；对应里程碑：M4.9。
> 来源：需求池 D「笔记向外分享（微信 / 飞书）」；执行顺序为 v0.7 之后、v1.0 之前。无日历交付日期承诺。

## 1. 版本定位

把当前笔记、指定文件夹或整个知识库交给微信 / 飞书分享；本地内容支持文件打包，Git 内容可选择 ZIP 或远端链接。

## 2. 完成判定

三个范围有明确入口与范围预览；单篇可生成排版图片、Markdown / ZIP，文件夹与知识库可生成 ZIP，Git 库另可选择远端链接。接收人解压后能阅读 Markdown 并加载包内本地图片；取消与失败不修改原笔记，不携带内部数据。系统分享面板调起与目标应用接收分别验收，不把调起成功当发送成功。

## 4. 明确不做

- 小红书等社媒模板、封面、尺寸适配与直发：低优先级，继续留在需求池。
- 在线托管链接、公开发布、权限管理、自动上传；本地库不虚构网页链接。
- 文件夹/整库排版长图，任意多选、跨库打包、递归收集双链目标，以及下载网络图片。
- ZIP 导入、换机恢复、完整应用备份：内容分享不等于备份恢复，原 Q2 决定见 [待决清单](../../open_questions.md#q2-zip-导出要不要进-mvp--已决定后置2026-10-17-用户决定)。
- Git clone / commit / push 排障，不改变 v0.3 的外部依赖队列。

## 5. 技术约束与依赖

- API ≤24、路径解析、AtomicFile 与隐私规则遵循 [AGENTS.md](../../../AGENTS.md) 和 [API 笔记](../../harmonyos/api_notes.md)。先核实系统分享、文件 URI 授权、ZIP 与图片生成 API 的名称、签名和限额，不能凭记忆落码；结论按 [鸿蒙知识库工作流](../../harmonyos/README.md) 归档。
- 复用已有编辑内容与预览渲染；打包前获取本次分享内容快照，后续编辑不应造成包内笔记和图片混用不同状态。生成过程不回写用户 Markdown。
- 只通过统一解析器读取当前库内内容。所引用图片缺失或越界时列出并阻止不完整打包，不静默丢失；网络图片保留原链接。
- Git 链接按托管平台和库元数据适配（GitHub / Gitee），使用分支与正确编码的文件/文件夹路径；无法确认目标存在或平台不支持时说明原因，不提供猜测链接，仍可分享 ZIP。
- 本地图片/文件分享可独立交付。Git 链接逻辑用元数据样例和已知远端目标验证；依赖完整同步链路的联调随 v0.3 补验，不能冒称已通过，也不阻塞本地范围验收。
- 实施顺序见 [实施总清单](../实施总清单.md)，交互原型见 [设计稿](../../prototype/index.html)。当前原型已覆盖单篇与仓库首页链接，文件夹与整库 ZIP 选择交互待补。
