# v1.90 需求文档 —— 超长笔记长图失败时引导改用 PDF

> 状态：规划中（2026-11-19 立项）。需求来源：用户 2026-11-19 反馈「笔记过长无法生成清晰的单张长图」；同批确认该笔记用 PDF 可正常导出 63 页（分页路径不受单张图面积限制）。
> 归属分享域；本版只改一处用户可见错误文案，**不动生成/捕获架构、不动尺寸预算**。

## 1. 版本定位

v1.9 拍板单篇笔记分享为一张连续长图，并明确：超像素预算时整图等比缩小，宽度低于 640px 时拒绝并给出替代建议。原文案只列「Markdown / ZIP」，漏掉了项目已有的 PDF 分享路径——而 PDF 走 A4 分页，正好是超长笔记的合适出路。本版把 PDF 补进这句引导，让用户一次就能选到对的工具。

## 2. 完成判定

超长笔记（高宽比 > 约 61:1，触发 `longImageGeometry` 的最小宽度拒绝）走「分享 → 图片」时，错误提示同时给出 PDF / Markdown / ZIP 三种替代方式；其余分享格式、尺寸预算、捕获与合成逻辑零行为变化。

## 3. 需求清单

### 90.1 错误文案补 PDF

- `NoteImageShareService.longImageGeometry` 宽度低于 `MIN_IMAGE_WIDTH` 时的报错文案：
  `笔记过长，无法生成清晰的单张长图；请改用 Markdown / ZIP`
  → `笔记过长，无法生成清晰的单张长图；请改用 PDF / Markdown / ZIP`。
- 该错误经 `prepareShare` 的 catch → `shareFailureMessage`（`error.message` 非空时原样透传）显示，改这一处即可让用户看到新文案；不改透传链路。
- 判定：源级断言文案含「请改用 PDF / Markdown / ZIP」；`test_note_image_share_pagination` 定向通过。

## 4. 明确不做

- 不调 `MAX_PIXEL_MAP_BYTES`（96 MiB 工程预算）、`MIN_IMAGE_WIDTH`（640px）、`MAX_PAGES`（500）——它们是 v1.9 拍板 + api_notes O3 记录的约束，放宽会撞平台 128 MB 序列化上限与接收端未验的尺寸能力。
- 不做预览阶段尺寸预警：需要额外渲染测量，与生成流程重复且更慢；捕获前 metrics 的提前失败方案另评估，不并入本版。
- 不改普通尺寸长图、PDF 分页、Markdown / ZIP / 文本分享路径。
- 不改 `UserErrorMessages.image_prepare` 的通用兜底文案（只在 `error.message` 为空时用，与超长场景无关）。

## 5. 技术约束

- 只改用户可见文案，属 UI 改动，故立版本（不套纯代码修复豁免）。
- 中文文案、无新增资源键、无新增权限；零埋点零日志零上报（硬约束 16）。
