## 背景（给我自己看的，不用复制）

- 编辑器方案已定 A（Web 组件 + CodeMirror 6），但 A 成立的前提是「WebView 里中文输入能用」——
  这一点**官方无记载，只能实测**（`api_notes.md` B5/B6），且官方建议优先 `TextArea`，
  而 CodeMirror 6 恰恰是 `contenteditable`，两者可能冲突。
- 有真机（XT2 三折叠），中文输入法必须由**人在真机上敲**，Agent 无法自己完成验证。
  所以这份提示词把交付物拆成两半：Agent 搭工程 + 出清单，**人跑真机填记录**。
- spike 结论决定 M2 走 A 还是 B，进而决定 v0.2 剩余工作量 —— 所以**先做这个，不要先做文件树**。

# 〇、最重要的两条铁律（违反直接返工）

1. **禁止凭记忆编造 HarmonyOS API 名 / 参数 / 返回值。**

   「照着记忆里或不确定的 API 写代码」踩过坑（例：折痕接口被官方答复误导，SDK 实证才发现返回的是数组）。

   - 或在本仓库 `docs/harmonyos/api_notes.md` 里找到对应条目；
   - **两者都找不到 → 停下来，在最终报告里列出「需要确认的 API」，不要用猜测的实现蒙混过去。**

# 四、你要交付什么

## 4.1 一个最小可运行的 spike 页面（能装真机）

要求：

- **一个页面里同时放两个编辑器，可切换**：
  ① **A 档**：Web 组件 + CodeMirror 6（`contenteditable`）
  ② **B 档**：Web 组件 + 原生 `TextArea`（对照组；如能顺带放一个 ArkTS 原生 `TextArea` 更好，标注清楚）
- 每档都要能：**输入中文、看光标、滚动长文（建议预置一篇 500 行以上的中文长文）、折叠切换**。
- 页面上要有**便于记录现象的东西**（这部分你设计，要求：不用看日志也能看出问题）：
  - 实时显示最近若干条 composition / input 事件的类型与关键字段（用于判断输入法有没有被吞）
  - 实时显示光标位置（行/列或 offset）
  - 一个「本次操作的观察记录」可滚动区域
- 代码位置建议（**集中放，便于事后整体移除**）：
  - `web/spike_editor/` —— 前端源码（照 `web/gitbridge/` 的结构与打包方式，esbuild 打成单文件）
  - `entry/src/main/resources/rawfile/spike_editor/index.html` —— 打包产物
  - `entry/src/main/ets/spike/SpikeEditorPage.ets` —— ArkTS 页面
  - 入口：在 `main_pages.json` 注册 + 从 `Index.ets` 顶栏加一个**临时**入口按钮，
    代码里留 `// TODO(spike 后移除)` 注释
- ⚠️ **不要动现有 v0.1 代码逻辑**（断点、库模型、路径解析器、布局矩阵一律不改），
  只加一个入口按钮。也不要动 `web/gitbridge/` 与 `entry/src/main/ets/git/`（那是 v0.3 同步代码）。

## 4.2 一份「真机验证清单」（这是本次交付的重点之一）

⚠️ **中文输入法没法自动化，必须由人在真机上敲。** 你无法自己完成 0.1 的判定，
所以你必须输出一份**可执行、可打勾的清单**，交给真机操作者（我）执行。

清单要求：

- **每一步都是具体动作 + 明确的观察点**（例：「切到拼音输入法，输入 `nihao`，
  观察候选条是否跟随光标、上屏后是否重复插入」），不要写「测试中文输入是否正常」这种无法判定的话。
- 覆盖 **0.1–0.4 四项**，每项给出：
  | 步骤 | 操作 | 预期 | 实际（待填） | 判定（✅/⚠️/❌，待填） |
- 明确写出**「什么现象算 ❌」**（不可接受）—— 例如：拼音候选条不跟随光标、上屏后字符重复、
  语音输入丢失首字、折叠后内容重载回到初始文本。
- 明确写出**「什么现象算 ⚠️（能忍）」** —— 例如：候选条位置略偏但插入正确、resize 有短暂闪烁但不丢内容。
- 清单末尾留一个**结论栏**：`方案 A 可用 / 需降级到 B / 需进一步验证`，由真机操作者回填。
