# v1.92 需求文档 —— PDF 逐页快照降分辨率（scale 试验，P6）

> 状态：**试验性立项**（2026-11-20）。需求来源：用户 2026-11-20 反馈 PDF / 长图预览慢，要求「试一下」优化；讨论「预览少预览几页」后确认该方向不省总时长（合成 PDF 复用预览时截的逐页 JPEG，只截 K 页只是把等待推迟到点确认后），改走「降低每页截图分辨率」。
> 归属分享域；本版**只改 PDF 逐页捕获的 snapshot scale**，长图路径保持 1.0，不动 Web 等待（P2 已证伪）、不动旧帧校验语义、不动分页与合成逻辑。
> ⚠️ 试验性质：真机性能对比已通过（约 15.5s→10.0s）；「预览一页很短」的页几何 / 清晰度待判定后决定**保留 / 调整 scale 值 / 整版回退**。判据与数据见 `docs/engineering/分享预览渲染性能优化.md` §3.5 / §3.6 / §4 P6。

## 1. 版本定位

真机打点（63 页、连跑两轮、125 条）显示 PDF 预览约 15s = 63 × 235ms，三段几乎均分：

| 段 | 单页 | 63 页 | 可动性 |
|---|---|---|---|
| `waitMs` | 94ms | 5.9s | ❌ 含 64ms 合成必等，P2 已实测删掉净亏（43.4s），§3.4 明令不再动 |
| `snapMs` | 73ms | 4.6s | ✅ 截图像素量相关 |
| `tailMs` | 68ms | 4.3s | ✅ crop + JPEG 编码像素量相关 |

`snapMs + tailMs ≈ 8.9s` 都与**截图像素数量**成正比。`componentSnapshot.get` 的 `SnapshotOptions.scale`（SDK `@ohos.arkui.componentSnapshot.d.ts:414`，`@since 12`，API24 可用）等比缩小截图产物，官方注释亦明示「高 scale 会增加截图耗时甚至失败」——反向即降 scale 能省时。这是唯一没试过、且风险可控的方向。

## 2. 完成判定

同一篇 63 页笔记、真机 XT2，装本版 HAP 跑 PDF 分享，`ShareDbg` 打点中 `snapMs` / `tailMs` 相对 §3.3 基线（73 / 68ms）**明显下降**，且 `waitMs` 与 `retries` 不劣化；肉眼确认 PDF 页清晰度可接受。任一不满足即按 §4 判据回退或调值。

## 3. 需求清单

### 92.1 PDF 逐页快照传入 scale

- `ShareFlowPanel.ets` 顶部新增常量 `PDF_SNAPSHOT_SCALE: number = 0.5`（试验值，注释写明依据与回退路径）。
- `captureSegmentVerified(prevBuffer, snapshotScale)` 增加第二参数，透传到
  `get(id, { waitUntilRenderFinished: true, scale: snapshotScale })`。
- PDF 循环（`:846` 附近）传 `PDF_SNAPSHOT_SCALE`；**长图循环（`:686` 附近）固定传 `1.0`**。
- 判定：源级断言锁定签名、`scale: snapshotScale` 透传、常量值、两循环各自实参。

### 92.2 长图不受影响（正确性硬约束）

- `longImageGeometry` 依赖**原始截图尺寸**与 `pixelsPerVp` 反推 96 MiB 预算 / 640px 下限；若长图也降 scale，几何计算与缩放系数全错。故 scale 由调用方传入、长图固定 1.0，不写成方法内固定值。
- 判定：源级断言锁定长图实参为 `1.0`；长图分享功能回归正常。

### 92.3 尺寸无关的校验不被破坏

- PDF 循环里的 A4 宽高比校验、页间尺寸一致性校验、按 `imageInfo.size` 比例计算 `cropPx`、按 `pageAspects` 贴图合成——全部是**比例**运算，等比缩放不改变结果。代码不改这几处。
- `readPixelsToBuffer` 读的是缩放后的缓冲，旧帧检测「两段像素完全相同」的判据在低分辨率下仍需成立（见 §5 风险）。

## 4. 明确不做

- **不动 `waitMs`**：64ms 死等是 XT2 合成表面的必要等待，P2（`f8a56c5` 回退）已实测删掉后重试率 0.8%→87%、墙钟 15.5s→43.4s。⛔ 不再提议删或缩短。
- **不做「预览少截几页 / 延迟捕获」**：合成 PDF 复用预览时逐页 JPEG，只截前 K 页需点确认后补截剩余页，总时长不变且多出交互与失败回滚；只有「多数预览最终不导出」才划算，未获该使用模式证据。
- **不改 `MAX_PIXEL_MAP_BYTES` / `MIN_IMAGE_WIDTH` / `MAX_PAGES`**（v1.9 拍板 + api_notes O3）。
- **不改长图、Markdown / ZIP / 文本分享路径**，不改分页与合成逻辑，不动 `quality: 92`（P3 前置未满足）。
- **不改 Web 侧 `setShareCaptureScrollTop`**：不涉及 rawfile 产物，本版无需重建 mdpreview。

## 5. 技术约束与风险

- `SnapshotOptions.scale` 与 `waitUntilRenderFinished` 同属一个 options 接口（已核 SDK 声明），`@since 12` 低于 API24，可用。
- **清晰度风险**：0.5 使页图物理像素减半，PDF 贴图是屏幕截图非矢量，放大阅读可能有损。用户明确接受「试一下」，验证后定去留。
- **旧帧检测风险**：低分辨率下两页「像素完全相同」的概率理论上更低（细节更多被抹平反而可能相同），需按 §5.1 触发一次重试路径确认仍报错而非静默放行。
- 零新增权限、零埋点零日志零上报（硬约束 16）；现有打点只记耗时数字不记笔记内容。
- `SHARE_PERF_TRACE` 诊断期仍为 `true`，优化验收后按优化文档 §6 约定**删除**打点代码。
