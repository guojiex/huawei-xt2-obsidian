# 〇、两条铁律（违反直接返工）

1. **禁止凭记忆编造 HarmonyOS API 名 / 参数 / 返回值。** 写任何一个 API 之前，先在 `docs/harmonyos/api_notes.md` 或当前 SDK 类型定义里核实它真实存在且签名一致；两者都找不到 → 停下来，在最终报告里列出「需确认的 API」，不许用猜测的实现蒙混。
2. **严格只用 API ≤ 24 的接口**（compatibleSdkVersion 6.1.1(24)）。发现更方便的接口是 API 25/26 才有（例：`listFileExt` 的 fileFilter），必须降级到 ≤24 的等价写法并在报告里注明。

# 一、环境事实（都已核实，不要质疑也不要改）

- ArkTS + Stage 模型，禁止 FA 模型 / JS；目标 API 24；包名 `com.jxg.huaweiobsidian`
- `deviceTypes` 保持 `["phone","tablet","2in1"]` —— 三折叠在系统里始终被识别为 `phone`，全展开 10 英寸也不变，别试图改
- 沙箱内读写不需要任何权限，`module.json5` 只声明 `INTERNET`，不要新增权限
- 仓库根目录：`E:/github/huawei-xt2-obsidian`
- **测试方式（用户已定，必须遵守）**：不在模拟器上主动制造崩溃、强杀进程、写入中断；恢复与失败处理只用单测（可控时钟、存储失败注入、重建服务实例）；模拟器只验证正常编辑、保存、切换、重新打开。单测不代表真实进程中断或设备级原子性已验证
- 模拟器、Node 冒烟、编译、真机四类证据**分别报告，不互相替代**；本地 UI 证据不外推到 XT2

# 二、动手前必读（每轮开工都按顺序读）

1. `AGENTS.md` —— 硬约束、命令、已知坑，逐条遵守不要反驳
2. `docs/releases/README.md` —— 版本化开发规则 R1–R10
3. `docs/releases/实施总清单.md` —— **当前目标顺序与未完成项的唯一排期来源**，以其中「当前优先任务 / 当前目标顺序」为准，历史顺序记录不覆盖它
4. `docs/mvp_design.md` + `docs/open_questions.md` —— 已定决策不重新讨论（三栏自绘、FoldSplitContainer 已否决、本地 Agent View 不做等）
5. `docs/harmonyos/api_notes.md` —— 鸿蒙行为单一真源；标 ⚠️/❓ 的结论在真机验证前不许写进关键路径
6. 当前要做的版本的 `需求文档.md` 与 `实现提示词.md`（如有）—— **动码前必须已读**

# 三、工作循环（不停下来，除非满足第六节停止条件）

每轮：

1. **取下一项**：读实施总清单，按优先级取「当前还能做」的下一项——当前目标顺序（收口 v0.9 → 验收 v0.10 动效 → 收口 v0.11）→ 实施总清单 §2 领取顺序表（v1.4 等）→ 其他未收口本地版本。外部依赖队列（v0.3 剩余验收、小艺平台相关）不主动领取。只领取一个版本或其中一个可独立验收的任务。
2. **落码**：改动严格对应该版本需求文档里的条款；需求文档里没有的不许顺手做；新冒出的需求先记 `docs/requirements_backlog.md`，不当轮加塞。
3. **本地验证**（第四节）全过才算这项做完。
4. **记录**：更新该版本 `需求文档.md` §6 验收记录——写清做了什么、哪些测试及结果、哪些标「待验证」及原因。**没有证据的项不许标完成，任何版本不许写「已发布」。**
5. **提交**：只包含本任务改动（代码 + rawfile 产物 + 文档一起），提交信息用中文 Conventional Commits。提交前检查 diff、未跟踪文件和敏感内容。**保留他人未提交的改动**；禁止 `git reset --hard`、force push、打 tag、改 `versionName`/`versionCode`。
6. 立即进入下一轮，不要输出「要不要继续」之类的问题。

# 四、本地验证清单（每项任务提交前跑）

- 相关 Node 测试：动了 `web/gitbridge/src` 才跑 `cd web/gitbridge && npm run smoke`；mdeditor / mdpreview 相关 Node 测试按各版本 §6 记录的命令执行
- 生成器检查：改了样例 / changelog 数据才跑 `python3 tools/build_sample_vault.py --check`、`python3 tools/build_changelog.py --check`
- 改了 `web/gitbridge/src` 必须 `node build.mjs` 重新打包，产物一起提交；改编辑器 / 预览 web 源码同理重建 rawfile 产物（否则真机跑旧代码）
- 构建：`./tools/build.ps1`（命令行构建，已自动带 JAVA_HOME），HAP 必须 BUILD SUCCESSFUL
- 生成的 ETS / CHANGELOG.md / 原型标记区不许手改
- 跑不了模拟器就如实记录「未跑」，不许假装跑过

# 五、Skip 规则（遇到这些就跳过，记录原因，继续下一项）

1. 需要 XT2 / API24 真机才能判定的 → 标「待验证（需 XT2/API24）」，skip
2. 需要外部能力 / 第三方条件的（真实小艺平台调用、平台审核发布、真实远端 git 提供商认证、接收端应用实际读取）→ 标「待验证（外部依赖）」，skip
3. API 名 / 签名在 api_notes.md 和 SDK 里都核实不了的 → 列入报告「需确认的 API」，跳过该子项
4. 同一项试了两轮还失败 → skip，在 §6 记录失败原因，不死磕
5. 需要用户拍板的新范围 / 新决策 → 不做，记录「待用户决策」
6. v0.3 既定门槛：在设计并验证应用级恢复 / 事务边界之前，**不许调用 checkout、不许实现 pull**；v0.3 其余按 Native 优先路线与验收记录推进
7. 破坏性操作一律不碰：删库、清数据、`reset --hard`、动签名配置（`build-profile.json5` 永久保持 `signingConfigs: []`）

# 六、停止条件

同时满足才停：

- 当前目标顺序 + §2 领取顺序里的每一项都已处理完：要么有本地证据通过，要么明确标了「待验证 / skip + 原因」并写进对应版本 §6
- 外部依赖队列剩余项都已标注阻塞原因
- 最后 `git status` 干净，或只剩写明了原因的未提交改动

停止时输出最终报告（结论先行）：

1. 做了哪些版本 / 条款，各自结果
2. 跑过的测试与构建结果清单（Node / 生成器 / 构建 / 模拟器分别列）
3. 全部「待验证」项及原因，按「需 XT2/API24」「外部依赖」「待用户决策」分类
4. 建议的下一步
