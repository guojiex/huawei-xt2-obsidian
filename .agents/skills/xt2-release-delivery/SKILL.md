# 版本任务交付

目标是尽快交付一个有需求依据、可验证、可提交的完整变更。不要把“持续开发”理解为持续搜索或持续审计。

## 领取与续接

- 新会话先按根目录 `AGENTS.md` 的必读入口完成一次核对，再以 `docs/releases/实施总清单.md` 领取当前可执行的最高优先项；版本号、已有未提交代码不决定优先级。
- 每项任务先明确：版本需求编号、当前缺口、最小修改范围、验证方式和退出条件。用简短进度说明即可，不为小任务另建计划文档。
- 续接或上下文压缩后，检查当前 Git 状态、相关 diff 和任务对应的最新记录；复用已核实且未变化的上下文，不从头重读全部手册。新证据、文件变动或疑点才触发定向补读。
- 用户中途询问实现原因、速度或流程时，若未要求暂停或换目标，基于已有证据简答后继续原任务；先检查现有 diff 续做，不重启全量阅读 / 审计。
- 对用户明确指出的可复用流程问题，只把最小、稳定的规则补入本 Skill 或既有决策文档，不另造重复知识；随后立即应用于当前任务。

## 探索与修改

- 优先按已知文件、符号和调用链定位；独立读取并行执行，查询输出限于相关片段。
- 已能复现或已有充分源码证据后，先完成该问题的最小修复与回归。只有新发现会影响本任务正确性或数据安全，才扩展调查，并说明原因。
- 小日志修复不自动升级为全 App 日志审计；普通改动不自动升级为架构重构或安全加固。无关发现留待原版本或需求池，不能直接开工。
- 不重复查询已回答且输入未变的问题。遇到测试误报先核查断言范围，不能为了匹配正则删除正确的业务代码。
- 不打印大型生成 HTML / minified bundle 的完整 diff。检查源码 diff、生成命令、产物统计和必要的定点内容；生成物按现有构建链更新，不手改。

## 验证只为证明改动

| 改动 | 默认验证 |
| --- | --- |
| 仅文档或工作规则 | 差异、链接与已有文档 / Skill 校验；不构建 HAP |
| 局部日志或错误提示 | 定向回归、受影响模块回归；涉及 ArkTS / Web 产物时完成相应构建 |
| 保存、恢复、目标代次或共享状态 | 先复现，覆盖失败 / 竞态和关联调用方，再做整合回归与构建 |
| UI 或交互 | 自动回归与对应构建，再按版本要求做可安全执行的视觉 / 交互检查 |

- 以上是选择测试的默认依据，不减少需求文档已经承诺的验收。全仓回归在逻辑变更稳定后集中执行，不因同一问题的每次微调重复全套测试。
- 同一源码、工具链和夹具下已经通过的验证可复用，记录适用范围；依赖变化后重跑受影响项。不把旧证据写成本轮新执行。
- 已确认与本任务无关的环境或基线失败，记录具体失败与证据；除非阻断本任务验证，不顺手修复，也不反复重跑期待自行通过。
- 小任务不以增加搜索轮数、测试数量或进度汇报次数作为完成度。等待命令时报告新结果或实际阻塞，不重复讲同一计划。

## 抽象决策与快速核对

- 新增独立 Service / Manager / Repository 前，先把需求要求的行为与代码组织方式分开：定位需求条目、现有调用方与生命周期，再说明为什么不能由已有模块直接承担。若只是包装一段局部流程，优先沿用现有边界；不能从类名、测试或现存代码反推用户已批准该抽象。
- 用户问“为什么有这个服务”时，先沿“需求行为 → 实际调用点 → 测试证据”给出简短解释，并明确哪些是必需行为、哪些是当前实现选择；不要把解释问题扩成架构审计或未经要求的重构。
- 草稿恢复案例：v0.2 §2.5 要求已持久化草稿可恢复、按库 / 文件隔离并在正常保存后清理；v1.7 §17.7 要求接入草稿恢复并在保存失败时保留修改，§17.3 要求正文、草稿和保存结果来自同一编辑状态。`NoteDraftService` 当前集中处理快照与文件生命周期；这些需求能证明行为必要，不能单独证明独立服务边界已获用户批准。重访时定向检查需求和调用链即可，不必重读整套发布文档。
- 小而明确的任务采用一次定向核对：查需求、相关实现 / 调用点和对应测试；三者一致后立即实施并跑聚焦验证。只有证据冲突、数据安全受影响或缺少关键产品决定时才扩大调查或提问。

## 退出、提交与下一项

达到事先定义的退出条件后，不再追加“再全面检查一下”：

1. 检查相关 diff，更新对应验收记录与实施总清单，分别标明源码、自动测试、构建、模拟器、API24 / XT2、发布证据。
2. 只暂存本任务文件 / hunk，执行 `git diff --cached --check` 并检查暂存范围，按仓库规范提交。已有未提交改动不覆盖、不回滚、不混入提交；混合文件需可靠拆分，不能为省事整文件提交。
3. 简短报告完成项、验证、提交与剩余阻塞，然后领取下一独立任务，不逐项询问是否继续。

### 共享文件的部分暂存（与并行会话共存）

目标文件同时带有并行会话未提交改动（如 api_notes.md 被另一工作流改写）时，自己的增量按「构造暂存 blob」提交，不整文件提交：

- HEAD 原始字节用 `cmd /c "git show HEAD:<path> > <tmp>"` 导出；**PowerShell 重定向会转码，禁止**用它保字节。
- 拼接前先核**插入点的实际行尾**：仓库存在混合行尾文件（api_notes.md 即 LF 区 + CRLF 区并存），自己的增量按 HEAD 插入点的行尾风格拼，不整体归一。
- 入库必须 `git hash-object -w --no-filters`：缺 `--no-filters` 时 git 对文件参数应用 autocrlf clean 过滤**静默改写字节**（出现「LF will be replaced by CRLF」警告即中招信号）。
- `git update-index --cacheinfo 100644,<sha>,<path>` 后用 `git diff --cached -- <path>` 复核：必须只含目标增量（纯 `+` 行）；出现大面积 EOL 差异 = 行尾或过滤器没对齐，推倒重来，不带着噪声提交。
- 提交后把同一增量按**工作树的行尾风格**同步进 WT 文件，避免并行会话后续提交时把自己的内容显示为删除。

阻塞项写清已完成内容、失败证据、原因和恢复步骤，再转向不依赖它的任务。没有新条件时不反复轮询。

## 不得用提速突破的边界

- 需求来源、设计真源、HarmonyOS API 核实和签名规则仍按 `AGENTS.md` 与当前版本文件执行；不凭原型推断原生完成。
- 不操作用户 XT2；不以模拟器、mock 或构建代替 API24 / XT2 证据。不主动制造模拟器崩溃、强杀或写入中断，失败 / 恢复用可控注入与服务重建验证。
- 已失败的设备用例必须保留失败结论；没有安全隔离夹具不编辑用户笔记或教程样例，不擅自清数据。
- 不修改在线政策、不发布、不提交商店审核、不操作真实 Git 远端，除非用户另行明确授权。
- 最新优先级、阻塞和产品决定只查当前版本文档，不把易过期的进度、测试计数或提交号固化在本 Skill。
