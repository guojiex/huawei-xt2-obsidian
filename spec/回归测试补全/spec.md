# Feature Specification: 回归测试补全（Bug 驱动）

**Created**: 2026-11-08  
**Status**: Approved  
**Input**: User description: "
持续补充回归测试用例，把我们当前已经实现了的需求，都补充好单元测试和ui测试。保证曾经出现的bug不回归。同时如果发现有bug就修掉增加回归测试"

## Overview

为曜石笔记当前已实现的需求系统性补全回归测试防线。主线策略为 **bug 驱动**：盘点全部历史修复记录（143 个 fix 提交 +
`docs/harmonyos/api_notes.md` 实测踩坑），逐条核对是否已有防回归测试，缺口全部补上；同时按 EM 模拟器回归用例组扩展 UI
自动化可达子集。过程中发现的 bug 直接修复并补防回归测试。

本工作是**质量保障资产**，不是产品需求：不新建 `docs/releases/vX.Y` 版本目录（QA 资产豁免，见 `docs/testing/UI自动化测试.md`
），除纯 bug 修复外不改变任何产品行为。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Bug 回归清单与防线补全 (Priority: P1)

维护者需要确认：历史上每一个已修复的 bug，今天都有至少一道自动化防线（Node 单测、hypium UI 用例或源码级断言测试），防止同类问题随后续版本回归。

**Why this priority**: 143 个历史 fix 中已确认部分无防回归测试（如 faqs-arkui-95 菜单整屏宽、`@BuilderParam` this
丢失闪退等仅靠人工目视）。这些是真实发生过的缺陷，回归概率最高，是本工作的核心价值。

**Independent Test**: 产出《bug 回归清单》文档，每条历史修复标注「已有防线（测试名）」或「无防线」；对无防线条目逐个补充测试后清单中不再存在「无防线」状态。

**Acceptance Scenarios**:

1. **Given** 全部 143 个 fix 提交与 api_notes 实测踩坑记录， **When** 逐条核对现有测试资产（tools/tests 135 个 Node 测试、17
   个 UI 用例、源码级断言）， **Then** 每条 bug 在《bug 回归清单》中登记：bug 摘要、根因类别、防回归测试归属（测试文件/用例名）或标记缺口。
2. **Given** 清单中标记为「无防线」的条目， **When** 按其所属层面（逻辑层 / UI 层 / 视觉 token 层）补充对应类型测试， **Then**
   每条缺口获得至少一道自动化防线，且全仓测试通过。
3. **Given** 无法自动化验证的条目（如纯真机/纯视觉/环境阻塞项）， **When** 评估后， **Then** 在清单中标注「不可自动化 + 依赖的人工
   EM 用例编号」，不硬凑假测试。

---

### User Story 2 - 过程 Bug 修复 (Priority: P2)

在补测试过程中发现的新 bug（测试写出来暴露的实现缺陷），直接修复，且修复本身必须带防回归测试。

**Why this priority**: 补测试的直接目的就是暴露缺陷；发现了不修等于白测。修复沿用仓库 fix 提交惯例，纯 bug 修复不要求对应版本需求文档。

**Independent Test**: 每个被修复的 bug 有：修复 diff + 修复前失败的防回归测试（修复后通过）。

**Acceptance Scenarios**:

1. **Given** 新写测试暴露的实现缺陷， **When** 定位并修复， **Then** 修复提交包含防回归测试，该测试在修复前失败、修复后通过。
2. **Given** 修复涉及 ArkTS 源码， **When** 修复完成， **Then** 签名 HAP 构建成功且相关定向回归全部通过。

---

### User Story 3 - UI 自动化扩展（EM 可达子集） (Priority: P2)

维护者需要把人工模拟器回归用例（`docs/testing/模拟器回归用例.md` EM-A～M）中 x86 模拟器可达、且尚未自动化的子集纳入 hypium
套件，降低每轮人工回归负担。

**Why this priority**: UI 自动化现仅 17 用例，EM 可达子集仍有大量未自动化（快切范围分段、设置诊断/更新日志、回收站恢复、同步界面、导入弹窗等）。

**Independent Test**: 新 UI 用例全部在 `UI自动化测试.md` 映射表登记（套件、用例、覆盖要点、EM 对应）；映射表中不再存在「EM
可达但无自动化对应」的空白项。

**Acceptance Scenarios**:

1. **Given** EM 用例组中 x86 可达且未自动化的条目， **When** 按 UI 自动化边界（不做 Web
   文本注入、不做拖拽/折叠形态切换、不做像素断言、不注入崩溃）筛选并实现， **Then** 新用例在映射表登记，套件注册进
   `List.test.ets`。
2. **Given** 新 UI 用例需要的控件锚点， **When** 主工程控件缺 `.id()`， **Then** 为主工程补 kebab-case
   id（沿用现有命名），不改变布局与行为。
3. **Given** 全部 UI 用例编写完成， **When** 收尾阶段统一在 x86_64 模拟器执行一轮全量， **Then**
   全部通过（或区分「用例失败」与「环境阻塞」如实记录），证据落 `.local/uitest/`。

---

### User Story 4 - 测试基建一致性维护 (Priority: P3)

所有新增测试资产遵循现有基建约定，保证可一键回归。

**Why this priority**: 仓库已有成熟的测试 harness（Node 自研 runner、`tools/uitest.ps1`、生成器 `--check`
），新测试必须挂进现有链条而不是另起炉灶。

**Independent Test**: 全仓 Node 测试一键可跑且零新增失败；`uitest.ps1 -Suite` 可选执行新 UI 套件；文档映射表与实际用例一一对应。

**Acceptance Scenarios**:

1. **Given** 新增 Node 测试， **When** 执行全仓测试， **Then** 除既有 5 项基线失败（原型 v2 旧断言 4 项 + Windows SDK 路径
   1 项）外零新增失败。
2. **Given** 新增 UI 套件/用例， **When** 运行 `.\tools\uitest.ps1`， **Then** harness 能构建、装机、执行并解析结果，
   `UI自动化测试.md` 映射表与用例实况一致。

---

### Edge Cases

- 历史 fix 中部分 bug 的根因已被后续重构消除（代码不复存在）：清单标注「根因已消除，防线为现状测试」，不硬造测试。
- 同一 bug 被多个 fix 提交反复修复：合并为一条清单条目，登记最终修复与防线。
- UI 用例在 x86 模拟器上因环境阻塞（冷启动首击被吞、窗口不可见等已知坑）而非用例缺陷失败：按现有约定先修超时/选择器，确属环境阻塞的记录原因并区分，不硬凑通过。
- 补测试过程中触发的既有基线失败变化（5 项之外新增失败）：必须归因——是本工作引入的回归则修复，是暴露的既有缺陷则走 US2 修复流程。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 产出《bug 回归清单》文档，覆盖全部历史 fix 提交（143 个）与 api_notes 实测踩坑条目，每条登记 bug
  摘要、根因类别、防回归测试归属或缺口标记。
- **FR-002**: 清单中每个「无防线」缺口 MUST 在本工作内获得对应层面的自动化测试（逻辑层→Node 单测；UI 层→hypium 用例；视觉
  token 层→源码断言测试），或明确标注不可自动化的原因与依赖的人工 EM 用例编号。
- **FR-003**: 过程中发现的实现缺陷 MUST 直接修复，且每个修复附带修复前失败、修复后通过的防回归测试。
- **FR-004**: UI 自动化扩展 MUST 遵守既有边界：不做 Web 编辑器文本注入、不做拖拽与折叠形态切换注入、不做像素级视觉断言、不制造崩溃/强杀/写入中断、不碰真实
  Git 远端。
- **FR-005**: 新 UI 用例 MUST 在 `docs/testing/UI自动化测试.md` 映射表登记（含 EM 对应用例编号；无对应 EM 用例的先补 EM
  用例），并在 `List.test.ets` 注册。
- **FR-006**: 全部 UI 用例编写完成后 MUST 在 x86_64 模拟器统一执行一轮全量，结果如实记录（通过/失败/环境阻塞分开），证据存
  `.local/uitest/`（gitignore）。
- **FR-007**: 所有新增测试 MUST 遵守隐私红线：笔记内容（标题/文件名/路径/正文/字数/标签）不进入日志与埋点；测试数据用
  `uitest` 前缀 + 时间戳唯一名等既有约定。
- **FR-008**: 测试资产变更后全仓 Node 测试 MUST 通过（既有 5 项基线失败不计），签名 HAP 构建 MUST 成功。

### Key Entities

- **Bug 回归清单（条目）**: 历史修复记录 → 字段：来源（commit/文档）、bug
  摘要、根因类别（状态管理/布局约束/文件IO/焦点/日志隐私/构建链/其他）、涉及版本、防回归测试归属（可多个）、状态（已有防线/已补防线/不可自动化/根因已消除）。
- **UI 用例映射（行）**: 套件名、用例名、覆盖要点、EM 对应用例编号——与 `UI自动化测试.md` 现有表结构一致。
- **防回归测试（Node/UI/源码断言）**: 挂接现有 harness 的测试单元，命名沿用现有约定（`test_*.mjs`、`Ui<域>.test.ets`
  小写下划线用例名）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 《bug 回归清单》覆盖 100% 历史 fix 提交；清单内不存在未处置的「无防线」条目（已补 / 不可自动化+人工依赖 /
  根因已消除，三态之一）。
- **SC-002**: 全仓 Node 测试在全部新增测试合入后通过，新增失败为 0（5 项既有基线失败除外）。
- **SC-003**: UI 套件总用例数较现状（17）显著增长，且新增用例在模拟器终验轮全部通过或如实区分环境阻塞。
- **SC-004**: 过程中发现并修复的每个 bug 均附带防回归测试（修复前失败、修复后通过可复演）。
- **SC-005**: `docs/testing/UI自动化测试.md` 映射表与实际用例一一对应，无「可达但未登记」项。

## Assumptions

- 本机环境（Windows x86_64 宿主、DevEco、双 ABI libgit2 已编、x86_64 模拟器可用）与 2026-11-07 UI 套件 17/17 时一致；模拟器终验轮按
  `xt2-emulator-regression` Skill 环境前置执行。
- 「已经实现了的需求」以实施总清单及各版本需求文档中「本地实现完成」记录为准；纯设备验收待用户项不影响测试补全。
- Node 单测继续用 `tools/tests/` 自研 harness（esbuild + vm + 源码切片断言），不引入新测试框架。
- 5 项既有基线失败（原型 v2 旧断言 4 项 + 硬编码 Windows SDK 路径 1 项）不在本轮修复范围，保持原状。
- spec 工件（本目录）在 QA 资产完成后按用户指示保留或清理；测试资产与清单文档本身是长期资产。
